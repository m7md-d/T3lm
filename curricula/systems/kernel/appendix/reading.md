# ماذا تقرأ ومتى

## القاعدة

لا يُقرأ مرجعٌ كاملاً قبل البدء. لكل وحدةٍ قراءةٌ محدودةٌ مرتبطةٌ بالمشكلة التي
تُبنى فيها، والمواصفاتُ الكبيرة **بيئةُ عملٍ كـ`man pages` لا واجبُ قراءة**.

والإجراء ثمانٍ:

```
اقرأ سؤال الوحدة
 ↓ اقرأ قسماً محدَّداً يكفي لبناء نموذجٍ ذهنيّ
 ↓ افتح المواصفة عند الحقول أو التعليمات التي ستنفّذها
 ↓ ابنِ أصغر نسخةٍ تعمل
 ↓ اكسرها عمداً
 ↓ ارجع إلى نظامٍ حقيقيّ وقارن
 ↓ دوّن الفجوة التي اكتشفتها
 ↓ انتقل إلى الفرع التالي
```

---

## ترتيب الثقة

عند اختلاف المصادر، هذا هو الترتيب — وهو يخالف ترتيب بقيّة مناهج المستودع، لأن
الادّعاء عن سلوك المعالج لا يقرّره تشغيلٌ ولا كود:

```
مواصفة المعمارية أو البروتوكول
    ↓ توثيق التنفيذ الرسميّ
    ↓ مصدر نظامٍ حقيقيّ
    ↓ مادّةٌ جامعية أو نظامٌ تعليميّ
    ↓ wiki أو درسٌ مجتمعيّ
    ↓ مدوَّنة أو منتدى أو فيديو
```

فإن خالف مقالٌ في OSDev مواصفةَ Intel في سلوك استثناءٍ أو بتٍّ في جدول الصفحات،
**فالمواصفة هي الفيصل**. وقد وقع ذلك في هذا المنهج مرّتين: في الفصل `02` حيث
أظهر المحاكي سلوكاً أوسع ممّا تضمنه المواصفة، وفي الفصل `03` حيث لم يكتب بتّاً
تقول المواصفة إنه يُكتَب.

## المراجع الدائمة

| | النوع | يُفتَح عند |
|---|---|---|
| **Intel® 64 and IA-32 SDM** — المجلّد ٣ خاصّةً | مواصفة | كل فصلٍ تقريباً: paging، الامتياز، GDT/TSS، المقاطعات، APIC، SMP |
| **AMD64 APM, Vol. 2** | مواصفة | صياغةٌ ثانية حين تلتبس الأولى — long mode وترجمة الصفحات |
| **System V psABI (x86-64)** | مواصفة | الفصول `07` و`11` و`15`: تمريرُ الوسائط، ومحاذاةُ المكدَّس، وما يُحفَظ |
| **System V gABI — ELF** | مواصفة | الفصلان `01` و`16`: الترويسة، وprogram headers، والتحميل |
| **Limine Protocol** | بروتوكول | الفصول `01` و`04` و`22`: ما يُسلَّم، وحالةُ الدخول، وإيقاظُ المعالجات |
| **OSTEP** | تعليميّ | النموذجُ المفاهيميّ قبل البناء: الذاكرة، والجدولة، والتزامن، والملفّات |
| **xv6 (كتاب ومصدر)** | نظامٌ تعليميّ | **بعد** بناء كل subsystem، للمقارنة |
| **Linux Kernel Documentation** | تنفيذ | بعد بناء نسختك: كيف يفعلها نظامٌ في الإنتاج |
| **OSDev Wiki** | مجتمعيّ | حين تعلق في تفصيلٍ عمليّ — ويُراجَع بالمواصفة |

## قراءةُ نواةٍ حقيقية

بعد أن تبني، لا قبل. والترتيب:

**١. xv6.** صغيرةٌ تُقرأ كاملةً، وقريبةٌ من تصميمنا. اقرأ `swtch.S` بجانب
`switch.S` عندنا، و`trap.c` بجانب `idt.c`، و`vm.c` بجانب `vmm.c`. والفرقُ في
`proc.c`: عندهم جدولُ عملياتٍ ثابتٌ وحالاتٌ أكثر.

**٢. Linux، حسب subsystem.** لا من أوّل ملفٍّ إلى آخره:

| بعد فصلنا | اقرأ |
|---|---|
| `04` · `06` | `mm/page_alloc.c` (buddy) · `mm/slub.c` |
| `05` | `arch/x86/mm/` · `include/asm-generic/pgtable.h` |
| `07` · `08` | `arch/x86/entry/entry_64.S` — وهو نظيرُ `isr.S` عندنا |
| `11` · `13` | `arch/x86/entry/entry_64.S:__switch_to_asm` · `kernel/sched/core.c` |
| `15` | `arch/x86/entry/syscall_64.c` · `arch/x86/lib/usercopy_64.c` |
| `19` | `fs/open.c` · `fs/read_write.c` · `fs/file.c` |
| `24` | `fs/pipe.c` |

**٣. seL4 أو microkernel آخر.** ليس للتنفيذ بل للحدود: أعِد قراءة كل ما بنيتَه
حين لا تكون التعريفاتُ ونظامُ الملفّات والشبكة **داخل** النواة. أي فصلٍ يبقى كما
هو، وأيٌّ ينقلب؟

## استعمال مشاريع الآخرين

**ممنوعٌ في المسار الأساسيّ:**

```
انسخ تنفيذاً ← عدّله حتى يُقلِع ← ادّعِ الفهم
```

**والمطلوب:**

```
اشتقّ تصميمك الأصغر ← نفّذه ← راقبه ← ثم قارِن بنواةٍ أخرى ← فسّر لماذا اختلفوا
```

وإن وجدتَ تنفيذاً قبل أن تحاول تصميمك، فاكتب أوّلاً توقّعك: **أي حالةٍ يجب أن
توجد؟ وأي ثابتٍ يجب أن يصحّ؟ وأي آليةٍ عتادية لازمة؟** ثم افتح المصدر.

---

## Definition of Done

لا تُعَدّ الوحدة مكتملةً لأن الكود يعمل. خمسةُ artifacts:

```
مخطّطُ نموذجٍ ذهنيّ
تنفيذٌ يعمل
تجربةُ فشل
أثرُ تنفيذ
ملاحظةُ مقارنة
```

وجدولُ الـArtifact في نهاية كل فصلٍ يسمّي الخمسة لتلك الوحدة. **وهذه الخمسة هي
ما يمنع تحوّل المنهج إلى سلسلة دروسٍ منفصلة.**
