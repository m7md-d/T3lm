# الفصل 01 — الإقلاع وصورة الكيرنل

## المشكلة

نواتُك ملفٌّ على قرص. فمن يقرؤه إلى RAM، وعلى أي عنوان، وبأي حالةٍ يترك المعالج
قبل أن يقفز إليك؟

وهذا الفصل لا يكتب bootloader. نستعمل واحداً معروفاً ونقرأ **عقده**: ما يطلبه
منّا، وما يعطينا، وما يتركه غير معرَّف. فالبديهية ٢ تسأل عن الآلية الخام تحت
التجريد، والآلية الخام هنا **بروتوكولٌ مكتوب** لا سحرٌ في الـfirmware.

---

## الآلية الخام: ثلاث تسليماتٍ قبلك

| من | إلى | ماذا يسلّم |
|---|---|---|
| إعادة التعيين | الـfirmware | معالجٌ في نمطٍ حقيقيّ ١٦ بت، وRIP على reset vector |
| الـfirmware (BIOS/UEFI) | الـbootloader | ذاكرةٌ مُعدَّة، وخريطةُ RAM، وطريقةٌ لقراءة القرص |
| الـbootloader | نواتك | نمطٌ طويل، وجداولُ صفحاتٍ عاملة، وخريطةٌ، ومكدَّس |

ولا نتوسّع هنا في الـpaging ولا الـdrivers ولا أنظمة الملفّات: هذه أفرعٌ تُفتَح في
مواضعها، وذكرُها الآن يوسّع الشجرة قبل أن يثبت الجذع.

---

## البنية الداخلية: الصورة ملفُّ ELF

الرابط لا يُنتج «كوداً»؛ يُنتج **segments** لكلٍّ أذونات. وهذا هو سكربت الربط
كلُّه:

<!-- part: kernel/linker.ld -->

```ld
. = 0xffffffff80000000;
  .text : { *(.text .text.*) } :text            /* X R */
  .rodata : { *(.rodata .rodata.*) } :rodata    /*   R */
  .data : { *(.data .data.*) } :data            /* W R */
  .bss  : { *(.bss .bss.*) *(COMMON) } :data
```

**المخرَج**

<!-- out @abi: صورة المرحلة 01؛ والأحجام تتغيّر بتغيّر الكود -->

```
$ llvm-readelf -h out/01/kernel.elf
  Class:                             ELF64
  Type:                              EXEC (Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Entry point address:               0xffffffff80000000

$ llvm-readelf --program-headers out/01/kernel.elf
  Type   Offset   VirtAddr           PhysAddr           FileSiz  MemSiz   Flg Align
  LOAD   0x001000 0xffffffff80000000 0xffffffff80000000 0x0000dd 0x0000dd R E 0x1000
  LOAD   0x002000 0xffffffff80001000 0xffffffff80001000 0x0000e0 0x0000e0 R   0x1000
  LOAD   0x003000 0xffffffff80002000 0xffffffff80002000 0x000000 0x000020 RW  0x1000
```

ثلاثةُ `LOAD` بثلاث أذونات: تنفيذٌ وقراءة، ثم قراءةٌ فقط، ثم كتابةٌ وقراءة. وهذا
هو W^X وقد وُلد في سكربت الربط قبل أن يوجد جدولُ صفحاتٍ يفرضه.

والصفّ الثالث فيه ما يستحقّ النظر: `FileSiz` صفر و`MemSiz` ٠x٢٠. الـ`.bss` لا
بايتَ لها في الملفّ، ومع ذلك تشغل ذاكرةً عند التحميل — فمن الذي يصفّرها؟ جوابُه
في «الفخاخ» أدناه.

### section ليست segment

<!-- out @abi: نفس الصورة، وقد قُرئت أقساماً لا segments -->

```
$ llvm-readelf -S out/01/kernel.elf
  [Nr] Name              Type      Address          Off    Size   Flg
  [ 1] .text             PROGBITS  ffffffff80000000 001000 0000dd  AX
  [ 2] .limine_requests  PROGBITS  ffffffff80001000 002000 0000e0  WA
  [ 3] .bss              NOBITS    ffffffff80002000 003000 000020  WA
```

القسم `.limine_requests` موسومٌ `W` — قابلاً للكتابة. وهو يسكن الـsegment الثاني،
وهو `R` فقط. **القاعدة** أنّ الأذونات تُفرَض بالـsegment لأنه وحدةُ التحميل، والقسم
وصفٌ للرابط. فالـbootloader يكتب فيه جوابَه عبر مطابقته الخاصّة، ثم لا نستطيع نحن
الكتابة فيه — وهو المطلوب.

---

## العقد: طلبٌ في الصورة، وجوابٌ قبل التشغيل

لا نداءَ دوال بين النواة والـbootloader. الواجهة **بنياتٌ نضعها في الصورة**، فيبحث
عنها بمعرّفاتها ويملأ `response`:

<!-- part: kernel/limine.h -->

```c
#define LIMINE_COMMON_MAGIC 0xc7b1dd30df4c8b88, 0x0a82e883a194f07b

struct limine_hhdm_request {
    uint64_t id[4], revision;
    struct limine_hhdm_response *response;   /* يملؤه الـbootloader */
};
#define LIMINE_HHDM_REQUEST_ID \
    { LIMINE_COMMON_MAGIC, 0x48dcf1cb8ad2b852, 0x63984e959a98244b }
```

وهذه الأرقام منقولةٌ من `PROTOCOL.md` ومُعلَنةٌ في ملفّنا. لم نستورد ترويسةً
جاهزة: لو استوردناها لصار العقد صندوقاً أسود، ولا يجوز في هذا المنهج أن يبقى
شيءٌ صندوقاً أسود بلا إعلان.

---

## مسار التنفيذ

```
kernel.elf على القرص
 ↓ الـbootloader يقرأ e_entry وprogram headers
 ↓ يحجز ذاكرةً فيزيائية ويطابقها على العنوان الافتراضيّ المطلوب
 ↓ ينسخ FileSiz بايتاً لكل LOAD، ويصفّر ما زاد إلى MemSiz
 ↓ يبحث عن الطلبات بين الحدَّين ويملأ أجوبتها
 ↓ يبني جداول صفحات: النواة في النصف الأعلى + HHDM + مطابقةٌ مطابِقة
 ↓ يضبط rsp، ويدفع عنوان عودةٍ = 0
 ↓ jmp e_entry
```

### حالةُ المعالج عند الدخول

هذه من المواصفة لا من التجربة — والفصل `03` يقرؤها من السجلّات فتتطابق.

<!-- out @boot: بروتوكول Limine، الإصدار الأساسيّ ٣ — نصّ المواصفة لا تشغيل -->

```
CS = 0x28                      DS = ES = SS = FS = GS = 0x30
GDT: جدولٌ للـbootloader، سبعة واصفات، في ذاكرةٍ قابلةٍ للاستعادة
IDT: غير معرَّف          ← «Executable must load its own»
IF = VM = DF = 0
cr0:  PE ET WP PG          cr4: PAE          EFER: LME LMA NX
rsp:  قمّةُ مكدَّسٍ ≥ 64 KiB، وعنوانُ عودةٍ 0 مدفوعٌ عليه
rax..r15 = 0               PIC: كل الـIRQs مقنَّعة
```

وسطرُ الـIDT هو سبب وجود الحزمة الثالثة كلِّها: لا يوجد معالجُ استثناءٍ بعد.

---

## أصغر implementation

نقطةُ الدخول لا تفعل إلا التحقّق من العقد:

<!-- part: kernel/boot.c -->

```c
#define NEED(cond, code) do { if (!(cond)) { qemu_exit(code); halt_forever(); } } while (0)

void _kstart(void) {
    NEED(LIMINE_BASE_REVISION_SUPPORTED(base_revision), 0x10);
    NEED(hhdm_req.response   != NULL, 0x11);
    NEED(memmap_req.response != NULL, 0x12);
    hhdm_offset = hhdm_req.response->offset;
    memmap      = memmap_req.response;
    stage_main();
    halt_forever();          /* المرحلة إن عادت، لا نعود نحن */
}
```

والتحقّق ليس احتياطاً زائداً: الـbootloader **يجوز** أن يُقلِع نواةً يطلب إصداراً
لا يدعمه، ويُبلِّغ بذلك بترك عنصرٍ في الوسم كما هو. فمن لم يفحص، قرأ صفراً وحسبه
إزاحة.

---

## التجربة: كيف نعرف أننا وصلنا وبلا طرفية؟

بايتٌ واحد إلى منفذٍ يفهمه المحاكي، فيخرج بشفرةٍ نختارها:

<!-- part: demos/s01.c -->

```c
void stage_main(void) {
    qemu_exit(0x2a);
}
```

**المخرَج**

<!-- out @qemu: شفرةُ الخروج = (القيمة << 1) | 1، وهي آليةُ isa-debug-exit -->

```
$ ./build.sh 01 run ; echo "status=$?"
status=85
```

و‎85 = ‎0x55 = ‎(0x2a << 1) | 1. لا طرفية ولا ذاكرةٌ ولا مقاطعات، والادّعاء
المُثبَت واحدٌ فقط: **التنفيذ بلغ دالّتنا.** وهذا كل ما نحتاجه الآن، وهو أيضاً
حدُّه: لا يستطيع أن يقول لنا شيئاً آخر — ولهذا يأتي الفصل التالي.

## كسرها عمداً: العودة إلى العنوان صفر

المواصفة تقول إنّ عنوان العودة المدفوع هو `0`. فلنقفز إليه صريحةً:

<!-- part: demos/s01x.c -->

```c
void stage_main(void) {
    void (*nowhere)(void) = (void (*)(void))0;
    nowhere();                       /* لا IDT بعد: الخطأ لا يجد معالجاً */
}
```

**المخرَج**

<!-- runs: 01x -->
<!-- out @qemu: ‎-d cpu_reset؛ والسجلّات لحظةَ التعيين، لا لحظةَ الخطأ -->

```
$ qemu-system-x86_64 -cdrom out/01x/kernel.iso -no-reboot -d cpu_reset
CPU Reset (CPU 0)
EAX=00000000 EBX=00000000 ECX=00000000 EDX=00060fb1
ESI=00000000 EDI=00000000 EBP=00000000 ESP=00000000
EIP=0000fff0 EFL=00000002 [-------] CPL=0 II=0 A20=1 SMM=0 HLT=0
CS =f000 ffff0000 0000ffff 00009b00
CR0=60000010 CR2=00000000 CR3=00000000 CR4=00000000
EFER=0000000000000000
```

اقرأ الأرقام: `EIP=0xfff0` و`CS=0xf000` — المعالج عند reset vector. و`CR0` بلا
`PG`، و`CR4` صفر، و`EFER` صفر: لا paging ولا نمطٌ طويل. **النتيجة** أنّ الآلة عادت
إلى الحالة التي فتح بها هذا الفصل.

والسلسلة: قفزٌ إلى صفحةٍ غير مطابَقة ⇒ `#PF` ⇒ لا IDT ⇒ `#DF` ⇒ لا معالج ⇒
triple fault ⇒ إعادة تعيين. **وثلاث مرّاتٍ لا واحدة**، وهذا ما يجعل نواةً بلا IDT
تُعيد التشغيل بدل أن تتوقّف.

⚠ و`-no-reboot` هو ما جعل المحاكي يقف هنا بدل أن يدور. ولولاه لرأيت إقلاعاً
متكرّراً، وهو أكثرُ أعراض «النواة لا تعمل» تضليلاً.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الـbootloader يحمّل الأقسام» | يحمّل **segments**. والقسم وصفٌ للرابط، ولا يراه المحمِّل |
| «الـ`.bss` مصفَّرةٌ لأن C تضمن ذلك» | يصفّرها **المحمِّل**: `MemSiz` أكبرُ من `FileSiz`، والفرقُ أصفار. ونواةٌ يحمّلها محمِّلٌ لا يفعل ذلك تبدأ بمتغيّراتٍ عشوائية |
| «نقطة الدخول اسمها `main`» | اسمُها ما في `ENTRY()`، وقيمتُها `e_entry` في الترويسة. و`main` اصطلاحُ libc، ولا libc هنا |
| «النواة محمَّلةٌ على `0x100000`» | العنوان الفيزيائيّ يختاره المحمِّل. وسترى في الفصل التالي أنه ليس رقماً مستديراً |
| «الـbootloader يبني كل شيء فأنا أبني القليل» | يترك الـIDT غير معرَّف، ولا TSS، ولا مخصِّص ذاكرة. **الحدّ** مكتوبٌ في المواصفة ويُقرأ منها |

## Checkpoint

أجب قبل المتابعة:

١. لماذا لا تكفي `e_entry` وحدها ليعمل الكيرنل، وما الذي يجب أن يصحّ في `rsp`
قبل أوّل `call`؟
٢. الـsegment الثالث `MemSiz` أكبر من `FileSiz`. من يملأ الفرق، ومتى؟
٣. لو نسي الـbootloader أن يملأ `hhdm.response`، ما الذي سيحدث في كودنا بلا
`NEED`؟ وفي أي سطرٍ بالضبط؟
٤. المواصفة تقول إنّ `CS = 0x28`. لماذا لا يكفينا ذلك، ونبني جدولاً في الفصل `03`؟

## Artifact

خمسةُ نواتج لهذه الوحدة:

| | |
|---|---|
| مخطّط | `kernel.elf` ← segments ← عناوينٌ افتراضية ← RIP، بأذونات كل segment |
| تنفيذ | المرحلة `01` تُقلِع وتخرج بـ85 |
| تجربةُ فشل | المرحلة `01x` وسجلّاتُ إعادة التعيين |
| أثرُ تنفيذ | مسار التنفيذ أعلاه، وقد تحقّقتَ من كل خطوةٍ فيه من `readelf` أو المواصفة |
| مقارنة | Linux يُحمَّل بـ`vmlinuz`: صورةٌ **تفكّ ضغط نفسها** ثم تقفز إلى النواة الحقيقية. فأي خطوةٍ في مسارنا تختفي، وأيّها يتكرّر مرّتين؟ |

---

## التمرين

غيّر `. = 0xffffffff80000000;` في سكربت الربط إلى `0xffff800000000000`، وأعد
البناء والتشغيل.

هل أقلعت؟ وما الذي تقوله المواصفة عن العنوان المسموح لصورة النواة؟ ثم أعد العنوان
وأزِل `-mcmodel=kernel` من وسائط الترجمة، واقرأ الخطأ من الرابط: أي نوعٍ من
الإزاحات لا يتّسع، ولماذا يخصّ هذا العنوان بالذات؟

**الفصل التالي:** شفرةُ خروجٍ تقول «وصلتُ» ولا تقول شيئاً غيرها. وقبل الذاكرة
والمقاطعات نحتاج مخرَجاً يُعتمَد عليه — وأوّلُ ما سنطبع به هو الأرقام التي سلّمها
الـbootloader في هذا الفصل.
