# الفصل 14 — الحلقة الثالثة

## المشكلة

كلُّ خيوطنا حتى الآن في الحلقة صفر. تقرأ `cr3`، وتنفّذ `hlt`، وترى ذاكرة النواة
كلَّها، وتثق ببعضها. وذلك ليس نظاماً: هو برنامجٌ واحدٌ كبير بخيوط.

والمطلوب أن تشغّل كوداً **لا تثق به**: لا يستطيع أن يمسّ حالتك، ولا أن ينفّذ
تعليمةً تملك بها الآلة، ولا أن يرى ذاكرةً لا تخصّه.

وثلاثةُ أشياء يجب أن تصير موجودةً قبل ذلك: امتيازٌ أدنى، وفضاءُ عنوانٍ خاصّ،
وطريقٌ للعودة.

---

## الآلية الخام: `iretq` في الاتّجاه الآخر

لا تعليمةَ اسمُها «انزل إلى الحلقة ٣». والأداة هي نفسها التي تعود بها من كل
استثناء منذ الفصل `07`.

`iretq` تقرأ خمس كلماتٍ من المكدَّس — `rip` و`cs` و`rflags` و`rsp` و`ss` — وتحمّلها
معاً. فإن كان `cs` المقروء ذا `RPL = 3`، نزل المعالج إلى الحلقة ٣ وبدّل المكدَّس
في نفس الخطوة.

فنبني إطاراً لعودةٍ **لم تقع**:

<!-- part: kernel/user.S -->

```asm
enter_user:                     /* rdi = rip المستخدم   rsi = rsp المستخدم */
    movq $0x1b, %rax            /* SEL_UDATA | RPL 3 = 0x18 | 3 */
    movw %ax, %ds
    pushq $0x1b                 /* ss   */
    pushq %rsi                  /* rsp  */
    pushq $0x202                /* rflags: IF مضبوطة، والبتّ ١ محجوزٌ بواحد */
    pushq $0x23                 /* cs = SEL_UCODE | RPL 3 = 0x20 | 3 */
    pushq %rdi                  /* rip  */
    iretq
```

والمحدِّدان `0x23` و`0x1b` هما `SEL_UCODE` و`SEL_UDATA` من الفصل `03` مضافاً
إليهما `RPL = 3`. فالجدول الذي بنيناه هناك يُستعمَل الآن لأوّل مرّة.

و`rflags = 0x202`: البتّ ٩ هو `IF` — لو تركناه صفراً لعمل برنامج المستخدم بلا
مقاطعات، ولملك الآلة إلى الأبد. والبتّ ١ محجوزٌ بواحدٍ في المعمارية.

## البنية الداخلية: فضاءٌ يُنسَخ نصفُه

<!-- part: kernel/vmm.c -->

```c
uint64_t vmm_new_space(void) {
    uint64_t f = pmm_alloc();
    if (!f) return 0;
    uint64_t *neu = table_at(f), *cur = table_at(root_phys);
    for (int i = 0; i < 256; i++) neu[i] = 0;
    for (int i = 256; i < 512; i++) neu[i] = cur[i];
    return f;
}
```

نصفٌ أدنى فارغ — وهو فضاء المستخدم — ونصفٌ أعلى منسوخٌ من فضاء النواة.

والسؤال الذي يطرحه هذا فوراً: **لماذا تبقى النواة مطابَقةً في فضاء المستخدم
أصلاً؟** ولو لم تكن، لوجب تبديلُ `cr3` عند كل مقاطعةٍ وكل استدعاء — وتبديلُ `cr3`
يُبطِل الـTLB (الفصل `05`)، فيصير كلُّ عبورٍ للحدّ باهظاً.

والحماية ليست بالغياب بل ببتّ `U`: مطابَقةٌ بلا `PTE_U` لا تراها الحلقة ٣ ولو عرفت
عنوانها.

⚠ وهذا الاختيار — الأداءُ مقابل السطح — هو بالضبط ما نقضته ثغراتُ التنفيذ
التخمينيّ، وما يجعل `KPTI` موجوداً. والفصل `25` يعود إليه.

### والأذونات تُجمَع عبر المستويات

مطابقةٌ للمستخدم لا تكفي فيها `PTE_U` على الورقة: كلُّ جدولٍ وسيطٍ في الطريق يجب
أن يحمله كذلك.

```c
    if (u && !(e & PTE_U)) tbl[idx] = e | PTE_U; /* فرعٌ صار مشتركاً مع المستخدم */
```

ونضعه حين تطلبه المطابقة وحدها. فتبقى فروعُ النواة بلا `U`، ويبقى التقييد الحقيقيّ
في الورقة.

## مسار التنفيذ

```
بناءُ فضاءٍ جديد (نصفٌ أعلى منسوخ)
 ↓ مطابقةُ صفحة كودٍ بـPTE_U، ومكدَّسٍ بـPTE_U|W|NX
 ↓ tss.rsp0 ← مكدَّسُ الحلقة صفر   ← وإلّا فلا طريق للعودة
 ↓ cr3 ← الجذر الجديد
 ↓ بناءُ إطار iretq بمحدِّدات RPL 3
 ↓ iretq  →  CPL = 3
```

والخطوة الثالثة شرطٌ لما بعدها: عند أوّل مقاطعةٍ أو استثناءٍ بعد
النزول، سيقرأ المعالج `rsp0` من الـTSS ليجد مكدَّساً موثوقاً. ولو كان صفراً لدفع
حالة الاستثناء على العنوان صفر.

## التجربة

<!-- runs: 14 -->

```c
vmm_map_in(user_root, USER_CODE, code, PTE_U);   /* تنفيذٌ وقراءة، بلا كتابة */
vmm_switch(user_root);
enter_user(USER_CODE, USER_STACK_TOP);
```

وبرنامج المستخدم ثلاث تعليمات: قفزةٌ لا تفعل شيئاً، ثم `swapgs` — وهي ممتنعة.

**المخرَج**

<!-- out @arch: الرفض من المعمارية؛ والعناوين الفيزيائية تتغيّر بين تشغيلين -->

```
[INFO] tss.rsp0 = 0xffffffffc0005018
[INFO] new address space root = 0x000000000007d000  (kernel half copied)
[INFO] user code at 0x0000000000400000 -> frame 0x000000000007e000
[INFO] checking the kernel is NOT visible: pte for our own text
[INFO]   kernel text pte = ff32021  U-bit=0
[INFO] cr3 switched. entering ring 3 now.
[INFO] #GP from CPL=3 at rip=0x0000000000400002 error=0
[INFO] the instruction was privileged. ring 3 may not execute it.
[INFO] cs=23 ss=1b rflags=10202
```

أربعةُ أرقامٍ تُقرأ معاً:

`rip = 0x400002` — التعليمة الأولى نُفِّذت. فقد عمل كودُ المستخدم فعلاً، والقفزة
الفارغة تقدّمت ببايتين.

`cs = 0x23` و`CPL = 3` — البتّان الأدنيان من `cs` هما الامتياز، و`0x23 & 3 = 3`.
فنحن في الحلقة الثالثة، وهذا هو الدليل لا الادّعاء.

`kernel text pte` بـ`U-bit = 0` — صفحةُ كود النواة **مطابَقةٌ** في هذا الفضاء
وغيرُ مرئيةٍ للمستخدم. وهذا هو الفرق بين «غير موجود» و«ممنوع».

و`#GP` بـ`error = 0` — الرفض جاء من المعمارية لا من كودنا. لم نكتب فحصاً، ولم
نقرأ قائمة تعليماتٍ ممنوعة: المعالج نفسه رفض.

**المكسب** أنّ البديهية ٣ صارت مقيسة. وهذا هو الجواب على السؤال الذي فتح الفصل
`03`: لماذا لا يستطيع برنامجٌ عاديّ أن يكتب في `cr3`.

⚠ ولاحظ ما لم نفعله: لم نمنع شيئاً. بنينا جدولاً بـ`DPL` صحيحة في الفصل `03`،
وضبطنا `RPL` في المحدِّد هنا — والمنعُ نتيجةٌ تلقائية.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الحلقة ٣ تعني ذاكرةً منفصلة» | الامتياز شيءٌ والفضاء شيء. والعزل يأتي من `PTE_U` وجدولٍ خاصّ، لا من `CPL` وحده |
| «النواة غير موجودةٍ في فضاء المستخدم» | موجودةٌ ومطابَقة. وما يمنع رؤيتَها بتُّ `U` — واللوحة تُظهره صفراً |
| «أنزل بـ`jmp` إلى كودٍ ذي `DPL=3`» | تبديلُ الامتياز يحتاج تعليمةً تنقل التنفيذ **وتحمّل `cs` معاً**: `iretq` أو `sysret` |
| «`PTE_U` على الصفحة تكفي» | كلُّ وسيطٍ في الطريق يحتاجها. وهذا بالضبط ما جعل أوّل تشغيلٍ لنا يفشل بـ`#PF` |
| «نسيتُ `rsp0` فسأرى خطأً واضحاً» | ترى استثناءً يُدفَع على مكدَّسٍ غير صالح، فيصير `#DF` ثم إعادة تعيين |

## Checkpoint

١. `cs = 0x23`. اشتقّ الرقم من `SEL_UCODE` ومن `RPL`، وقل ماذا يقع لو كانت
`RPL = 0` والواصفُ `DPL = 3`.
٢. لماذا نبني إطار `iretq` بأيدينا بدل استعمال `sysret`؟ وأي شيءٍ يملكه `iretq`
ولا يملكه `sysret`؟
٣. صفحةُ كود المستخدم مُطابَقةٌ بـ`PTE_U` بلا `PTE_W`. ماذا يقع لو كتب فيها
المستخدم، وأي شفرةِ خطأٍ سترى؟
٤. اكتب ما الذي يجب أن يتغيّر في `schedule` قبل أن يعمل خيطان في فضاءين مختلفين.

## التمرين

أزِل `PTE_U` عن صفحة الكود وأعد التشغيل. أي استثناءٍ وقع، وما شفرةُ خطئه؟ فكّ
بتاتها الثلاثة وقارنها بجدول الفصل `07`.

ثم اجعل `tss_set_rsp0(0)` وأعد التشغيل مع `-d cpu_reset`. كم استثناءً وقع قبل
إعادة التعيين، ولماذا لا ترى تقرير `panic` الذي بنيتَه في الفصل `07`؟

ثم اجعل برنامج المستخدم يقفز إلى عنوان دالّةٍ في نواتك — تجدها بـ`llvm-nm`.
ما الذي يقع، وأي بتٍّ في أي مدخلٍ منعه؟

**الفصل التالي:** كودٌ لا يملك شيئاً لا يستطيع أن يفعل شيئاً — لا يطبع ولا يقرأ.
فكيف يطلب خدمةً من النواة، وقد مُنع من القفز إليها؟
