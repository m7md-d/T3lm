# الفصل 07 — الاستثناءات: من العتاد إلى دالّة C

## المشكلة

الفصل `05` ترك سؤالاً معلّقاً. لمسنا صفحةً بلا مطابقة، فأُعيد تعيينُ الآلة، و`CR2`
— السجلُّ الذي يحمل العنوان الفاصل — قُرئ صفراً بعد التعيين.

والسبب سطرٌ في مواصفة الإقلاع قرأناه في الفصل `01`: **الـIDT غير معرَّف، وعلى
الكيرنل أن يحمّل جدولَه**. فما دام لا جدول، فلا معالج، ولا سبيل إلى معرفة ما جرى.

وهذا الفصل يبني البوّابة — وهي البديهية ٣ بعينها: العبور إلى كود الكيرنل لا يقع
إلا عبر مدخلٍ يعرّفه الكيرنل.

---

## الآلية الخام: ما يفعله المعالج وحده

عند الاستثناء يفعل المعالج هذا **قبل** أن ينفّذ سطراً من كودك:

| # | الخطوة |
|---|---|
| ١ | يقرأ المدخل رقم `vector` من الـIDT عبر `IDTR` |
| ٢ | يقارن `DPL` المدخل بـ`CPL` الجاري، ويرفع `#GP` إن لم يجز |
| ٣ | إن كان الانتقال من حلقةٍ أعلى، يبدّل المكدَّس إلى `rsp0` من الـTSS — الفصل `03` |
| ٤ | يدفع `ss` و`rsp` و`rflags` و`cs` و`rip`، وشفرةَ خطأٍ لبعض المتّجهات |
| ٥ | لبوّابة المقاطعة: يصفّر `IF` — فلا تُقاطَع وأنت تعالج |
| ٦ | يحمّل `cs:rip` من المدخل |

والخطوة الرابعة هي سبب كل تعقيدٍ في هذا الفصل: **الدفعُ ليس متماثلاً.** عشرةُ
متّجهاتٍ تدفع شفرة خطأ، والباقي لا يدفع — فتخطيطُ المكدَّس يختلف بحسب المتّجه.

## البنية الداخلية: مدخلٌ من ستّة عشر بايتاً

<!-- part: kernel/idt.c -->

```c
struct __attribute__((packed)) idt_entry {
    uint16_t off_lo;
    uint16_t selector;      /* محدِّدُ الكود الذي يُنفَّذ فيه المعالج */
    uint8_t  ist;           /* 0 = استعمل المكدَّس الحاليّ أو rsp0 */
    uint8_t  type_attr;     /* P | DPL | نوعُ البوّابة */
    uint16_t off_mid;
    uint32_t off_hi;
    uint32_t zero;
};
```

والعنوان مقطوعٌ ثلاث قطع في مواضع متباعدة — ندبةُ توافقٍ خلفيّ: المدخل كان ثمانية
بايتاتٍ في ٣٢ بت، فأُضيف الباقي حوله.

| الحقل | ما يقرّره |
|---|---|
| `selector` | الكود الذي يُنفَّذ فيه المعالج — `SEL_KCODE` من الفصل `03` |
| `type_attr = 0x8E` | بوّابةُ **مقاطعة**: تصفّر `IF` عند الدخول |
| `type_attr = 0x8F` | بوّابةُ **مصيدة**: تترك `IF` كما هو |
| `DPL` في `type_attr` | من يجوز له استدعاء المتّجه بـ`int n`. والصفر يمنع userspace |
| `ist` | فهرسُ مكدَّسٍ بديلٍ في الـTSS — يُستعمَل حين لا يُوثَق بالمكدَّس الجاري |

و`DPL = 0` لكل مداخلنا قرارٌ له أثر: برنامجٌ في الحلقة ٣ ينفّذ `int $14` لا يدخل
معالجَ الـpage fault — بل يأخذ `#GP`. ولو كان `DPL = 3` لاستطاع أي برنامجٍ أن
يزوّر أي استثناء.

## أصغر implementation: مئتان وستّة وخمسون مقطعاً بلا مئتين وستّة وخمسين تسمية

المعالج يقفز إلى عنوانٍ ثابت، ولا يمرّر رقم المتّجه. فلكل متّجهٍ مقطعُ دخولٍ خاصّ
يعرف رقمه. والمقاطع متطابقة إلا في رقمين، فنولّدها:

<!-- part: kernel/isr.S -->

```asm
isr_stubs:
vec = 0
.rept 256
    .align 16
    .if (vec==8)||(vec==10)||(vec==11)||(vec==12)||(vec==13)||(vec==14)||(vec==17)||(vec==21)||(vec==29)||(vec==30)
        nop
        nop
    .else
        pushq $0
    .endif
    pushq $vec
    jmp isr_common
vec = vec + 1
.endr
```

وفكرتان في هذه الأسطر:

**توحيدُ التخطيط.** المتّجهات التي لا يدفع لها المعالج شفرةَ خطأ ندفع لها صفراً
بأيدينا. فيصير مكدَّسُ كل المتّجهات واحداً، ويصير معالجُ C واحداً. ولو تركناها
مختلفة لاحتاج كلُّ متّجهٍ دالّةً بتخطيطٍ مختلف.

و`nop nop` في الفرع الآخر ليستا حشواً: هما بايتان بطول `pushq $0` بالضبط، فيبقى
كلُّ مقطعٍ في مكانه من الشبكة.

**الشبكةُ بدل التسمية.** كلُّ مقطعٍ محاذًى إلى ١٦ بايتاً، فعنوان المتّجه `n` هو
`isr_stubs + 16n` حساباً:

```c
for (int v = 0; v < 256; v++)
    set_gate(v, (uint64_t)isr_stubs + 16ull * (unsigned)v, GATE_INT);
```

### ونقطةُ الالتقاء

<!-- part: kernel/isr.S -->

```asm
isr_common:
    pushq %rax
    pushq %rbx
    movq %rsp, %rdi          /* الوسيط الأوّل في System V: مؤشّرٌ إلى struct regs */
    cld                      /* الـABI يشترط DF = 0 عند دخول دالّة C */
    call isr_dispatch
    addq $16, %rsp           /* المتّجه وشفرة الخطأ: دفعناهما فنزيلهما */
    iretq                    /* وهي التي تعيد rip وcs وrflags وrsp وss معاً */
```

**القاعدة** التي تحكم هذا المقطع: نحن لسنا دالّةً نودي، بل تنفيذٌ قُوطع. فلا يكفي
حفظُ ما يحفظه المنادى في الـABI — كلُّ سجلٍّ يخصّ الكود المقطوع ويجب أن يعود كما
كان. ولهذا تُدفَع الخمسةَ عشرَ كلُّها.

و`movq %rsp, %rdi` هي الجسر: ما دفعناه بالترتيب المعكوس صار **بنيةً** في C،
لأن المكدَّس ينمو نزولاً فأوّلُ ما دُفع أعلى العنوان:

<!-- part: kernel/idt.h -->

```c
struct regs {
    uint64_t r15, r14, r13, r12, r11, r10, r9, r8;
    uint64_t rbp, rdi, rsi, rdx, rcx, rbx, rax;
    uint64_t vector, error;          /* نحن */
    uint64_t rip, cs, rflags, rsp, ss;   /* المعالج */
};
```

وهذه بنيةٌ **قابلةٌ للكتابة**: تعديلُ `r->rip` يغيّر إلى أين يعود `iretq`. وهو ما
يجعل المعالجة ممكنةً أصلاً، وما يجعل تبديل السياق ممكناً في الفصل `11`.

## التجربة: ثلاثةُ استثناءاتٍ متعمَّدة

<!-- runs: 07 -->

```c
idt_set_handler(0,  on_de);
idt_set_handler(6,  on_ud);
idt_set_handler(14, on_pf);
__asm__ volatile("idivl %2" : "+a"(q) : "d"(0), "r"(z) : "cc");
__asm__ volatile("ud2");
*(volatile uint64_t *)SCRATCH = 0xcafebabe;
```

**المخرَج**

<!-- out @arch: العناوين تتغيّر بتغيّر البناء؛ وشفرةُ الخطأ وأسماءُ المتّجهات ثابتة -->

```
[INFO] IDT loaded: 256 gates, stub n at isr_stubs + 16n
[INFO] --- deliberate #DE ---
[INFO] caught #DE divide error at rip=0xffffffff800030d1
[INFO] survived #DE, de_seen=1
[INFO] --- deliberate #UD ---
[INFO] caught #UD invalid opcode at rip=0xffffffff80003106
[INFO] survived #UD, ud_seen=1
[INFO] --- deliberate #PF, then repair and resume ---
[INFO] #PF at cr2=0xffffff0000000000 rip=0xffffffff80003147 error=2  [not-present write supervisor]
[INFO] mapped it and returning: the faulting instruction runs again
[INFO] wrote cafebabe through the repaired mapping, pf_seen=1
```

السطر قبل الأخير هو جواب الفصل `05`. `CR2 = 0xffffff0000000000` — العنوان الذي
لمسناه بالضبط. و`error = 2` يُفكّ ثلاثة بتات:

| البتّ | ٠ | ١ |
|---|---|---|
| ٠ | الصفحة **غير حاضرة** | الأذونات منعت |
| ١ | قراءة | **كتابة** |
| ٢ | supervisor | user |

فـ`2` تعني: غير حاضرة · كتابة · من الحلقة ٠. وهذا وصفٌ كاملٌ لما فعلناه.

### والمعالجة تُصلِح وتعود

```c
static void on_pf(struct regs *r) {
    uint64_t cr2 = read_cr2();
    vmm_map(cr2 & ~0xfffull, pmm_alloc(), PTE_W | PTE_NX);
}
```

بنينا المطابقة الناقصة وعُدنا بلا تعديل `rip`. فأعاد المعالج **نفس التعليمة**،
ونجحت هذه المرّة.

**النتيجة** أنّ `#PF` ليس دائماً خطأً. هو **آلية**: الصفحة غائبة، فيخبرك المعالج،
فتقرّر. وعلى هذا يقوم demand paging وcopy-on-write والـmmap الذي رأيتَه من الطرف
المستهلِك في `c-advanced` — ونحن لا نبنيها، والسبب مكتوبٌ في جدول «ما رُفض» في
الفصل `00`.

⚠ و`r->rip += 2` في معالجَي `#DE` و`#UD` **ليست معالجة**: هي تخطٍّ لتعليمةٍ بطولٍ
عرفناه بالنظر، وصلحت للعرض وحده. ولا تفعل نواةٌ حقيقيةٌ ذلك: `#DE` من الحلقة ٣
تُنهي العملية بإشارة، ومن الحلقة ٠ تُوقِف النظام.

## كسرها عمداً: استثناءٌ بلا معالج

<!-- out @ours: صيغةُ التقرير قرارُنا، والسجلّات من `struct regs` -->

```
[INFO] --- and one we do not handle ---

[PANIC] unhandled exception
       vec=3 (#BP breakpoint)  error=0
       rip=0xffffffff8000317e  cs=8  rflags=86
       rsp=0xffff80000ff91fd0  ss=10
       rax=a rbx=0 rcx=10 rdx=3f8
```

قارن هذا بنهاية الفصل `05`: هناك أُعيد تعيينُ الآلة وضاع كلُّ شيء، وهنا تقريرٌ
بالمتّجه والعنوان والسجلّات. **المكسب** أنّ الفشل صار مقروءاً — وهو أوّلُ شرطٍ
لتشخيص أي شيءٍ بعد هذا الفصل.

و`cs=8` يقول إنّ الخطأ وقع في `SEL_KCODE`، أي في الحلقة صفر. وسيصير هذا الحقل
الحقلَ الذي يُقرأ أوّلاً في التقرير حين توجد حلقةٌ ثالثة في الفصل `14`.

## كيف تفعلها الأنظمة الحقيقية

Linux يفرّق بين ما لا نفرّق فيه بعد: `#PF` من userspace على عنوانٍ داخل منطقةٍ
مُعلَنة ⇒ يحجز صفحة؛ وعلى عنوانٍ خارجها ⇒ `SIGSEGV`؛ ومن الحلقة ٠ على عنوان
userspace ⇒ يبحث في **جدول استثناءات** يربط عنوان التعليمة بعنوان تعافٍ — وهي
الآلية التي تجعل `copy_from_user` آمنةً، والفصل `15` يعود إليها.

وعنده كذلك `IST` لـ`#DF` و`NMI`: مكدَّسٌ مستقلٌّ لا يعتمد على سلامة الجاري. ونحن
نترك `ist = 0` لكل المداخل، وذلك حدٌّ مُعلَن — والفصل `25` يبيّن متى يسقط هذا
الاختيار.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «المعالج ينادي دالّتي» | يقفز إلى عنوان. ولا مكدَّسَ دالّةٍ ولا وسائط: أنت تبنيها في المقطع |
| «كلُّ المتّجهات متماثلة» | عشرةٌ منها تدفع شفرة خطأ. والتوحيد قرارُك، لا حالٌ تجدها |
| «حفظُ السجلّات المنادى ستّةٌ كما يقول الـABI» | الـABI عقدٌ بين دالّتين. والمقاطعة ليست نداءً — فكلُّ السجلّات تُحفَظ |
| «`#PF` خطأٌ يعني برنامجاً معطوباً» | آليةُ إبلاغ. واللوحة أصلحت وعادت |
| «`iretq` مثل `ret`» | تعيد خمس كلماتٍ معاً — ومنها `rflags` و`cs`. وبها وحدها يُنزَل إلى الحلقة ٣ في `14` |
| «`DPL` في المدخل يخصّ الأمان فقط» | يقرّر من يستطيع `int n`. و`DPL=3` يجعل أي برنامجٍ يزوّر أي استثناء |

## Checkpoint

١. لماذا يجب أن يكون طول `nop nop` مساوياً لطول `pushq $0` بالضبط؟ وما الذي يكسر
لو كان أطول ببايت؟
٢. `error = 2` في اللوحة. اكتب قيمة `error` لبرنامجٍ في الحلقة ٣ يقرأ صفحةً حاضرةً
بلا `PTE_U`.
٣. `isr_common` تنادي `cld` قبل `call`. ما الذي يضمنه الـABI هنا، وماذا يفسد لو
كانت `DF = 1`؟
٤. معالجُنا يعدّل `r->rip`. صِف بالضبط كيف يصل هذا التعديل إلى المعالج، وأي
تعليمةٍ تنفّذه.

## Artifact

| | |
|---|---|
| مخطّط | استثناء ← IDT[vec] ← مقطع ← `struct regs` على المكدَّس ← C ← `iretq` |
| تنفيذ | `idt_init` و`isr_stubs` و`isr_dispatch` |
| تجربةُ فشل | `int $3` بلا معالج ⇒ تقريرٌ بالسجلّات بدل إعادة تعيين |
| أثرُ تنفيذ | `#PF` ← `CR2` ← فكُّ شفرة الخطأ ← `vmm_map` ← إعادةُ التعليمة |
| مقارنة | جدولُ استثناءات Linux، و`IST` — وما الذي يمنعه كلٌّ منهما |

## التمرين

اجعل معالج `#PF` يطبع `error` ثم **لا** يُصلِح شيئاً ويعود. شغّل، واقرأ المخرَج.

كم مرّةً طُبع السطر، ولماذا؟ وما الفرق البنيويّ بين هذا وبين حلقةٍ في كودك؟

ثم اضبط `DPL = 3` للمتّجه `14` وحده، واستدعِ `int $14` من الحلقة صفر. هل تغيّر
شيء؟ ولماذا لن تعرف الفرق حتى الفصل `14`؟

**الفصل التالي:** بنيتَ بوّابةً لاستثناءاتٍ يولّدها كودُك. والعالم خارجُك يريد أن
يقاطعك أيضاً — فمن يقرّر أيُّ متّجهٍ يصل إلى المعالج حين يضغط أحدٌ مفتاحاً؟
