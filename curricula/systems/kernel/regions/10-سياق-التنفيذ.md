# الفصل 10 — ما هو execution context

## المشكلة

المؤقّت يقطع التنفيذ مئة مرّةٍ في الثانية. والقطع بلا وجهةٍ لا ينفع: لا بدّ من
تنفيذٍ آخر تنتقل إليه، وتنفيذٍ أوّلَ تستطيع العودة إليه.

فالسؤال الذي يفتح هذه الحزمة: **ما أقلُّ ما إذا حفظتَه أمكن إيقافُ تنفيذٍ ثم
استئنافُه من حيث وقف بالضبط؟**

وهذا سؤالٌ يُجاب بالعدّ لا بالوصف.

---

## الآلية الخام: ما الذي يصف «تنفيذاً» في المعالج

| ما يصفه | السجلّات |
|---|---|
| أين ينفّذ | `rip` |
| أين مكدَّسه | `rsp` · `rbp` |
| ما بيده من قيم | `rax`..`r15` |
| شروطُه | `rflags` |
| أي ذاكرةٍ يرى | `cr3` |
| بأي امتيازٍ | `cs` · `ss` |
| حالةُ الفاصلة العائمة | `xmm0`..`xmm15` · حالةُ x87 |

هذه القائمة تبدو طويلة. والخدعة أنّ أكثرها **لا يحتاج حفظاً في بنية**: يكفي أن
يبقى على المكدَّس. فإن حفظتَ `rsp` وحده، وكان الباقي مدفوعاً على ذلك المكدَّس، فقد
حفظتَ الكلّ.

وهذه هي البديهية ٢ مجرّدةً: تجريدُ «الخيط» تحته آليةٌ خام اسمُها **رقمٌ
واحد**.

⚠ وثلاثةٌ من الجدول لا نحفظها ونحن مصيبون اليوم، والسبب مُعلَن: `cr3` واحدٌ لكل
النواة حتى الفصل `14`، و`cs`/`ss` ثابتان ما دمنا في الحلقة صفر، وحالةُ الفاصلة
العائمة **لا نستعملها** — بنينا بـ`-mno-sse -mno-80387`. ولو استعملناها لوجب حفظُها
بـ`fxsave`، وهي أغلى ما يُحفَظ.

## البنية الداخلية: كلُّ حقلٍ يبرّر وجوده

<!-- part: kernel/thread.h -->

```c
struct thread {
    uint64_t     rsp;        /* قمّةُ المكدَّس المحفوظ — وهي كلُّ حالة التنفيذ */
    uint64_t     stack_base; /* لتحريره، ولحساب حدّه */
    enum tstate  state;
    int          id;
    const char  *name;
    uint64_t     slices;     /* كم مرّةً جُدوِل — للقياس لا للسياسة */
};
```

ستّةُ حقول، وواحدٌ منها فقط يخصّ **التنفيذ**. والباقي إدارة: `stack_base` للتحرير،
و`state` لمن يجوز اختياره، و`id` و`name` للتشخيص، و`slices` للقياس.

**القاعدة** التي يُفحَص بها كل حقلٍ تُضيفه لاحقاً: هل يمنع غيابُه الاستئناف
الصحيح، أم يمنع إدارةً نريدها؟ الأوّل إلزام، والثاني اختيار.

### ولكلّ خيطٍ مكدَّسٌ خاصّ

لأن المكدَّس **هو** الحالة المحفوظة. ولو تشارك خيطان مكدَّساً لكتب كلٌّ منهما فوق
إطارات الآخر عند أوّل تبديل.

```c
#define KSTACK_PAGES 4                      /* ١٦ كيلوبايت لكل خيط */
```

وحجمُه قرارٌ بثمن: صغيرٌ جداً يفيض — ومعالجُ المقاطعة يدفع عليه أيضاً — وكبيرٌ
جداً يستهلك ذاكرةً بعدد الخيوط. والفصل `25` يضيف صفحةَ حراسةٍ تجعل الفيض `#PF`
بدل فسادٍ صامت.

---

## أصغر implementation: مكدَّسٌ يُبنى كأنه بُدِّل خارجاً

الخيط الجديد لم يعمل قطّ، فلا حالة محفوظة له. فنبنيها بأيدينا — ونبنيها بالشكل
الذي **يتوقّعه** `context_switch` عند الاستئناف:

<!-- part: kernel/thread.c -->

```c
    uint64_t *sp = (uint64_t *)(base + KSTACK_PAGES * PAGE_SIZE);
    *--sp = (uint64_t)thread_exit;       /* لو عادت، لا تسقط في فراغ */
    *--sp = (uint64_t)thread_trampoline; /* ما تقرؤه `ret` في context_switch */
    *--sp = 0;                           /* rbp */
    *--sp = 0;                           /* rbx */
    *--sp = 0;                           /* r12 */
    *--sp = 0;                           /* r13 */
    *--sp = 0;                           /* r14 */
    *--sp = (uint64_t)entry;             /* r15 — المقطعُ ينادي ما فيه */
```

وهذا **تزوير مقصود**: نصنع أثراً لتنفيذٍ لم يقع، لأن التبديل لا يعرف الفرق بين
خيطٍ توقّف وخيطٍ لم يبدأ. وهو ما يجعل إنشاء الخيط وتبديله عمليةً واحدة.

## التجربة: اقرأ الحالة المبنيّة

<!-- runs: 10 -->

```c
struct thread *t = thread_create("worker", never_runs);
uint64_t *sp = (uint64_t *)t->rsp;
```

**المخرَج**

```
[INFO] the running code is now thread 0 (boot), rsp saved = 0x0000000000000000
[INFO] created thread 1 (worker)
[INFO]   stack base = 0xffffffffc0001018   size = 16384 bytes
[INFO]   saved rsp  = 0xffffffffc0004fd8   (64 bytes below the top)

       [rsp+ 8] = 0x0000000000000000   r14
       [rsp+16] = 0x0000000000000000   r13
       [rsp+24] = 0x0000000000000000   r12
       [rsp+32] = 0x0000000000000000   rbx
       [rsp+40] = 0x0000000000000000   rbp
       [rsp+48] = 0xffffffff8000369f   <- what `ret` jumps to (thread_trampoline)
       [rsp+56] = 0xffffffff80003630   <- where the entry returns to (thread_exit)
```

أربعةٌ وستّون بايتاً تحت القمّة، وهي كلُّ ما يلزم ليصير هذا الخيط قابلاً للتشغيل.
والصفر في `rsp saved` للخيط `boot` صحيح: التنفيذ الجاري لم يُحفَظ بعد، ولن يُحفَظ
إلا حين يُبدَّل خارجاً.

و`stack_base = 0xffffffffc0001018` عنوانٌ من الكومة — بترويسة `kmalloc` البالغة ٢٤
بايتاً من الفصل `06`، ولذلك لا ينتهي بأصفار.

**المكسب** أنّ «الخيط» توقّف عن كونه مفهوماً: هو ستّةُ حقول، وأثمنُها رقمٌ واحد،
وحالةٌ من ثمانِ كلماتٍ مبنيّةٍ بيدك.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الخيط يحفظ كل السجلّات في بنيته» | يحفظ `rsp`. والباقي **على** المكدَّس الذي يشير إليه |
| «الخيط الجديد حالتُه فارغة» | حالتُه مبنيّةٌ بدقّة، وبالشكل الذي يتوقّعه التبديل. والفراغُ يعني قفزاً إلى عنوانٍ عشوائيّ |
| «مكدَّسٌ واحدٌ يكفي ما دام واحدٌ يعمل» | المكدَّس هو الحالة المحفوظة. ومشاركتُه تعني أن يكتب كلٌّ فوق الآخر |
| «حفظُ السياق نسخُ سجلّات» | في التعاونيّ: ستّةُ سجلّاتٍ يفرضها الـABI. وفي المقاطعة: خمسةَ عشرَ. والفرق يأتي في الفصل التالي |
| «`slices` جزءٌ من الحالة» | قياسٌ نضيفه. واحذفه فلا يتغيّر شيءٌ في صحّة الاستئناف |

## Checkpoint

١. `rsp saved = 0` للخيط `boot`. متى تُملأ هذه القيمة بالضبط، وبأي تعليمة؟
٢. لماذا وُضعت نقطة الدخول في خانة `r15` لا في خانةٍ أخرى من الستّ؟
٣. لو حذفنا `stack_base` من البنية، ما الذي يتعطّل — وهل يتعطّل الاستئناف؟
٤. اكتب ما يجب أن يُضاف إلى `struct thread` قبل أن نستطيع تشغيل خيطين في فضاءَي
عنوانٍ مختلفين، وسمِّ الفصل الذي يضيفه.

## Artifact

| | |
|---|---|
| مخطّط | `struct thread` وسهمٌ من `rsp` إلى المكدَّس، وعليه الثماني كلمات مسمّاة |
| تنفيذ | `thread_create` و`thread_bootstrap` |
| تجربةُ فشل | اجعل `KSTACK_PAGES = 0` واقرأ ما يقع — تمرين هذا الفصل |
| أثرُ تنفيذ | `kmalloc` ← قاعدة ← قمّة ← ثماني دفعات ← `rsp` محفوظ |
| مقارنة | `task_struct` في Linux فيه مئاتُ الحقول. أيُّها يخصّ الاستئناف وأيُّها إدارة؟ |

## التمرين

اجعل `KSTACK_PAGES = 1` ثم أنشئ خيطاً يستدعي دالّةً تُعرِّف مصفوفةً محلّيةً من ٨
كيلوبايت، وشغّل المرحلة `11`.

ما الذي يُكتَب فوقه؟ ولماذا لا يظهر الخطأ عند الكتابة بل بعدها بحين؟ وأي فصلٍ
يعطيك أداةً تجعل هذا الفيض يُكتشَف لحظةَ وقوعه؟

ثم اطبع الفرق بين `stack_base` وأدنى `rsp` بلغه الخيط فعلاً أثناء عمله. كم
استُعمل من الستّةَ عشرَ كيلوبايت؟

**الفصل التالي:** عندك حالتان محفوظتان. وبينهما تعليماتٌ معدودة تنقل التنفيذ من
إحداهما إلى الأخرى — وهي أقصرُ دالّةٍ في هذا المنهج وأكثرُها أثراً.
