# الفصل 15 — الاستدعاءات

## المشكلة

الحلقة ٣ لا تستطيع القفز إلى كود النواة — أثبت الفصل السابق ذلك. فكيف تطلب خدمة؟

والبديهية ٣ تعطي شكل الجواب: بوّابةٌ يعرّفها الكيرنل بنفسه. وتبقى أسئلةُ التنفيذ:
أي تعليمة، وأين تهبط، وبأي مكدَّس — فالمعالج **لا يبدّل المكدَّس** في هذا الطريق،
بخلاف المقاطعة.

---

## الآلية الخام: `syscall` و`sysret`

`syscall` تعليمةٌ مخصّصة لهذا. ما تفعله قليلٌ ومحدَّد:

| ما تفعله `syscall` | من أين |
|---|---|
| `rcx ← rip` التالي | حفظُ العودة — وتُتلِف `rcx` |
| `r11 ← rflags` | حفظُ الرايات — وتُتلِف `r11` |
| `rflags &= ~FMASK` | فتُطفأ `IF` إن كان بتُّها في القناع |
| `cs ← STAR[47:32]`، `ss ← +8` | بلا قراءة GDT: القيم من سجلٍّ |
| `rip ← LSTAR` | نقطةُ الدخول التي كتبناها |

وما **لا** تفعله يقرّر شكل المقطع كلَّه: **لا تبدّل `rsp`.** فعند أوّل تعليمةٍ في نواتك تكون
على مكدَّسٍ يملكه المستخدم، وقد اختار عنوانه بنفسه.

| | مقاطعة | `syscall` |
|---|---|---|
| مصدرها | خارجيّ أو استثناء | تعليمةٌ ينفّذها المستخدم |
| المكدَّس | يبدّله المعالج من `rsp0` | **لا يتغيّر** |
| الحالة المحفوظة | خمسُ كلماتٍ على المكدَّس | `rcx` و`r11` وحدهما |
| العودة | `iretq` | `sysretq` |
| الكلفة | أعلى | أدنى — ولهذا وُجدت |

## البنية الداخلية: أربعةُ MSRs

<!-- part: kernel/syscall.c -->

```c
void syscall_init(uint64_t kstack_top) {
    syscall_kstack = kstack_top;
    wrmsr(MSR_STAR,  ((uint64_t)0x10 << 48) | ((uint64_t)0x08 << 32));
    wrmsr(MSR_LSTAR, (uint64_t)syscall_entry);
    wrmsr(MSR_FMASK, 0x700);                 /* IF وDF وAC تُطفأ عند الدخول */
    wrmsr(MSR_EFER,  rdmsr(MSR_EFER) | 1);   /* SCE: بلا هذا البتّ فـ`syscall` = #UD */
}
```

و`STAR` هو سبب ترتيب الـGDT في الفصل `03`. المعالج **يحسب** المحدِّدات ولا يقرؤها:

| | يُحسَب من | فيصير عندنا |
|---|---|---|
| `syscall` → `cs` | `STAR[47:32]` = `0x08` | `SEL_KCODE` |
| `syscall` → `ss` | `+ 8` = `0x10` | `SEL_KDATA` |
| `sysret` → `cs` | `STAR[63:48] + 16` = `0x20` | `SEL_UCODE` |
| `sysret` → `ss` | `STAR[63:48] + 8` = `0x18` | `SEL_UDATA` |

فلو رتّبنا الجدول غير هذا الترتيب، لعاد المستخدم بمحدِّدٍ خاطئ — وقد ثُبِّت
الترتيب قبل اثني عشر فصلاً لهذا السبب.

و`FMASK = 0x700` يطفئ `IF` عند الدخول. ولولاه لوصلت مقاطعةٌ ونحن على مكدَّس
المستخدم، فدُفعت حالتُها هناك.

## أصغر implementation: الجسر بين عقدين

<!-- part: kernel/syscall.S -->

```asm
syscall_entry:
    movq %rsp, syscall_user_rsp(%rip)   /* مكدَّسُ المستخدم: نحفظه ولا نثق به */
    movq syscall_kstack(%rip), %rsp     /* مكدَّسٌ نملكه — معالجٌ واحد، والفصل 22 يعمّمه */

    pushq %rcx                  /* عنوانُ العودة — تعيده `sysretq` */
    pushq %r11                  /* rflags — تعيدها `sysretq` */
    pushq %rdi                  /* وما تحت: يفرضه عقدُ الاستدعاء لا عقدُ C */
    pushq %rsi
    pushq %rdx
    pushq %r10
    pushq %r8
    pushq %r9

    movq %rdx, %rcx             /* a3 */
    movq %rsi, %rdx             /* a2 */
    movq %rdi, %rsi             /* a1 */
    movq %rax, %rdi             /* رقم الاستدعاء */
    call syscall_dispatch       /* الجواب يعود في rax، وهو ما يراه المستخدم */
```

وهنا **عقدان مختلفان يلتقيان**، وهذا هو عمل هذا الملفّ:

عقدُ الاستدعاء يقول: الوسائط في `rdi rsi rdx r10 r8 r9`، والرقم في `rax`،
و**كلُّ السجلّات تعود كما كانت إلا `rax` و`rcx` و`r11`**.

وعقدُ C يقول: الوسائط في `rdi rsi rdx rcx r8 r9`، وهذه السجلّات **متطايرة** —
للدالّة أن تتلفها.

فالسطران الاختلافان: `r10` مكان `rcx` لأن المعالج أتلف `rcx` بعنوان العودة.
وحفظُ `rdi rsi rdx r10 r8 r9` لأن عقد C يبيح إتلافها وعقد الاستدعاء يمنعه.

**المخرَج**

آخر، فيُفحَص كأي رقم آخر.

## البديهية ٥ في سطرٍ واحد

السطر الرابع هو موضوع هذا الفصل حقاً: مؤشّرٌ قيمتُه `0xffffffff80000000` — عنوانُ
نواتنا. لو نسخنا منه لقرأنا ذاكرةَ النواة وأرسلناها إلى المستخدم.

<!-- part: kernel/syscall.c -->

```c
bool copy_from_user(void *dst, uint64_t src, size_t n) {
    if (src >= USER_LIMIT) return false;                 /* يبدأ في النواة */
    if (n > USER_LIMIT || src + n > USER_LIMIT) return false; /* يتجاوزها، أو يلتفّ */
    for (size_t off = 0; off < n; ) {
        uint64_t page = (src + off) & ~0xfffull;
        /* الجذرُ العامل الآن لا جذرُ النواة: المؤشّر يُفحَص في فضاء صاحبه */
        uint64_t *pte = vmm_pte_in(vmm_cr3(), page, false);
        if (!pte || !(*pte & PTE_P) || !(*pte & PTE_U)) return false;  /* ليست له */
```

وأربعةُ فحوصٍ، وكلٌّ منها يردّ هجوماً مختلفاً:

| الفحص | ما يردّه |
|---|---|
| `src >= USER_LIMIT` | مؤشّرٌ يبدأ في ذاكرة النواة |
| `src + n > USER_LIMIT` | مؤشّرٌ يبدأ عند المستخدم **وينتهي** عند النواة |
| `n > USER_LIMIT` | التفافُ الجمع: طولٌ هائل يجعل `src + n` يبدو صغيراً |
| `PTE_P` و`PTE_U` | صفحةٌ مطابَقة، وللمستخدم فعلاً — لا لجارٍ في فضاءٍ آخر |

**والفحص بالصفحة لا بالمدى** لأن المدى قد يعبر صفحاتٍ بعضُها له وبعضُها ليس له.

⚠ ويبقى ثقبٌ مُعلَن: بين الفحص والنسخ لحظة. وفي نظامٍ بمعالجين، قد يُغيِّر خيطٌ
آخر من العملية نفسها المطابقةَ في تلك اللحظة — وهي `TOCTOU`. ولا نعالجها اليوم،
والفصل `22` هو الذي يخلق الشرط الذي تحتاجه.

## كسرها عمداً: مدخلٌ يخالف العقد

احذف حفظ `rdi rsi rdx r10 r8 r9` من المقطع، ودعْ دالّةَ التوزيع تتلفها بحقّها في
عقد C.

<!-- runs: 16x -->
<!-- out @abi: العطبُ في برنامج المستخدم، والسببُ في النواة -->

```
tag: OK[INFO] syscall n=1 a1=1 a2=402000 a3=7 -> 7
[INFO] syscall n=1 a1=a a2=401024 a3=1 -> -38
```

اقرأ `a1 = a`. برنامج المستخدم كتب `write(1, "\n", 1)`، ووصلت النواةَ `fd = 10`
— فردّت خطأً لأن لا وصفَ بهذا الرقم. والرقمُ المردود ثانويّ؛ الأوّلُ هو الوسيط.

والسبب في المترجم وهو مصيب: رأى أنّ `rdi` يحمل `1` من الاستدعاء السابق، وعقدُ
الاستدعاء يضمن بقاءه، فلم يُعِد تحميله. فالكودُ الذي وَلَّده صحيحٌ بحكم العقد،
ونواتُنا هي التي نقضته.

**النتيجة** أنّ نقض عقد الـABI ينتج عطباً يظهر في **برنامج المستخدم**، ويختلف
باختلاف المترجم ودرجة التحسين. ويقاوم التشخيص: لا سطرَ خاطئٌ في أيٍّ من
الطرفين.

⚠ ولاحظ أنّ الرسالتين الأوليين طُبعتا صحيحتين. العطبُ لم يظهر إلا حين قرّر
المترجم ألّا يعيد تحميل سجلّ — وذلك قرارُ تحسينٍ قد يتغيّر بتغيّر راية.

## كيف تفعلها الأنظمة الحقيقية

Linux يستعمل `swapgs`: تعليمةٌ تبدّل قاعدة `gs` بقيمةٍ محفوظةٍ في MSR، فيصير مكدَّسُ
النواة مقروءاً بـ`%gs:offset` بلا متغيّرٍ عامّ. ونحن نستعمل متغيّراً عامّاً —
ويعمل لأن عندنا معالجاً واحداً. والفصل `22` يكسر هذا الشرط.

وعنده جدولُ استثناءات: كلُّ تعليمة نسخٍ من المستخدم مسجَّلةٌ فيه بعنوان تعافٍ. فبدل
أن يفحص المطابقة مسبقاً، **ينسخ ويترك `#PF` يقع** — ومعالجُ الخطأ يجد التعليمة في
الجدول فيقفز إلى التعافي ويعيد `-EFAULT`. وثمنُ ذلك أنّ المسار السليم بلا فحصٍ
مسبقاً، وهو الأكثر.

| | نحن | جدول الاستثناءات |
|---|---|---|
| المسار السليم | مشيٌ في الجداول لكل صفحة | نسخٌ مباشر |
| المسار الفاسد | رفضٌ قبل اللمس | `#PF` ثم تعافٍ |
| ما يحتاجه | لا شيء | قسمٌ في الصورة، ومعالجٌ يقرؤه |

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «`syscall` مثل مقاطعة» | لا تبدّل المكدَّس ولا تدفع شيئاً. والفرق هو كلُّ تعقيد المقطع |
| «فحصتُ المؤشّر فهو آمن» | فحصتَ بدايته. والطولُ يعبر صفحاتٍ، والجمعُ يلتفّ |
| «رقم الاستدعاء يفهرس جدولاً» | رقمٌ من الحلقة ٣. وفهرسةٌ بلا فحصِ حدٍّ قراءةٌ خارج المصفوفة |
| «`sysret` أسرع فهي أفضل دائماً» | لا تعيد `rsp` ولا تصلح للعودة إلى حلقةٍ اختارها غيرك. و`iretq` تبقى للمقاطعات |
| «العقدان واحد» | عقدُ الاستدعاء يحفظ الوسائط، وعقدُ C يبيح إتلافها. واللوحة تُظهر ثمن الخلط |

## Checkpoint

١. `STAR[63:48] = 0x10` أعطى `cs = 0x20`. اشتقّ الرقم، وقل ماذا يقع لو كان
`SEL_UCODE = 0x18`.
٢. لماذا يُحفَظ `rcx` مع أنّ `sysretq` تقرؤه؟ وما الذي كان سيتلفه لولا الحفظ؟
٣. اكتب مؤشّراً وطولاً يمرّان بالفحص الأوّل ويسقطان بالثالث.
٤. `FMASK` يطفئ `IF`. لماذا لا يكفي أن نطفئها بـ`cli` كأوّل تعليمةٍ في المقطع؟

| | |
|---|---|
| مخطّط | عقدان متجاوران: سجلّاتُ الاستدعاء وسجلّاتُ C، والأسهمُ بينهما |

## التمرين

أضِف `sys_getpid` برقم ٣٩ يعيد رقماً ثابتاً، ونادِه من برنامج المستخدم. كم سطراً
لزم في كل طرف؟

ثم اجعل برنامج المستخدم يمرّر `len = 0xffffffffffffff00` مع مؤشّرٍ صالح. أي فحصٍ
ردّه؟ واحذف ذلك الفحص وحده وأعد التشغيل — ماذا يقع، ولماذا لا يقع `#PF` فوراً؟

ثم اقرأ `syscall_user_rsp` بعد أوّل استدعاء واطبعه. هل يقع في فضاء المستخدم؟ وما
الذي يمنع برنامجاً خبيثاً من وضع عنوانٍ في النصف الأعلى فيه؟

**الفصل التالي:** برنامجُنا بايتاتٌ كتبناها بأيدينا في مصفوفة. والبرامج الحقيقية
ملفّاتٌ لها بنية — وقد رأيتَ تلك البنية من الطرف الآخر في `c-advanced`.
