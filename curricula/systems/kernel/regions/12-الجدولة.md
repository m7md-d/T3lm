# الفصل 12 — الجدولة: من يُختار

## المشكلة

`context_switch` تعرف **كيف** تنتقل، ولا تعرف **إلى من**. وحتى الآن كنّا نسمّي
الخيط بأيدينا في الاختبار، وذلك يكفي لاختبار الآلية ولا يصلح نظاماً.

والمطلوب ثلاثة: بنيةٌ تعرف من يوجد، وحالةٌ في كل خيطٍ تقول هل يجوز اختياره الآن،
وسياسةٌ تختار واحداً منهم. والثلاثة معاً هي `schedule()`. والثانية هي موضع الخلط، لأن
«لا يريد المعالج» حالةٌ مختلفةٌ عن «يريده ولم يأخذه»، والخلطُ بينهما يجعل النائم
يستهلك دوراً في كل لفّة.

---

## البنية الداخلية: الحالة قبل السياسة

قبل أي سياسةٍ يجب أن يُجاب سؤالٌ أبسط: **من يجوز أن يعمل الآن؟** والجواب حقلٌ في
كل خيط:

<!-- part: kernel/thread.h -->

```c
enum tstate { T_UNUSED = 0, T_READY, T_RUNNING, T_BLOCKED, T_DEAD };
```

| الحالة | معناها | من ينقله عنها |
|---|---|---|
| `T_READY` | يريد المعالج ولا يملكه | الجدولة، باختياره |
| `T_RUNNING` | يملك المعالج الآن | الجدولة، باختيار غيره |
| `T_BLOCKED` | لا يريد المعالج: ينتظر شيئاً | **غيرُه** — وهذا هو المهمّ |
| `T_DEAD` | انتهى، ولم تُستَردّ موارده بعد | لا أحد |

والصفُّ الثالث هو الفرق بين الجدولة الحقيقية وحلقةِ دَوَران. الخيط المحجوب لا
يُختار **ولا يُفحَص**: ليس ينتظر في حلقة، بل خرج من مجموعة المرشّحين. ومن يعيده
طرفٌ آخر يعرف أنّ سببَ الانتظار زال.

## أصغر implementation

<!-- part: kernel/sched.c -->

```c
void schedule(void) {
    struct thread *cur = thread_current();
    struct thread *next = NULL;
    for (int k = 0; k < qn; k++) {
        qi = (qi + 1) % qn;
        if (queue[qi]->state == T_READY) { next = queue[qi]; break; }
    }
    if (!next || next == cur) return;         /* لا بديل: نُكمِل */

    if (cur->state == T_RUNNING) cur->state = T_READY;
    next->state = T_RUNNING;
    next->slices++;
    switches++;
    thread_set_current(next);
    context_switch(&cur->rsp, next->rsp);     /* نعود هنا حين يُختار cur ثانيةً */
}
```

وثلاثة قراراتٍ في هذه الأسطر، وكلُّها **سياسةٌ لا آلية**:

**البحثُ يبدأ من بعد آخر اختيار** (`qi` محفوظ بين النداءات). ولو بدأ من الصفر في
كل مرّةٍ لاختير الأوّلُ دائماً، ولجاع من بعده.

**`cur->state == T_RUNNING` شرطٌ لا زينة.** فالخيط الذي حجب نفسه صار `T_BLOCKED`
قبل أن ينادي `schedule`، ولو أعدناه `T_READY` لألغينا حجبَه في السطر التالي
لطلبه.

**العودة عند `!next`** تعني أنّ الخيط الجاري يُكمِل. وهذا صحيحٌ حين لا يكون معه جاهزٌ آخر، **وخطأٌ حين يكون هو نفسه محجوباً** — والنظام حينئذٍ بلا شيءٍ يعمل. والحلّ
المعتاد خيطٌ خامل لا يُحجَب، ونحن لا نبنيه لأن الخيط `boot` يقوم مقامه في
كل مراحلنا. **وهذا حدٌّ مُعلَن**، وتمرينُ الفصل يُظهر أثره.

## التجربة: المحجوب لا يُختار

<!-- runs: 12 -->

```c
static void waiter(void) {
    INFO("waiter: blocking myself. the queue must skip me.");
    thread_block();
    INFO("waiter: woken and running again");
}
static void waker(void) {
    for (int i = 0; i < 3; i++) { INFO("waker: pass %d", i); yield(); }
    thread_unblock(sleeper);
}
```

**المخرَج**

<!-- out @ours: الترتيب يتبع سياستنا الدوّارة، والحالات تتبع الجدول أعلاه -->

```
       at start         boot=RUNNING waiter=READY waker=READY
[INFO] waiter: blocking myself. the queue must skip me.
[INFO] waker: pass 0
[INFO] waker: pass 1
[INFO] waker: pass 2
[INFO] waker: unblocking the waiter
[INFO] waiter: woken and running again
       at end           boot=RUNNING waiter=DEAD waker=DEAD
[INFO] switches = 12
[INFO] thread 0 (boot  ) slices=5
[INFO] thread 1 (waiter) slices=2
[INFO] thread 2 (waker ) slices=5
```

اقرأ `slices`. الخيط `waiter` جُدوِل **مرّتين** في حين جُدوِل `waker` خمساً: مرّةً
ليحجب نفسه، ومرّةً بعد أن أُيقظ. وبين المرّتين مرّت ثلاث دوراتٍ كاملة لم يكن فيها
مرشَّحاً.

**المكسب** أنّ «الانتظار» صار له ثمنٌ صفريّ في المعالج. والخيط النائم لا يستهلك
شيئاً — وهذا هو الفرق الذي يبنيه الفصل `20` كاملاً فوق هذه الحالة.

⚠ ولا تُظهر هذه اللوحة إنصافاً ولا أولوية. سياستُنا دوّارةٌ بلا أوزان، وكلُّ خيطٍ
يأخذ دوراً واحداً — وهذا **قرارٌ** لا قانون. ومقارنةُ سياساتٍ أخرى بهذه اللوحة
غيرُ مشروعة: اللوحة تشهد على ما فعلَته سياستُنا، لا على أيّها أفضل.

## كيف تفعلها الأنظمة الحقيقية

الدوّارة أبسطُ ما يعمل، وثمنُها أنّها تعامل كلَّ الخيوط سواء. وذلك يكفي لخيوط
نواةٍ متشابهة، ولا يكفي لنظامٍ فيه محرِّرُ نصوصٍ ينتظر مفتاحاً ومترجِمٌ يحسب.

و`CFS` في Linux — ثم `EEVDF` بعده — يبني على فكرةٍ أخرى: لكل خيطٍ **زمنٌ افتراضيٌّ**
يتقدّم بمعدّلٍ يتبع وزنه، ويُختار صاحبُ أقلّ زمنٍ افتراضيّ. فالخيط الذي نام كثيراً
يجد نفسه متأخّراً، فيُختار أوّلاً — وهو ما يجعل الاستجابة جيّدةً بلا فئاتٍ خاصّة.

| | دوّارة | زمنٌ افتراضيّ موزون |
|---|---|---|
| ما تحتاجه من حالة | مؤشّرٌ في مصفوفة | زمنٌ متراكمٌ لكل خيط، وبنيةٌ مرتّبة |
| ما تشتريه | بساطةٌ وقابليةُ تنبّؤ | استجابةٌ للنائم، وأوزانٌ تُحترَم |
| كلفةُ الاختيار | مشيٌ حتى أوّل جاهز | استخراجُ أدنى من شجرة |

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الجدولة تقاطع الخيط» | لا تقاطع شيئاً. تُنادى — إمّا من الخيط نفسه، وإمّا من معالج مقاطعة. والفصل التالي هو الثاني |
| «المحجوب ينتظر في حلقة» | خرج من مجموعة المرشّحين. ولا يُفحَص أصلاً حتى يوقظه غيرُه |
| «الخيط يوقظ نفسه» | من حُجب لا ينفّذ شيئاً. فالإيقاظ من طرفٍ آخر دائماً — وهذا شرطٌ بنيويّ لا أسلوب |
| «`T_DEAD` تعني أنّ الموارد استُرِدَّت» | تعني أنه انتهى. والمكدَّس ما زال محجوزاً، والفصل `23` هو الذي يستردّه |
| «الدوّارة عادلة» | تعطي دوراً واحداً لكلٍّ. والعدلُ في الزمن شيءٌ آخر: خيطٌ يتنازل فوراً يأخذ دوراً كخيطٍ يستهلك شريحةً كاملة |

## Checkpoint

١. لماذا `qi` ساكنٌ بين النداءات؟ صِف ما يقع لو صُفِّر في أوّل `schedule`.
٢. الخيط `waiter` أخذ `slices=2`. سمِّ الحدثين اللذين أنتجا هذين الرقمين.
٣. لو حَجَبَ الخيطُ `boot` نفسَه وكلُّ الباقي محجوب، ما الذي ينفّذه المعالج؟
وما البنية التي تحلّ هذا في نظامٍ كامل؟
٤. `schedule` تزيد `switches` قبل `context_switch` لا بعدها. لماذا لا يصحّ العكس؟

## Artifact

| | |
|---|---|
| مخطّط | الطابور دائرةً، ومؤشّرُ `qi` عليها، ولكل خيطٍ لونُ حالته |
| تنفيذ | `schedule` و`thread_block` و`thread_unblock` |
| تجربةُ فشل | احجب كلَّ الخيوط ثم اقرأ ما يقع — تمرين الفصل |
| أثرُ تنفيذ | `waiter` يُحجَب ← ثلاث دورات لا يُختار فيها ← يُوقَظ ← يُختار |
| مقارنة | الزمن الافتراضيّ الموزون: ما يشتريه، وما يحتاجه من حالة |

## التمرين

اجعل كلَّ الخيوط تحجب نفسها بلا موقِظ، وشغّل. ما الذي ينفّذه المعالج؟ واقرأ
`schedule` وحدّد السطر الذي جعل ذلك ممكناً.

ثم أضِف خيطاً اسمه `idle` جسمُه `for (;;) __asm__ volatile("hlt");` ولا يُحجَب
أبداً، واستثنِه من الاختيار ما دام غيرُه جاهزاً. كم سطراً لزم؟ وما الذي تغيّر في
معنى «لا مرشَّح»؟

ثم أضِف حقل `weight` واجعل الخيط يُختار مرّتين متتاليتين إن كان وزنُه ٢. قارن
`slices` بالسابق — وهل هذا «عدل»؟ بأي تعريف؟

**الفصل التالي:** كلُّ ما سبق يقوم على أن الخيط **يتنازل**. فماذا عن خيطٍ لا يفعل؟
