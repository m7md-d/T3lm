# الفصل 02 — الرؤية قبل التعقيد

## المشكلة

الفصل السابق أثبت الوصول بشفرة خروج. وهي تقول شيئاً واحداً ولا تقول غيره: لا قيمةً
ولا عنواناً ولا سبب فشل. وكل ما يأتي بعدها — مخصِّصُ إطارات، وجدول صفحات، ومعالج
استثناء — يُفحَص بما يُطبَع.

فالمخرَج أوّل subsystem يُبنى، لأنه أداةُ فحص الباقي.

---

## الآلية الخام: منفذٌ لا عنوان

لـx86 فضاءُ عناوينٍ ثانٍ إلى جانب الذاكرة — منافذ I/O — لا يتقاطع معها،
وتعليمتان وحدهما تصلان إليه:

```
in  al, dx      /* اقرأ بايتاً من المنفذ في dx */
out dx, al      /* اكتب بايتاً إلى المنفذ في dx */
```

و`COM1` يسكن المنفذ `0x3F8`، وثمانيةُ سجلّاتٍ متتابعة بعده. وهذه أبسطُ آليةٍ خام
في المنهج: لا مطابقةً تحتاجها ولا جدولَ صفحات — ولهذا صلحت أن تكون الأولى.

⚠ وهذا الفضاء خاصٌّ بـx86. على `arm64` لا توجد منافذ I/O: كلُّ جهازٍ يُقرأ
ويُكتَب بعناوين ذاكرةٍ مطابَقة (MMIO)، وهو ما نبنيه في الفصل `18`.

---

## البنية الداخلية: ثمانيةُ سجلّاتٍ وبتٌّ واحد يهمّ

| الإزاحة | حين `DLAB=0` | حين `DLAB=1` |
|---|---|---|
| `+0` | بيانات — الكتابةُ إرسال، والقراءةُ استلام | نصفُ المقسوم الأدنى |
| `+1` | تمكينُ المقاطعات | نصفُ المقسوم الأعلى |
| `+2` | ضبطُ الـFIFO | — |
| `+3` | ضبطُ الخطّ: عددُ البتات والتماثل، وبتُّ `DLAB` | — |
| `+4` | ضبطُ المودم: `DTR` و`RTS` و`OUT2` | — |
| `+5` | حالةُ الخطّ — وفيه البتّ الذي يهمّ | — |

والبتّ الخامس في `+5` معناه «حوض الإرسال فارغ». فقبل كل بايتٍ نستقصيه.

والاستقصاء هنا مقصودٌ ومُعلَن: ما زلنا بلا IDT، فلا سبيل إلى مقاطعةٍ تخبرنا أنّ
الخطّ جاهز. والفصل `20` يعود إلى هذا الموضع بعد أن تصير المقاطعة متاحة.

## أصغر implementation

<!-- part: kernel/serial.c -->

```c
void serial_init(void) {
    outb(COM1 + R_IER, 0x00);   /* لا مقاطعات: لا IDT بعد */
    outb(COM1 + R_LCR, 0x80);   /* DLAB=1 ليصير 0 و1 نصفَي المقسوم */
    outb(COM1 + R_DATA, 0x01);  /* المقسوم 1 ⇒ 115200 باود */
    outb(COM1 + R_LCR, 0x03);   /* DLAB=0، ثمانية بتات، بلا تماثل، توقّفٌ واحد */
    outb(COM1 + R_FCR, 0xC7);   /* FIFO يعمل، ويُفرَّغ، وعتبته أربعة عشر */
    outb(COM1 + R_MCR, 0x0B);   /* DTR وRTS وOUT2 */
}

void serial_putc(char c) {
    if (c == '\n') serial_putc('\r');           /* الطرفية تريد CR قبل LF */
    while (!(inb(COM1 + R_LSR) & LSR_THR_EMPTY)) { }
    outb(COM1 + R_DATA, (uint8_t)c);
}
```

### والمُنسِّق ليس `printf`

المطلوب رؤيةُ ما يحدث. فالمدعوم `%s %c %d %u %x %p`، وسابقةُ الطول `l`/`z`،
وعرضٌ عشريّ مع `-` للمحاذاة إلى اليسار — وهو ما يلزم لطباعة جدولٍ في الفصل `04`.
ولا دقّةَ ولا أعدادٍ عائمة. والطول جزءٌ من العقد:

<!-- part: kernel/log.c -->

```c
        bool left = false, wide = false;
        int width = 0;
        if (*fmt == '-') { left = true; fmt++; }
        while (*fmt >= '0' && *fmt <= '9') width = width * 10 + (*fmt++ - '0');
        while (*fmt == 'l') { wide = true; fmt++; }
        case 'd': put_s(wide ? va_arg(ap, int64_t) : va_arg(ap, int), width, left); break;
```

## التجربة: أوّلُ ما نطبعه هو جوابُ الفصل السابق

<!-- runs: 02 -->

```c
serial_init();
serial_write("serial: raw write, before any formatter\n");
INFO("hhdm offset        = %p", (void *)hhdm_offset);
INFO("kernel phys base   = %p", (void *)kernel_phys_base);
INFO("kernel virt base   = %p", (void *)kernel_virt_base);
INFO("memmap entries     = %lu", memmap->entry_count);
```

**المخرَج**

<!-- out @boot: القيم من الـbootloader؛ والعنوان الفيزيائيّ يختلف بين تشغيلين -->

```
serial: raw write, before any formatter
[INFO] hhdm offset        = 0xffff800000000000
[INFO] kernel phys base   = 0x000000000ff3f000
[INFO] kernel virt base   = 0xffffffff80000000
[INFO] memmap entries     = 14
[INFO] int=-42  unsigned=4096  hex=deadbeef
[INFO] same value, %lx then %x: ffffffff80000000  vs  80000000
```

ثلاثةُ أرقامٍ تستحقّ القراءة. الصورة تعمل على `0xffffffff80000000` وهي فيزيائياً
على `0x0ff3f000` — أي نحو ٢٥٥ ميغابايت، ورقمٌ غيرُ مستدير اختاره المحمِّل. فقد سقط
فخُّ «النواة على `0x100000`» بسطرٍ مطبوع.

و`hhdm offset` هو الإزاحة التي تجعل كلَّ عنوانٍ فيزيائيّ مقروءاً بجمعها إليه. وهي
كيف نقرأ خريطة الذاكرة في الفصل التالي، وكيف نلمس جدول صفحاتٍ في `05`.

والسطر الأخير يُري ما يعنيه الطول: نفسُ القيمة، و`%x` قطعت نصفها الأعلى. والمُنسِّق
لا يعرف نوع ما أُعطي — **القاعدة** أنّ الوسيط المتغيّر يُقرأ بالحجم الذي كُتب به،
والعقد بينك وبين نفسك.

**المكسب** صار عندك أداةُ فحصٍ لكل ما بعده، وقد فحصتَ بها أوّل شيء: عقدَ التسليم.

## كسرها عمداً: احذف الانتظار، ثم اقرأ ما لا يحدث

المواصفة تقول إنّ الكتابة قبل خلوّ الحوض تفقد بايتاً. فلنحذف السطر:

<!-- part: variants/serial_nowait.c -->

```c
void serial_putc(char c) {
    if (c == '\n') serial_putc('\r');
    outb(COM1 + 0, (uint8_t)c);          /* بلا فحص LSR */
}
```

**المخرَج**

<!-- runs: 02x -->
<!-- out @qemu: ثماني سطورٍ متعاقبة، والنصّ كاملٌ بلا نقص -->

```
line 0: the quick brown fox jumps over the lazy dog
line 1: the quick brown fox jumps over the lazy dog
line 2: the quick brown fox jumps over the lazy dog
...
line 7: the quick brown fox jumps over the lazy dog
```

**النتيجة** لا شيء. لا بايتَ ضائعاً ولا حرفاً مشوّشاً.

وهذا هو الدرس نفسه: **المحاكي يخفي العيب.** UART الذي يُصنِّعه QEMU يستقبل
البايت كلَّما كُتب، ولا يُبلِّغ انشغالاً؛ أمّا 16550 حقيقيّ فحوضُه ستةَ عشرَ بايتاً
وما زاد يسقط.

**القاعدة** — وستتكرّر في هذا المنهج — أنّ الغياب في التشغيل ليس منعاً. وترتيبُ
مصادر الحقيقة يحسم: **المواصفة تقرّر، والتشغيل يشهد**. وسطرُ الانتظار يبقى بحكم
`@arch` وحدها؛ و`@qemu` لم تُظهر له حاجة.

⚠ وهذه أثمنُ صورةٍ للعيب: الذي لا يظهر في بيئة التطوير. ولو كتبتَ النواة على
المحاكي وحده، لكان أوّلُ تشغيلٍ على عتادٍ حقيقيّ هو أوّلُ مرّةٍ ترى فيها الخطأ.

## `panic`: حين يسقط ثابت

<!-- runs: 02p -->

```c
uint64_t frames = 0;
if (frames == 0) panic("no usable frames: memmap gave %lu entries", memmap->entry_count);
```

**المخرَج**

<!-- out @ours: صيغةُ panic قرارُنا، ولا تصف نواةً أخرى -->

```
[INFO] about to lose an invariant

[PANIC] no usable frames: memmap gave 14 entries
[PANIC] halted
```

و`panic` تطفئ المقاطعات أوّلاً بـ`cli`، وذلك قرارٌ له سبب: معالجٌ يعمل الآن قد
يمسّ نفس الحالة الفاسدة، فيكتب فوق الدليل الذي نحاول طباعته. ثم `hlt` في حلقة،
فلا ينفّذ المعالج ما بعدها.

وهي ناقصةٌ اليوم: لا سجلّاتٍ تُطبَع، ولا أثرَ مكدَّس، ولا شيءٌ عن الخيط الجاري —
لأن لا شيءَ من ذلك موجودٌ بعد. والفصل `26` يعود إليها ويكملها، وهذا **إعلانٌ لا
وعد**: الدالّة موجودةٌ الآن بأقلّ ما يعمل.

## كيف تفعلها الأنظمة الحقيقية

Linux يواجه المشكلة نفسها: `printk` يحتاج ذاكرةً وأقفالاً وجدولةً لا توجد بعد
في الإقلاع. وحلُّه طبقتان — `earlycon` يكتب إلى UART بالاستقصاء كما نفعل، ثم
يُسلَّم إلى `printk` الكامل بحاجزٍ حلقيّ حين تصير الذاكرة متاحة.

فالفرق ليس في الآلية بل في **متى** تُستبدَل. ونحن نبقى على الأولى المنهج كلَّه،
لأن نواتنا صغيرةٌ بما يكفي لئلّا تحتاج الثانية.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الطرفية بطيئة فهي خيارٌ سيّئ» | بطؤها من الاستقصاء، والوسيلة تعمل قبل أن توجد ذاكرةٌ أو مقاطعات — ولذلك اختيرت أوّلاً |
| «`%x` تطبع القيمة» | تطبع ٣٢ بتاً. والقيمةُ الأوسع تُقطَع بلا إنذار، كما في اللوحة |
| «لديّ `printf`» | لا libc. وما لدينا مُنسِّقٌ كتبناه، وحدودُه مكتوبةٌ في ترويسته |
| «نجح على QEMU فالكود صحيح» | QEMU يقرّر ما تفعله هذه الآلة، لا ما تضمنه المعمارية. ولوحةُ «احذف الانتظار» هي البرهان |
| «`panic` تُنهي البرنامج» | لا برنامجَ ولا نظامَ تشغيلٍ تحتها يستقبل شفرةً. تُوقِف المعالج، وهذا كلُّ ما تستطيع |

## Checkpoint

١. لماذا يُضبَط `DLAB` مرّتين في `serial_init`، ولماذا يُعاد إلى صفر؟
٢. `serial_putc` تنادي نفسها حين ترى `\n`. ما أقصى عمقٍ للاستدعاء الذاتيّ هنا،
وكيف تعرف أنه لا يفيض؟
٣. لو كان `hhdm offset` صفراً، أي سطرٍ في هذا الفصل كان سيفشل، وأيّها كان
سيستمرّ صحيحاً؟
٤. لماذا لا نستطيع أن نكتب `panic` تطبع أثر المكدَّس الآن؟ وأي فصلٍ يعطينا ما
يلزم لذلك؟

## Artifact

| | |
|---|---|
| مخطّط | `kprintf` ← `serial_putc` ← استقصاء `LSR` ← `out 0x3F8` |
| تنفيذ | المرحلة `02`: طرفيةٌ ومُنسِّقٌ و`panic` |
| تجربةُ فشل | المرحلة `02x`: حذفُ الانتظار — ولا فرق، **وهو النتيجة** |
| أثرُ تنفيذ | قيمُ التسليم مطبوعةً: الإزاحة والعنوانان وعددُ المداخل |
| مقارنة | `earlycon` ثم `printk`: أي طبقةٍ عندنا، وأيُّها لا نحتاج ولماذا؟ |

## التمرين

أضف إلى المُنسِّق `%b` تطبع القيمة ثنائيةً بأربعٍ وستّين خانة. ثم اطبع بها
`hhdm_offset`، وعدَّ الأصفار السفلى.

كم صفراً؟ وما الذي يقوله ذلك عن محاذاة الإزاحة، ولماذا لا بدّ أن تكون كذلك؟

ثم اجعل `serial_putc` تعدّ كم دورةً انتظرت في حلقة الاستقصاء، واطبع المجموع بعد
ثماني سطور. ما الرقم على QEMU، وما تتوقّعه على عتادٍ حقيقيّ عند ١١٥٢٠٠ باود
لثمانين حرفاً؟

**الفصل التالي:** تقرأ الآن وتطبع، والمعالج يسمح لك بـ`in` و`out` — وهما تعليمتان
لا يسمح بهما لكل كود. فما الذي يجعل هذا الكود مميَّزاً بالضبط، وأي جدولٍ يحمل
الجواب؟
