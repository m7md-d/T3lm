# الفصل 24 — الأنبوب

## المشكلة

عملياتُنا معزولةٌ بعد الفصل `17`: نفسُ العنوان الافتراضيّ يعني إطارين
مختلفين، ولا تملك إحداهما اسماً للأخرى.

والعزلُ الكامل عديمُ الفائدة. والمطلوب قناةٌ **لا تكسره**: لا ذاكرةً مشتركةً ولا
مؤشّراتٍ تعبر، بل بايتاتٌ تُنسَخ عبر النواة.

والأنبوب أصغرُ ما يحقّق ذلك. وهو يجمع كلَّ ما بُني: وصفٌ من `19`، وحجبٌ ويقظةٌ من
`20`، وحالةٌ مشتركةٌ يحميها قفلٌ من `21`.

---

## البنية الداخلية

<!-- part: kernel/pipe.c -->

```c
struct pipe {
    uint8_t *buf;
    size_t   cap, head, tail;
    struct waitq readers, writers;
    struct spinlock lk;
    bool     closed;
};
```

وطابورا نومٍ لا واحد. والسبب أنّ الانتظار هنا نوعان مختلفان لا يُوقَظان بنفس
الحدث:

| من ينتظر | متى ينام | ومن يوقظه |
|---|---|---|
| قارئ | الحاجز فارغ | **كاتبٌ** وضع بايتاً |
| كاتب | الحاجز ممتلئ | **قارئٌ** أخلى مكاناً |

ولو جمعناهما في طابورٍ واحد، لأيقظ الكاتبُ كاتباً آخر — فيجد الحاجز ممتلئاً ويعود
إلى النوم. وذلك صحيحٌ ولا يتقدّم، وهو نمطُ `thundering herd`.

### والحاجز دائريّ بعدّادين لا مؤشّرين

`head` و`tail` عدّادان يزيدان ولا ينقصان، والموضع `index % cap`. فالفرق `head - tail`
هو عددُ البايتات المستعمَلة:

| الحالة | بعدّادين | بمؤشّرَين يلتفّان |
|---|---|---|
| فارغ | `head - tail == 0` | `head == tail` |
| ممتلئ | `head - tail == cap` | `head == tail` — **نفسُ الشرط** |
| المستعمَل | `head - tail` | يحتاج حقلاً ثالثاً أو خانةً مهدورة |

فالصفّان الأوّلان يتطابقان بالمؤشّرات، ولا يتطابقان بالعدّادات. وثمنُ ذلك التفافُ
العدّاد بعد ٢⁶⁴ بايتاً — وهو ما لا يُبلَغ.

## أصغر implementation

```c
static int64_t pipe_write(struct inode *ino, const void *src, size_t want) {
    struct pipe *p = ino->priv;
    size_t n = 0;
    while (n < want) {
        while (full_(p)) { wblocks++; wq_wake_all(&p->readers); wq_wait(&p->writers); }
        while (n < want && !full_(p)) { p->buf[p->head % p->cap] = ((const uint8_t *)src)[n++]; p->head++; }
        wq_wake_all(&p->readers);      /* صار فيه بيانات */
    }
    return (int64_t)n;
}
```

وثلاثةُ قراراتٍ في هذه الأسطر:

**الكتابةُ لا تعود ناقصة.** الحلقةُ الخارجية تدور حتى يُكتَب كلُّ ما طُلب. وهذا
اختيارٌ يخالف `read` — التي تعود بما استطاعت — وله سببٌ في العقد: كاتبٌ يعود
بنصف رسالةٍ يترك الباقي بلا مالك.

**إيقاظُ القرّاء قبل النوم.** الكاتب الذي وجد الحاجز ممتلئاً يوقظ القرّاء **ثم**
ينام. ولو نام أوّلاً وكان كلُّ القرّاء نائمين، لنام الجميع بلا من يحرّك شيئاً.

**والقراءةُ تعود بما وجدت.** فقارئٌ طلب ثمانيةً ووجد ثلاثةً يأخذ الثلاثة — وهذا
ما يجعل الحلقةَ حول `read` لازمةً في كل برنامجٍ يقرأ من أنبوب.

## التجربة: خمسةٌ وأربعون بايتاً في حاجزٍ من ستّةَ عشرَ

خمسةٌ وأربعون بايتاً عبرت حاجزاً سعتُه ستّةَ عشر. والعدّادان في السطر الأخير هما
الدليل: القارئ نام ثلاثاً لأن الحاجز فرغ، والكاتب نام مرّتين لأنه امتلأ.

**وهذا هو التحكّم بالتدفّق** ولم نكتب له سطراً واحداً: هو نتيجةٌ لحاجزٍ محدودٍ
وطابورَي نوم. فالكاتب الأسرع يُبطَّأ إلى سرعة القارئ تلقائياً.

⚠ والمخرَج متداخلٌ بلا أسطر لأن العمليتين تكتبان على نفس الطرفية بلا تزامنٍ
بينهما. وذلك **عيبٌ نتركه ظاهراً**: الطرفية موردٌ مشترَكٌ لا يحميه قفل، وهو بالضبط
ما يحكمه الفصل `21` — ولو كان لكلٍّ سطرٌ كامل لما ظهر.

**المكسب** أنّ عمليتين تبادلتا بياناتٍ بلا أن ترى إحداهما ذاكرةَ الأخرى، ولا أن
تعرف أنّ هناك أخرى أصلاً. وهذا هو IPC في أصغر صورةٍ تعمل.

## ولماذا يبقى العزل قائماً

البايتات **تُنسَخ مرّتين**: من فضاء الكاتب إلى حاجزٍ في النواة، ثم من الحاجز إلى
فضاء القارئ. ولا مؤشّرَ يعبر، ولا صفحةَ تُشارَك.

| | الأنبوب | الذاكرة المشتركة |
|---|---|---|
| النسخ | مرّتان | صفر |
| العزل | كامل | مكسورٌ بالتصميم |
| التزامن | في النواة، مجّاناً | **على العمليتين** |
| الحدّ | سعةُ الحاجز | حجمُ المطابقة |

والصفُّ الثالث هو الثمن الحقيقيّ للذاكرة المشتركة: تُسقِط النسخ وتُسقِط معه
التزامن الذي كان يأتي معه. فتصير المزامنةُ واجباً على البرنامجين — وهو ما درستَه
في `c-advanced` من الفصل `21` إلى `25`.

⚠ ولا نبني الذاكرة المشتركة: تحتاج مطابقةَ نفس الإطار في فضاءين، وهو ما تستطيعه
`vmm_map_in` بسطر — والناقصُ ليس الآلية بل **عقدُ التزامن** الذي يجعلها صالحةً
للاستعمال.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الأنبوب ملفّ» | له وصفٌ ويُقرأ ويُكتَب، ولا موضعَ فيه ولا حجم. و`lseek` عليه بلا معنى |
| «`write` تكتب ما طلبتَ» | في أنبوبنا نعم، وبحجبٍ حتى يتّسع. وفي أنظمةٍ أخرى قد تعود ناقصة |
| «`read` تعيد ما طلبتَ» | تعيد ما وجدت. والحلقةُ حولها ليست احتياطاً |
| «طابورُ نومٍ واحدٌ يكفي» | الكاتب يوقظ كاتباً فيعود إلى النوم. ونوعا الانتظار لا يُوقَظان بنفس الحدث |
| «الأنبوب أبطأ فهو أسوأ» | ينسخ مرّتين ويعطي تزامناً مجّاناً. والمشتركةُ تُسقِط النسخ وتُحمِّلك التزامن |
| «العمليتان تعرفان بعضهما» | كلٌّ تعرف اسماً في نظام الملفّات. ولا واحدةَ تعرف أنّ للأخرى وجوداً |

## Checkpoint

١. لماذا طابوران لا واحد؟ صِف التسلسل الذي يقف لو جمعناهما.
٢. `head` و`tail` عدّادان يزيدان ولا ينقصان. ما اللبس الذي يمنعه هذا، ومتى يلتفّان
عملياً؟
٣. الكاتب يوقظ القرّاء قبل أن ينام. اكتب ما يقع لو نام أوّلاً وكان القارئ نائماً.
٤. لو أغلق القارئُ طرفه وبقي الكاتب يكتب: ما الذي يجب أن يحدث، وأي حقلٍ في
`struct pipe` تركناه له؟

## Artifact

| | |
|---|---|
| مخطّط | حاجزٌ دائريّ بـ`head` و`tail`، وطابورا نومٍ على طرفيه |
| تنفيذ | `pipe_read` و`pipe_write` وربطُهما بـVFS |
| تجربةُ فشل | طابورٌ واحدٌ بدل اثنين — تمرين الفصل |
| أثرُ تنفيذ | كتابةٌ ← امتلاء ← إيقاظُ قارئ ← نومُ كاتب ← قراءة ← إيقاظُ كاتب |
| مقارنة | الذاكرة المشتركة: ما تُسقِطه، وما تُحمِّله للبرنامجين |

## التمرين

اجعل الحاجز أربعةَ آلافِ بايت. كم صارت الحجبات؟ وهل صار الكاتب أسرع فعلاً — وبأي
مقياسٍ تقيسه؟

ثم استعمل طابوراً واحداً للطرفين وشغّل بكاتبين وقارئٍ واحد. هل وقف شيء؟ وكم مرّةً
أُيقظ خيطٌ ليعود إلى النوم فوراً؟

ثم أضِف `closed`: اجعل القارئ يغلق طرفه بعد عشرين بايتاً، واجعل `pipe_write`
تعيد خطأً بدل أن تُحجَب إلى الأبد. أي رقمِ خطأٍ اخترتَ، ولماذا؟

**الفصل التالي:** نظامُك يشغّل عملياتٍ ويخدمها ويعزلها. وكلُّ حدٍّ بنيتَه يقوم على
بتٍّ في مدخل — فماذا لو نسيتَ بتّاً واحداً؟
