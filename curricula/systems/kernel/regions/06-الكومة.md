# الفصل 06 — `kmalloc`، والسلسلة تحته

## المشكلة

النواة تحتاج بنًى صغيرةً كثيرة: بنيةَ خيطٍ في الفصل `10`، ومدخلَ جدول ملفّاتٍ في
`19`، وحاجزَ أنبوبٍ في `24`. وأحجامُها ليست مضاعفاتٍ لأربعة كيلوبايت، وأعمارُها
ليست عمر النظام.

وما بنيناه حتى الآن يعطي إطاراً كاملاً ويطلب مطابقةً بسطرين. فكيف تصير هذه
السلسلة نداءً واحداً؟

وشرطُ هذا الفصل — من البديهية ٢ — أن تعرف عند نهايته السلسلةَ كلَّها بلا قفزةٍ
سحرية: `kmalloc` ← مدًى افتراضيّ ← مطابقة ← إطارٌ فيزيائيّ ← RAM.

---

## الصورة العامة: نافذةٌ نملكها

الكومة تسكن مدًى افتراضياً نختاره فوق صورة النواة، ونمدّه إطاراً إطاراً:

<!-- part: kernel/kheap.h -->

```c
#define KHEAP_BASE 0xffffffffc0000000ull   /* فوق صورة النواة، ونافذةٌ نملكها */
```

وهو `pml4[511] pdpt[511]` — ونواتنا في `pdpt[510]` كما رأينا في الفصل `05`. فبينهما
جيجابايتٌ كاملٌ من فراغ، ولا يتعارضان.

---

## البنية الداخلية: ترويسةٌ لكل كتلة

```c
struct hdr {
    size_t size;          /* حجمُ البيانات، بلا الترويسة */
    bool   free;
    struct hdr *next;     /* بالترتيب العنوانيّ — فالدمج يصير جارياً */
};
```

وحقلُ `next` مرتّبٌ عنوانياً بقرار، لا بالمصادفة. فالدمج يحتاج أن يعرف من يجاور
مَن في **العنوان**؛ وقائمةٌ مرتّبةٌ بترتيب التحرير تعرف من حُرِّر قبل مَن، وذلك لا
يفيد الدمج شيئاً.

### والمدّ هو السلسلة كلُّها

<!-- part: kernel/kheap.c -->

```c
static bool grow(size_t bytes) {
    size_t pages = (ALIGN_UP(bytes, PAGE_SIZE)) / PAGE_SIZE;
    for (size_t i = 0; i < pages; i++) {
        uint64_t f = pmm_alloc();                                  /* الفصل 04 */
        if (!f) return false;
        if (!vmm_map(heap_end, f, PTE_W | PTE_NX)) { pmm_free(f); return false; }
        heap_end += PAGE_SIZE;                                     /* الفصل 05 */
        frames_used++;
    }
    return true;
}
```

خمسةُ أسطرٍ فيها الفصلان السابقان. و`PTE_NX` قرارٌ مُعلَن: الكومة بياناتٌ لا كود،
فلا يُنفَّذ منها شيء. وتفصيلُه في الفصل `25`.

و`pmm_free(f)` عند فشل المطابقة سطرٌ يسهل نسيانُه: الإطار خُصِّص ولم يُستعمَل، ولو
تُرِك لتسرّب — إطارٌ مأخوذٌ لا يعرفه أحد، ولا سبيل إلى استعادته.

## التجربة: ثلاثةُ طلباتٍ وقراءةُ الفجوات

<!-- runs: 06 -->

```c
char *a = kmalloc(100), *b = kmalloc(2000), *c = kmalloc(48);
kheap_dump();
```

**المخرَج**

<!-- out @ours: التخطيط سياستُنا: ترويسةُ ٢٤ بايتاً، ومحاذاةُ ١٦، وfirst-fit -->

```
[INFO] after init: used=0 blocks=1 frames=1
[INFO] a=0xffffffffc0000018 b=0xffffffffc00000a0 c=0xffffffffc0000888
[INFO] gaps: b-a = 136   c-b = 2024   (header = 24 bytes)
       blk 0  at 0xffffffffc0000000  size    112  used
       blk 1  at 0xffffffffc0000088  size   2000  used
       blk 2  at 0xffffffffc0000870  size     48  used
       blk 3  at 0xffffffffc00008b8  size   1840  free
```

اقرأ الأرقام بدل تصديقها. `a` عند `...018`: أي ٢٤ بايتاً بعد أوّل الكومة — وهي
الترويسة. وطلبتَ ١٠٠ فأخذت الكتلة ١١٢: محاذاةٌ إلى ١٦.

والفجوة `b - a = 136` = ١١٢ بياناتٍ + ٢٤ ترويسة. فالثمن المقيس **٢٤ بايتاً لكل
تخصيصٍ** مهما صغر. وطلبٌ من ٨ بايتاتٍ يستهلك ٤٠ — خمسةَ أضعاف ما طلبتَ، وهو
ما يفتح الحاجة إلى مخصِّصٍ للأحجام الصغيرة.

والكتلة الأخيرة `1840 free` هي بقيّةُ الصفحة الأولى: ‎4096 − ‎24 − ‎112 − ‎24 −
‎2000 − ‎24 − ‎48 − ‎24 = ‎1840. فالحساب يقفل، ولا بايتَ مجهول.

### السلسلة تحت مؤشّرٍ واحد

<!-- runs: 06 -->
<!-- out @arch: الورقة تحمل `D` لأنّنا كتبنا عبرها؛ وعناوين الـbootloader تختلف بين تشغيلين -->

```
[INFO] kmalloc gave virtual 0xffffffffc00000a0
[INFO]   -> resolve -> physical 0x00000000000750a0
[INFO] walk 0xffffffffc00000a0  ->  pml4[511] pdpt[511] pd[0] pt[0] off 160
       pml4[511] = 0x000000000ff80027  PWUA--
       pdpt[511] = 0x0000000000076023  PW-A--
       pd  [  0] = 0x0000000000077023  PW-A--
       pt  [  0] = 0x8000000000075063  PW-ADX
```

هذا هو **Checkpoint** الحزمة كلِّها في أربعة أسطر: مؤشّرٌ أعادته `kmalloc`، ثم
فهارسه الأربعة، ثم الإطار `0x75000`، ثم الإزاحة ١٦٠ داخله — فالفيزيائيّ
`0x750a0`.

والورقة `PW-ADX`: فيها `D` الذي لم يكن في الفصل `05`. كتبنا عبر هذه الصفحة،
فكتب المعالج بتّ «مُوسَخة». وهو البتّ الذي تقوم عليه سياسات الإخراج إلى القرص في
الأنظمة الكاملة، ولا نبنيها.

ولاحظ `pml4[511]` مشتركٌ بين نواتنا وكومتنا، و`pdpt[511]` جديد.

### التحرير والدمج

<!-- runs: 06 -->
<!-- out @ours: first-fit والدمجُ مع الجار اللاحق؛ وعدّاد الإطارات يتغيّر بتغيّر حجم الصورة -->

```
[INFO] after freeing b: used=160 blocks=4
[INFO] re-alloc of the same size gave 0xffffffffc00000a0  (same=yes)
[INFO] 12 KiB request: 0xffffffffc0001018   frames now 5
[INFO] pmm free went 65143 -> 65136
```

`used=160` = ١١٢ + ٤٨، فـ`b` خرجت من الحساب. و`blocks` بقيت أربعاً: كتلةُ `b`
المحرَّرة لم تُدمَج، لأن جارَها `c` مستعمَل. ثم أعاد الطلبُ نفسَ العنوان، وذلك
`first-fit` وقد وجد أوّل ما يكفي.

وطلبُ ١٢ كيلوبايت مدّ النافذة إلى خمسة إطارات، و`pmm` نزل سبعة إطارات: أربعةٌ
للكومة وثلاثةٌ جداولُ صفحاتٍ وسيطة. **النتيجة** أنّ ثمن التخصيص ليس في الكومة
وحدها — البنيةُ التي تصف المطابقة تستهلك إطاراتٍ أيضاً.

## المقايضة: الـbump ليس درجةً أدنى

يُعرَض هذان أحياناً سلسلةً تصاعدية: bump بسيطٌ فيه عيبٌ تكشفه القائمة. وذلك خطأ.

<!-- part: demos/s06.c -->

```c
static uint8_t  arena[512];
static size_t   bump;
static void *bump_alloc(size_t n) {
    n = (n + 15) & ~15ull;
    if (bump + n > sizeof arena) return NULL;
    void *p = &arena[bump]; bump += n; return p;
}
```

**المخرَج**

<!-- runs: 06 -->
<!-- out @ours: الفجوة ٦٤ لا ٨٨ — لا ترويسةَ بين الكتلتين -->

```
[INFO] bump arena: 0xffffffff80004120 then 0xffffffff80004160, no header between them (gap=64)
```

فجوةٌ ٦٤ لطلبٍ ٦٤: **صفرُ حِمل**. ولا بحثَ ولا دمجَ ولا ترويسة.

| | `bump` | القائمة الضمنية |
|---|---|---|
| الهدف | مدًى يُحرَّر دفعةً واحدة | كتلٌ تُحرَّر مستقلّةً |
| الحِمل لكل تخصيص | صفر | ٢٤ بايتاً |
| زمن التخصيص | جمعٌ واحد | بحثٌ في القائمة |
| ما لا يستطيعه | تحريرُ كتلةٍ واحدة | أن يكون بلا حِمل |

فلكلٍّ هدفٌ وحِمْلٌ وثمن. والـbump هو الصواب لتحليل رسالةٍ واحدة تُرمى بعدها كلُّ
بنياتها — وهو ما تفعله بنيةُ `arena` أعلاه، ولا عيبَ فيه يُصلَح.

## كيف تفعلها الأنظمة الحقيقية

Linux عنده ثلاث طبقاتٍ لا واحدة: `buddy` للإطارات (الفصل `04`)، و`SLUB` لكائناتٍ
من نوعٍ واحدٍ بحجمٍ ثابت، و`kmalloc` فوقهما لأحجامٍ عامّة بمجموعاتٍ محدَّدة.

والذي يشتريه `SLUB` هو بالضبط ما قاسته لوحتُنا: **الترويسة**. فكائناتٌ متساويةُ
الحجم في صفحةٍ واحدة لا تحتاج حقلَ حجمٍ لكل واحد — الحجم صفةُ الصفحة. فيسقط
الثمنُ الذي دفعناه ٢٤ بايتاً.

⚠ ونحن لا نبني `SLUB`، وذلك حدٌّ مُعلَن: عدد بنياتنا الصغيرة قليل، وقياسُ الحاجة
شرطٌ قبل بناء طبقةٍ ثالثة.

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «`kmalloc` تعطي ذاكرةً» | تعطي عنواناً افتراضياً في نافذةٍ مطابَقة. والذاكرةُ إطاراتٌ من `pmm`، وقد تُخصَّص لحظةَ الطلب |
| «الحجم الذي طلبتُه هو ما استُهلك» | ‎+٢٤ ترويسةً و‎+محاذاةً إلى ١٦. واللوحة: طلبُ ١٠٠ صار ١١٢ في كتلةٍ تشغل ١٣٦ |
| «التحرير يُرجع الذاكرة إلى النظام» | يُعلِّم كتلةً حرّة. والإطارات تبقى مطابَقةً ومأخوذةً من `pmm` — ولا نقلّص النافذة |
| «`bump` نسخةٌ بدائية من القائمة» | عقدٌ آخر. والفجوة ٦٤ مقابل ٨٨ هي الفرق، ولا يُقرأ ترتيباً |
| «`kfree` تعرف الحجم بالسحر» | الترويسة قبل المؤشّر بـ٢٤ بايتاً. و`kfree` تطرح ثم تقرأ — ولهذا يفسد تحريرُ مؤشّرٍ لم تعطه `kmalloc` |
| «نفدت الكومة ⇒ نفدت الذاكرة» | نفد ما مُدَّ. والمدّ يفشل لسببين مختلفين: لا إطارات، أو لا مدخلَ جدولٍ يُبنى |

## Checkpoint

١. اشرح السلسلة من `kmalloc(2000)` إلى بايتٍ في RAM، وسمِّ في كل خطوةٍ البنية
التي استُشيرت والملفّ الذي يملكها.
٢. لماذا رتّبنا القائمة عنوانياً لا بترتيب التحرير؟ واذكر ما يفسد لو رتّبناها
بالتحرير.
٣. طلبُ ١٢ كيلوبايت أنزل `pmm` سبعة إطارات لا أربعة. أين الثلاثة الباقية؟
٤. `kfree(p)` تقرأ الترويسة عند `p - 24`. اكتب ثلاثة مؤشّراتٍ يُفسِد تحريرُها
الكومة، وقل ما يقرؤه `kfree` في كلٍّ منها.

## Artifact

| | |
|---|---|
| مخطّط | `kmalloc` ← كتلة ← نافذة ← مطابقة ← إطار ← RAM، وعند كل سهمٍ اسمُ الملفّ |
| تنفيذ | `kheap_init` و`kmalloc` و`kfree` بالدمج |
| تجربةُ فشل | `kfree` مرّتين ⇒ `panic`. وأضِف: تحريرُ مؤشّرٍ من `arena` |
| أثرُ تنفيذ | لوحةُ المشي تحت `b`: أربعةُ فهارس، إطار، إزاحة ١٦٠ |
| مقارنة | `SLUB` يُلغي الترويسة، والثمنُ المقيس عندنا ٢٤ بايتاً |

## التمرين

اطبع مجموع ما طلبتَه ومجموع ما استُهلك فعلاً بعد ألف تخصيصٍ بأحجامٍ من ٨ إلى ٦٤
بايتاً، واحسب النسبة.

ثم اجعل الترويسة `uint32_t size` وبتّاً واحداً للحالة بدل الحقول الثلاثة، وأعد
القياس. كم نزل الحِمل؟ وما الذي خسرتَه في `kfree` — وأي عملياتٍ صارت أبطأ؟

ثم حرّر `a` و`c` بعد `b` في اللوحة أعلاه، واطبع `kheap_dump`. كم كتلةً بقيت؟
ولماذا لا تعود الكومة كتلةً واحدةً مع أنّ كل شيءٍ محرَّر — وما الذي يلزم `kfree`
لتفعل ذلك؟

**الفصل التالي:** انتهت حزمة الذاكرة، وبقي فيها سؤالٌ بلا جواب: المرحلة `05x`
لمست صفحةً بلا مطابقة، فأعيد تعيينُ الآلة و`CR2` ممحوّ. فمن يستقبل الخطأ، وكيف
يصل من العتاد إلى دالّة C؟
