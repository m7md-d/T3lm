# الفصل 19 — VFS وجدولُ الأوصاف

## المشكلة

برنامجُ المستخدم يطلب «افتح `motd`». وليس في العتاد شيءٌ اسمُه ملفّ: لا سجلَّ ولا
بتَّ ولا تعليمة.

وهذا الفصل يختلف عمّا قبله بذلك: البديهية ٢ تسأل عن الآلية الخام تحت التجريد،
والجواب هنا **لا آليةَ خام**. الملفُّ تجريدٌ خالصٌ يخترعه الكيرنل ويفرضه بكودٍ
يكتبه — وقد قال الفصل `00` ذلك في جدول الموارد، وهذا موضعُه.

---

## البنية الداخلية: ثلاثةٌ تُخلَط

| | ما هو | كم منه | يملكه |
|---|---|---|---|
| `inode` | الشيءُ الموجود: بياناتٌ وطول | واحدٌ لكل ملفّ | نظام الملفّات |
| `file` | **فتحةٌ** عليه: عقدةٌ + موضعُ قراءة | واحدٌ لكل `open` | النواة |
| `fd` | **فهرسٌ** في جدول العملية | واحدٌ لكل عملية | العملية |

<!-- part: kernel/vfs.h -->

```c
struct inode {
    char     name[VFS_NAME];
    uint8_t *data;
    size_t   size, cap;
    bool     used;
    /* جهازٌ لا بياناتٌ: تُنادى بدل القراءة من `data` */
    int64_t (*dev_read)(struct inode *, void *buf, size_t n);
};

struct file {
    struct inode *ino;
    size_t   pos;
    bool     used;
    int      refs;
};
```

وحقلُ `pos` في `file` لا في `inode` هو الفرق كلُّه: فتحتان على نفس الملفّ لهما
موضعان مستقلّان، وقراءةُ إحداهما لا تحرّك الأخرى.

و`refs` يقول لماذا يوجد `file` أصلاً: فتحةٌ قد تُشارَك — بين عمليتين بعد `fork`،
أو بين وصفين بعد `dup`. فتُغلَق العقدةُ حين يسقط آخرُ مرجع، لا حين يُغلَق أوّلُ وصف.

⚠ ونحن لا نبني `fork` ولا `dup`، فـ`refs` عندنا يبقى واحداً. وهو حقلٌ **يحمل
تصميماً لا حاجةً قائمة** — ولولا أنّ العقد يقتضيه لَحُذف بحكم قاعدة الفصل `10`.

## الوصف فهرسٌ محلّيّ

<!-- part: kernel/proc.c -->

```c
int proc_fd_set(int fh) {
    struct process *p = proc_current();
    if (!p) return -1;
    for (int i = 3; i < MAX_FDS; i++)
        if (p->fds[i] < 0) { p->fds[i] = fh; return i; }   /* أصغرُ فهرسٍ حرّ */
    return -24;
}
```

والبدء من `3` اصطلاحٌ لا قانون: الثلاثة الأولى محجوزةٌ للدخل والخرج والخطأ.
و«أصغرُ فهرسٍ حرّ» قاعدةٌ من POSIX، وعليها تقوم حيلةُ `close(1); open(f)` التي
تجعل المخرَج يذهب إلى ملفّ.

**والوصف ليس مؤشّراً**، وهذا قرارُ عزلٍ لا راحةِ برمجة: لو أعطينا المستخدم مؤشّراً
إلى `struct file` لصار بيده عنوانٌ في ذاكرة النواة — يزوّره فيقرأ ما ليس له. أمّا
الفهرس فرقمٌ صغير، وتزويرُه يعطي فهرساً آخر في **جدوله هو**.

## أصغر implementation

أربعُ عملياتٍ لا أكثر:

<!-- part: kernel/vfs.c -->

```c
int64_t vfs_read(int fh, void *buf, size_t n) {
    struct file *f = vfs_file(fh);
    if (!f || !f->used) return -9;                  /* EBADF */
    if (f->ino->dev_read) return f->ino->dev_read(f->ino, buf, n);
    if (f->pos >= f->ino->size) return 0;           /* نهايةُ الملفّ */
    size_t left = f->ino->size - f->pos;
    if (n > left) n = left;
    memcpy(buf, f->ino->data + f->pos, n);
    f->pos += n;
    return (int64_t)n;
}
```

والسطرُ الثالث هو الـVFS كلُّه: **مؤشّرُ دالّةٍ في العقدة.** فإن وُجد، فالقراءة
تنادي شيئاً آخر؛ وإلّا فبيانات. وبهذا السطر يصير الجهازُ ملفّاً، والفصل التالي
يستعمله.

وهذه أصغرُ صورةٍ للتعدّدية: لا `struct file_operations` بعشرين حقلاً، ولا
`superblock`، ولا `dentry`. **ولا مجلّدات** — فالبحث خطّيٌّ في ثماني عقد.

## التجربة

<!-- runs: 19 -->

```c
int fd = (int)open("motd");
long n = read(fd, buf, sizeof buf);
```

**المخرَج**

<!-- out @ours: أرقامُ الأوصاف تتبع قاعدة «أصغرُ حرّ» وقد بدأناها من ٣ -->

```
[INFO] ramfs contents:
[INFO]   motd     31 bytes
[INFO]   notes    58 bytes
[INFO] nodes=2
open("motd") -> fd 3
read -> 31 bytes: welcome to a kernel with files
open("notes") -> fd 4
an inode is what exists; a file is an open position on it
open("missing") -> -2
read(99) -> -9
close(fd) -> 0
```

`fd 3` ثم `fd 4`: الجدول محلّيٌّ لهذه العملية، والثلاثةُ الأولى محجوزة.

و`open("missing") -> -2` و`read(99) -> -9`: اسمٌ لا يوجد ووصفٌ خارج الجدول. وكلُّ
رقمٍ جاء من الحلقة ٣ يُفحَص قبل أن يفهرس شيئاً — وقد أعادت النواة خطأً ولم تنهر.

**المكسب** أنّ برنامج المستخدم صار يتعامل مع النظام بأسماءٍ وأرقامٍ صغيرة، ولا
يعرف عن `inode` ولا عن الذاكرة التي تحتها شيئاً. وهذا هو التجريد وقد اكتمل.

## كيف تفعلها الأنظمة الحقيقية

Linux يضع بين الاسم والعقدة طبقةً لا نملكها: `dentry` — ذاكرةٌ مؤقّتةٌ لنتائج
البحث عن الأسماء. والسبب أنّ المسار `/usr/lib/x/y.so` بحثٌ في خمسة مجلّدات، ويتكرّر
آلافَ المرّات.

وعنده `superblock` لأن أنظمة الملفّات كثيرة، و`vfsmount` لأن شجرةً واحدةً تُركَّب
من عدّة أنظمة. **ونحن بلا مجلّداتٍ وبنظام ملفّاتٍ واحد**، فلا واحدةَ منها تشتري
شيئاً — وإضافتُها الآن بنيةٌ بلا حاجةٍ تقيسها.

| | نحن | Linux |
|---|---|---|
| الاسم إلى عقدة | بحثٌ خطّيٌّ في ثمانية | `dentry` مخزَّنة |
| أنظمة الملفّات | واحد | `superblock` لكلٍّ |
| الشجرة | مسطّحة | `mount` يركّب أشجاراً |
| واجهةُ العقدة | مؤشّرٌ واحد | `inode_operations` و`file_operations` |

## الفخاخ التصوّرية

| الفخّ | الصواب |
|---|---|
| «الوصف مؤشّرٌ إلى الملفّ» | فهرسٌ في جدولٍ يملكه النظام. وتزويرُه لا يخرج من جدول العملية |
| «موضعُ القراءة في الملفّ» | في **الفتحة**. وفتحتان على نفس الملفّ موضعان مستقلّان |
| «إغلاقُ الوصف يحذف الملفّ» | يُسقِط مرجعاً. والعقدة تبقى، وقد تبقى فتحاتٌ أخرى |
| «`read` تعيد ما طلبتَ أو خطأً» | تعيد **ما استطاعت**، وقد يكون أقلّ. والحلقةُ حول `read` ليست احتياطاً |
| «`read` تعيد صفراً عند الخطأ» | صفرٌ نهايةُ ملفّ. والخطأ سالب، والخلطُ بينهما يُسكِت الأخطاء |
| «الملفُّ شيءٌ على قرص» | تجريدٌ في الكيرنل. و`ramfs` بلا قرص، والفصل التالي يجعل جهازاً ملفّاً |

## Checkpoint

١. فتحتان على `motd` وقُرئ من إحداهما عشرةُ بايتات. كم يقرأ `read` التالي من
الأخرى، ولماذا؟
٢. لماذا يبدأ `proc_fd_set` من ٣؟ واشرح كيف تعمل `close(1); open("log")`.
٣. `read` أعادت `-9`. سمِّ الفحص الذي أنتجها، وقل أين يقع: في VFS أم في طبقة
الاستدعاء؟
٤. أضِف `dup(fd)`: ما الحقل الذي يتغيّر، وأي بنيةٍ **لا** تُنسَخ؟

## Artifact

| | |
|---|---|
| مخطّط | ثلاث طبقات: `fd` في جدول العملية ← `file` بموضعه ← `inode`، وسهمان يتقاطعان |
| تنفيذ | `vfs_open` و`vfs_read` و`vfs_close` وجدولُ الأوصاف |
| تجربةُ فشل | اسمٌ لا يوجد، ووصفٌ خارج الجدول — كلاهما رقمٌ سالب |
| أثرُ تنفيذ | `open("motd")` ← بحث ← فتحة ← فهرسٌ محلّيّ ← `read` ← `copy_to_user` |
| مقارنة | `dentry` و`superblock` و`mount`: ما يشتريه كلٌّ، ولماذا لا نحتاجه |

## التمرين

افتح `motd` مرّتين في نفس العملية، واقرأ عشرةَ بايتاتٍ من الأولى ثم عشرةً من
الثانية، واطبعهما. هل تكرّرت؟

ثم أضِف `sys_lseek` وأعد التجربة بقفزةٍ إلى الموضع صفر. أي حقلٍ عدّلتَ، وفي أي
بنية؟

ثم اجعل `MAX_FDS = 4` واطلب فتح ثلاثة ملفّات. أي خطأٍ عاد، وعند أي فتحة؟ وماذا
يقول ذلك عن حدود الجداول الثابتة في نواةٍ حقيقية؟

**الفصل التالي:** القراءة عندنا تعود فوراً — البيانات موجودةٌ أو لا. والأجهزة
الحقيقية تتأخّر، وبرنامجٌ ينتظرها في حلقةٍ يحرق نواةً بلا تقدّم.
