# الإقليم ١٣ — الذاكرة

> الإقليم ١٢ فتح الشجرة والتفويض: أين تُكتَب الحدود، ومن يُسمَح له بكتابتها.
> وهذا الإقليم يفتح أوّل مورد — وأشدَّها التباساً: **الذاكرة**.
>
> والالتباس كلُّه من أن «حدَّ الذاكرة» في الذهن رقمٌ يمنع، وفي النواة **أربعةُ
> ملفّاتٍ تتصرّف تصرّفاتٍ مختلفة**، ومنها ما لا يمنع شيئاً.

---

## الحدُّ ليس `ulimit`

**الاعتقاد، صريحاً:** إن حددتَ ذاكرة المجموعة بـ٦٤ ميجابايت، فطلبُ ٥١٢ يفشل.

البرنامج `programs/13-eat.c` يفصل الخطوتين عمداً — يخصّص أوّلاً، ثم يلمس صفحةً
صفحة:

<!-- part: 13-eat.c -->

```c
	want = atol(argv[1]) * MB;
	p = malloc(want);
	printf("malloc: %s\n", p ? "ok" : "NULL");
```

<!-- setup -->

```sh
gcc -O0 -o /tmp/eat programs/13-eat.c
mkdir -p /sys/fs/cgroup/mem
```

<!-- lab -->

```sh
echo 64M > /sys/fs/cgroup/mem/memory.max
echo 0   > /sys/fs/cgroup/mem/memory.swap.max
sh -c 'echo $$ > /sys/fs/cgroup/mem/cgroup.procs; exec /tmp/eat 512' 2>/dev/null
echo "exit: $?"
grep -e '^max ' -e oom_kill /sys/fs/cgroup/mem/memory.events
```

<!-- gate -->

```
malloc: ok
touched: 32M
exit: 137
max …
oom_kill 1
```

`malloc` لخمسمئة واثني عشر ميجابايت **نجح** تحت سقف أربعةٍ وستّين. ثم مات
البرنامج بـ`137` — أي `128 + 9`، وهي `SIGKILL`.

لأن `malloc` لا يأخذ ذاكرة؛ يأخذ **عنواناً**. والصفحة لا تُخصَّص حتى تُلمَس،
وعند اللمس يقع نداءُ خطأ الصفحة، وهناك — لا قبله — تُحاسَب المجموعة. فحدُّ
`memory.max` حدٌّ على **المقيم**، لا على المطلوب.

**والمكسب:** فحصُ قيمة `malloc` لا يحميك من هذا الموت أبداً، ولا يسبقه تحذير في
`errno`. الموت يأتي من الخارج، عند سطرٍ يكتب في مصفوفة.

> والعدّاد `max` في `memory.events` عدّ المرّات التي بلغت فيها المجموعة سقفها،
> و`oom_kill` عدّ القتلى. **دفترٌ لا إنذار**: يُقرأ بعد الحدث لا قبله.

---

## `max` تقتل، و`high` تخنق

الملفّ الثاني `memory.high`. وهو يُكتَب بنفس الصيغة، ويعني شيئاً مختلفاً
تماماً. اترك `max` بلا حدّ، وضع `high` عند اثنين وثلاثين، وأمهِله خمس ثوانٍ:

<!-- lab -->

```sh
mkdir -p /sys/fs/cgroup/hi
echo 32M > /sys/fs/cgroup/hi/memory.high
echo 0   > /sys/fs/cgroup/hi/memory.swap.max
timeout 5 sh -c 'echo $$ > /sys/fs/cgroup/hi/cgroup.procs; exec /tmp/eat 512' 2>/dev/null
echo "exit: $?"
grep -e '^high ' -e '^max ' -e oom_kill /sys/fs/cgroup/hi/memory.events
```

<!-- gate -->

```
malloc: ok
touched: 32M
exit: 124
high …
max 0
oom_kill 0
```

`124` هو رمز `timeout` حين ينتهي وقتُه — أي **أن البرنامج ما يزال حيّاً بعد خمس
ثوانٍ** وقد لمس اثنين وثلاثين ميجابايت فقط. و`oom_kill` صفر، و`max` صفر: لم
يُقتَل أحد، ولم يُبلَغ سقف.

فـ`high` ليست سقفاً بل **نقطة ضغط**: كلَّما تجاوزتْها المجموعة أوقفت النواةُ
العمليةَ الطالبة وأجبرتها على الاسترجاع قبل أن تُكمل. والعدّاد `high` يعدّ تلك
الوقفات.

**والمكسب:** الاثنان يُستعملان معاً لا بديلاً: `high` تجعل التجاوز **بطيئاً
ومرئيّاً** في `memory.events` قبل أن يصير قاتلاً، و`max` تجعله **نهائيّاً**.
ومن يضع `max` وحدها لا يرى شيئاً حتى يقرأ `137` في السجلّ.

## ما يكتبه `-m` بالضبط: مفتاحان لا مفتاح

الآن ارجع إلى الأداة. `docker run -m 64m` سطرٌ تكتبه كل يوم. **فكم ملفّاً
يكتب؟**

<!-- host -->

```sh
show() {
	docker rm -f m13 > /dev/null 2>&1
	docker run -d --name m13 "$@" alpine:3.20 sleep 60 > /dev/null
	printf '%-30s %s\n' "$*" \
		"$(docker exec m13 sh -c 'cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.swap.max' | tr '\n' ' ')"
}
show -m 64m
show -m 64m --memory-swap 64m
show -m 64m --memory-swap 128m
show -m 64m --memory-swap -1
docker rm -f m13 > /dev/null
```

<!-- gate @impl -->

```
-m 64m                         67108864 67108864
-m 64m --memory-swap 64m       67108864 0
-m 64m --memory-swap 128m      67108864 67108864
-m 64m --memory-swap -1        67108864 max
```

اقرأ العمودين: الأوّل `memory.max` وهو ٦٤ ميجابايت في الأربعة كلِّها. والثاني
`memory.swap.max`، وهو الذي يتحرّك.

و`--memory-swap` **مجموعٌ لا حصّة**: تكتب فيه `الذاكرة + التبديل`، فتطرح الأداة
منه `-m` وتكتب الباقي في `memory.swap.max`. ولذلك `128m` تعني تبديلاً بـ٦٤،
و`64m` تعني **صفر تبديل**، و`-1` تعني بلا حدّ.

**والسطر الأوّل هو المفاجأة:** `-m 64m` وحدها — بلا أي عَلَمٍ آخر — تمنح حاويتك
٦٤ ميجابايت من التبديل فوق الذاكرة. فحدُّها الفعليّ ١٢٨ لا ٦٤:

<!-- host -->

```sh
docker run --rm -m 64m --memory-swap 64m --tmpfs /t:size=256m alpine:3.20 \
	sh -c 'dd if=/dev/zero of=/t/x bs=1M count=100 2>/dev/null && echo survived'
echo "swap 0  -> exit $?"
docker run --rm -m 64m --tmpfs /t:size=256m alpine:3.20 \
	sh -c 'dd if=/dev/zero of=/t/x bs=1M count=100 2>/dev/null && echo survived'
echo "swap 64 -> exit $?"
```

<!-- out @distro -->

```
swap 0  -> exit 137
survived
swap 64 -> exit 0
```

مئةُ ميجابايت، وأمرانِ يختلفان في عَلَمٍ واحد: أحدهما يموت والآخر ينجو.

**والمكسب:** «وضعتُ `-m` ومع ذلك أكلت الحاوية أكثر» ليس خطأً في الحدّ. هو الحدّ
يعمل كما كُتب. ومن أراد سقفاً واحداً صلباً فليكتب `--memory-swap` مساوياً لـ`-m`.

> واللوحة الأخيرة `@distro`: السطر الناجي يفترض تبديلاً عند نواتك. ومن لا تبديل
> عنده كان الحدّان عنده واحداً منذ البداية — وهو ما يقوله الملفّان أعلاه، لا ما
> يقوله هذا التشغيل.

## من يختاره القاتل

حين يقع القتل، من يموت؟ في cgroup v2 الجواب **ملفٌّ ثالث**. ضع ثلاث عملياتٍ
نائمة ومعها آكلَ ذاكرة، وبدّل الملفّ وحده:

<!-- lab -->

```sh
for g in 0 1; do
	rmdir /sys/fs/cgroup/og 2>/dev/null; mkdir -p /sys/fs/cgroup/og
	echo 64M > /sys/fs/cgroup/og/memory.max
	echo 0   > /sys/fs/cgroup/og/memory.swap.max
	echo $g  > /sys/fs/cgroup/og/memory.oom.group
	for i in 1 2 3; do
		sh -c 'echo $$ > /sys/fs/cgroup/og/cgroup.procs; exec sleep 60' \
			< /dev/null > /dev/null 2>&1 &
	done
	sleep 1
	before=$(wc -l < /sys/fs/cgroup/og/cgroup.procs)
	sh -c 'echo $$ > /sys/fs/cgroup/og/cgroup.procs; exec /tmp/eat 512' > /dev/null 2>&1
	sleep 1
	echo "oom.group=$g : before=$before after=$(wc -l < /sys/fs/cgroup/og/cgroup.procs)"
	kill %1 %2 %3 2>/dev/null; wait 2>/dev/null
done
```

<!-- out -->

```
oom.group=0 : before=3 after=3
oom.group=1 : before=3 after=0
```

بـ`0` مات الآكل وحده وبقي جيرانه الثلاثة. وبـ`1` ماتت المجموعة كلُّها — والنائمون
لم يطلبوا بايتاً.

**والمكسب عمليّ ومرّ:** الافتراض عند الأداة `0`. فحاويتك التي تشغّل مشرفاً
وابنَه لا تموت كاملةً حين ينفجر الابن؛ يموت الابن، **ويبقى المشرف حيّاً بلا
عمل**. والحاوية «تعمل» في `docker ps` وهي جثّة. ومن أراد أن يموت الكلُّ معاً
فليكتب `1` بنفسه.

## الصفحة المشتركة تُحسَب لمن؟

المحاسبة على الصفحة لا على العملية. **فماذا لو استعملت مجموعتان الصفحةَ نفسها؟**

<!-- lab -->

```sh
rmdir /sys/fs/cgroup/a /sys/fs/cgroup/b 2>/dev/null
mkdir -p /sys/fs/cgroup/a /sys/fs/cgroup/b
umount /mnt 2>/dev/null; mount -t tmpfs -o size=256m t /mnt
mb() { echo "$(( $(cat /sys/fs/cgroup/$1/memory.current) / 1048576 ))M"; }
sh -c 'echo $$ > /sys/fs/cgroup/a/cgroup.procs
	exec dd if=/dev/zero of=/mnt/shared bs=1M count=64' 2>/dev/null
echo "after a wrote : a=$(mb a)  b=$(mb b)"
sh -c 'echo $$ > /sys/fs/cgroup/b/cgroup.procs; exec cat /mnt/shared' > /dev/null
echo "after b read  : a=$(mb a)  b=$(mb b)"
echo "procs in a    : $(wc -l < /sys/fs/cgroup/a/cgroup.procs)"
```

<!-- out -->

```
after a wrote : a=64M  b=0M
after b read  : a=64M  b=0M
procs in a    : 0
```

`b` قرأت أربعةً وستّين ميجابايت وحُوسبت بصفر. لأن **من يلمس الصفحة أوّلاً يدفع
ثمنها**، ومن يأتي بعده يجدها موجودةً فلا يُخصَّص له شيء.

والسطر الأخير أقسى: في `a` **صفر عمليات**، وعليها أربعةٌ وستّون ميجابايت. الحساب
معلَّقٌ على المجموعة لا على ساكنيها، ويبقى ما بقيت الصفحات.

**والمكسب:** حين تشترك حاوياتك في `tmpfs` أو في ملفّاتٍ مجبولة (الإقليم ١١)،
فحدُّ الأولى يقتل الأولى بسبب صفحاتٍ تستعملها الثانية. والرقم في `memory.current`
لا يجيب «كم تستعمل هذه الحاوية»، بل «كم دفعت هذه الحاوية».

## والحاوية لا تعرف حدَّها

<!-- host -->

```sh
docker run --rm -m 64m alpine:3.20 sh -c '
	grep MemTotal /proc/meminfo
	echo "memory.max : $(cat /sys/fs/cgroup/memory.max)"'
```

<!-- out @machine -->

```
MemTotal:        … kB
memory.max : 67108864
```

`MemTotal` هو ذاكرة النواة كلَّها، لا حدُّ الحاوية. والسبب من الإقليم الأوّل:
**لا يوجد نطاقٌ للذاكرة.** النطاقات تعزل ما ترى (الأقاليم ٠٢–٠٧)، والـcgroups
تحدّ ما تأخذ — والملفّ `/proc/meminfo` يقع في الأولى لا الثانية، فبقي كما هو.

**والمكسب:** كل برنامجٍ يحجم نفسه من `/proc/meminfo` سيحجم نفسه على ذاكرة
**جهازك كلِّه** داخل حاويةٍ بـ٦٤ ميجابايت، ثم يُقتَل بـ`137` بلا رسالة. ولذلك
تنصّ لغاتٌ حديثة على قراءة `memory.max` مباشرةً — وهي تقرأ الملفّ الذي رأيتَه
أعلاه بعينه.

## التمرين — اثنان، ولا حلول

**١.** أعد تجربة `high` مع `memory.max` مضبوطةً أيضاً عند ١٢٨ ميجابايت.
**معيار القبول:** قراءةٌ لـ`memory.events` تقول أيُّ العدّادين تحرّك وأيُّهما لم
يتحرّك، وسطرٌ يفسّر لماذا لا يكفي أحدهما وحده لتشخيص «الحاوية بطيئة».

**٢ (الأصعب).** اجعل مجموعتين تتقاسمان ملفّاً في `tmpfs` كما فوق، ثم **اقتل
مجموعة `a` واحذفها** (`rmdir`) بينما `b` تقرأ الملفّ. **معيار القبول:** جوابٌ عن
أين ذهبت الأربعة والستّون ميجابايت بعد `rmdir` — مسنداً إلى `memory.current`
مقروءاً، لا إلى تخمين — وسطرٌ يقول ماذا يعني ذلك لحاويةٍ تُحذَف وأخرى ما زالت
تقرأ ما كتبته.

## الخلاصة — أين نحن في الشجرة

| ما عرفتَه | العقدة التي يتعلّق بها |
|---|---|
| الحدُّ على المقيم لا على المطلوب | فحصُ `malloc` لا يحميك · والموت يأتي عند كتابةٍ في مصفوفة |
| `max` سقفٌ يقتل، و`high` ضغطٌ يُبطئ | استعملهما معاً: `high` ليُرى، و`max` ليُنهي |
| `-m` وحدها تمنح تبديلاً بقدرها | من أراد سقفاً صلباً كتب `--memory-swap` مساوياً |
| `memory.oom.group` افتراضُه صفر | حاويةٌ «تعمل» وقد مات فيها ما يعمل — والملفّ يحسمها |
| من يلمس الصفحة أوّلاً يدفع | `memory.current` يقول كم دفعت، لا كم تستعمل |
| `/proc/meminfo` لا يعرف الحدّ | لا نطاق للذاكرة · فاقرأ `memory.max` لا `MemTotal` |

> **البذرة:** الذاكرة موردٌ **تملكه أو لا تملكه**، ولذلك كان جوابها القتل. أمّا
> المعالج فمَوردُ **وقت**: لا يمكن أن تُقتَل لأنك أردت أكثر منه، ولا أن تُمنَع —
> يمكن فقط أن **تنتظر**.
>
> والانتظار لا يظهر في `top` ولا في متوسّط الحِمل. الإقليم القادم يقيسه حيث
> يظهر.
