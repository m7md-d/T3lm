# الإقليم ٠٧ — التقاسم: هنا يُدفَن نموذج الصندوق

> ستّة أقاليم، وكل واحدٍ منها قال الشيء نفسه من زاوية: النطاق **لا يُملَك مع
> «الحاوية» ككتلة**؛ يُملَك وحده، ويُشارَك وحده. هذا الإقليم يجمع الأدلّة
> كلَّها في تجربةٍ واحدة تكشف أن «الحاوية» **ليست وحدة عزلٍ من النواة** — هي
> **اسمٌ لتركيبةٍ معيّنة** من سبعة اختيارات مستقلّة، وDocker اختار واحدةً منها
> افتراضياً. غيّرها، وتحصل على شيءٍ آخر له اسمه الخاصّ: **pod**.

---

## `--net=host`: حاويةٌ بلا نطاق شبكة

<!-- host-setup -->

```sh
docker rm -f t3lm_a 2>/dev/null; true
```

<!-- host -->

```sh
echo "معزولة: $(docker run --rm alpine:3.20 sh -c 'ip -o addr show | wc -l') سطراً"
echo "host:    $(docker run --rm --net=host alpine:3.20 sh -c 'ip -o addr show | wc -l') سطراً"
```

<!-- out @impl -->

```
معزولة: 3 سطراً
host:    … سطراً
```

`--net=host` لا تعني «شبكةً أسرع» — تعني **لا نطاق شبكة جديد إطلاقاً**. العملية
ترى كل بطاقات الآلة التي يعمل عليها المحرّك: الجسر، والحاويات الأخرى، وأي
واجهةٍ حقيقية. وهذا بالضبط الثمن الذي حذّر منه الجدول في الفصل صفر: صفٌّ واحدٌ
يُسقَط، وتُفتَح شبكة المضيف كاملةً أمام كل ما يعمل بداخلها.

## حاويتان، شبكةٌ واحدة

<!-- host-setup -->

```sh
docker rm -f t3lm_pod_main t3lm_pod_side 2>/dev/null; true
docker run -d --name t3lm_pod_main --ipc shareable alpine:3.20 sleep 300 >/dev/null
docker run -d --name t3lm_pod_side --network container:t3lm_pod_main \
	--ipc container:t3lm_pod_main alpine:3.20 sleep 300 >/dev/null
```

<!-- host -->

```sh
echo "main: $(docker exec t3lm_pod_main sh -c "ip -o -4 addr | awk '{print \$4}'" | tail -1)"
echo "side: $(docker exec t3lm_pod_side sh -c "ip -o -4 addr | awk '{print \$4}'" | tail -1)"
```

<!-- out @machine -->

```
main: …
side: …
```

**نفس العنوان حرفياً.** لم تُنشئ Docker شبكةً جديدة للثانية؛ أعطتها **نفس
نطاق** الشبكة الذي تملكه الأولى — العَلَم `--network container:اسم` هو
`CLONE_NEWNET` مرفوضاً بدل مطلوب: **لا تصنع لي واحداً، أعطني الذي يملكه هذا**.

<!-- host -->

```sh
docker run --rm --network container:t3lm_pod_main alpine:3.20 sh -c 'echo | nc -w1 127.0.0.1 9999' &
sleep 0.3
docker exec t3lm_pod_main sh -c 'echo hi | nc -l -p 9999 -w2'
wait
```

<!-- runs -->

```
hi
```

**تواصلٌ عبر `127.0.0.1` بين حاويتين مختلفتين تماماً.** هذا مستحيلٌ إن كانتا
منعزلتين بنطاقَي شبكةٍ منفصلين — و`localhost` بينهما يعمل لأنه **نفس النطاق
حرفياً**، لا خدعة توجيه.

## ومع ذلك: عمليتان، لا واحدة

> **توقّع قبل أن تشغّل:** الشبكة مشتركة، وIPC مشترك. فهل ترى إحدى الحاويتين
> عمليات الأخرى؟

<!-- host -->

```sh
#! rc: 1
docker exec t3lm_pod_main ps -ef | sed -n 2p
docker exec t3lm_pod_side ps -ef | sed -n 2p
docker exec t3lm_pod_main sh -c 'echo وحدي > /tmp/only-main'
docker exec t3lm_pod_side sh -c 'cat /tmp/only-main'
```

<!-- gate -->

```
    1 root      0:00 sleep 300
    1 root      0:00 sleep 300
cat: can't open '/tmp/only-main': No such file or directory
```

**كلتاهما ترى نفسها برقم ١** — فضاءا عمليات منفصلان تماماً، مثل أي حاويتين لا
علاقة بينهما. والملفّ الذي كتبته الأولى **لا وجود له عند الثانية** — شجرتا
ملفّاتٍ منفصلتان أيضاً. **شاركتا نطاقين من سبعة، وبقي الخمسة الباقون معزولين
كما كانا.**

<!-- host-setup -->

```sh
docker rm -f t3lm_pod_main t3lm_pod_side >/dev/null
```

## وهذا بالضبط ما تسمّيه Kubernetes «pod»

لا بدائية جديدة في النواة. **الـpod تركيبةٌ بعينها من نفس السبعة** التي
رأيتَها منذ الإقليم ٠٢: شبكةٌ وIPC مشتركان، وكل شيءٍ آخر — العمليات، والملفّات،
والمستخدمون — منفصل. حاويات الـpod الواحد تتواصل بـ`localhost` بالضبط لأنها
**بنفس آلية `--network container:`**، لا لأن Kubernetes اخترع شيئاً.

```
  «حاوية» عادية                          «pod»
  ───────────────                        ─────

  mnt   خاصّ                              mnt   خاصّ  (لكلٍّ)
  pid   خاصّ                              pid   خاصّ  (لكلٍّ)
  net   خاصّ          ────── تبديل ──────► net   مشترَك
  ipc   خاصّ          ────── تبديل ──────► ipc   مشترَك
  uts   خاصّ                              uts   خاصّ  (لكلٍّ)
  user  خاصّ                              user   خاصّ  (لكلٍّ)
  time  (غير مفعَّل)                      time  (غير مفعَّل)
```

**سبعة مفاتيح مستقلّة، لا مفتاحٌ واحد اسمه «حاوية».** وما يفعله Docker حين
تكتب `docker run` هو تعيين **افتراضيّ واحد لكل السبعة**: كلٌّ منها جديدٌ خاصّ.
وما تفعله Kubernetes عند إنشاء pod هو **افتراضيٌّ آخر**: نطاقا الشبكة وIPC
يُنشآن مرّةً واحدة (بحاوية «هيكلية» صامتة تحمل «pause») ثم تُشارَكهما بقيّة
حاويات الـpod، بينما الخمسة الأخرى تبقى لكلٍّ وحدها.

**والقاعدة العامّة التي تحكم كل هذا**: أي تركيبةٍ من السبعة **قابلةٌ للاختيار**،
لا التركيبتان المسمّاتان فقط. مطوّر أدوات الحاويات حرٌّ أن يخترع تركيبةً ثالثة
— وهذا بالضبط ما فعله Podman حين اختار افتراضاً مختلفاً لنطاق المستخدمين
(الإقليم ٢٩).

---

## التمرين — واحد، ولا حلّ

اصنع **تركيبةً ثالثة** لم تَرِها Docker ولا Kubernetes بالاسم: شبكةٌ مشتركة،
IPC **منفصل**، وuts مشترك (فكلتا الحاويتين تريان نفس اسم المضيف). **معيار
القبول:** ثلاث لوحاتٍ تثبت الحالات الثلاث من نفس زوج الحاويات — بلا تخمين، من
تشغيلٍ حقيقيّ.

---

## الخلاصة — أين نحن في الشجرة

هذا يختم الحزمة الثانية كلَّها. ما تراكم عبر سبعة أقاليم:

| الإقليم | ما أثبته | وأين استُعمل هنا |
|---|---|---|
| ٠٢ | النطاق كائنٌ مستقلّ، يُملَك ويُمسَك | الأساس الذي بُني عليه `--network container:` |
| ٠٣ | الشجرة والانتشار منفصلان عن الهوية | لماذا كل حاويةٍ لها `/tmp` خاصّ رغم الشبكة المشتركة |
| ٠٤ | الرقم موضعٌ لا صفة | فسّر ظهور `PID 1` مرّتين في التجربة الأخيرة |
| ٠٥ | نطاقاتٌ صغيرة، تُنزَع منفردة | `uts` بقي خاصّاً في التمرين رغم مشاركة الباقي |
| ٠٦ | القدرة تتبع من يملك المورد | لماذا مشاركة نطاقٍ لا تمنح صلاحيةً على غيره |
| ٠٧ | «الحاوية» و«pod» **اسمان لتركيبتين**، لا نوعان | هذا الإقليم |

**والنتيجة النهائية للحزمة كلَّها**: نموذج «الصندوق الواحد المغلق» — الذي بدأ
هذا المنهج بهدمه في الفصل صفر — **لم يبقَ منه شيء**. سبعة مفاتيح، كل واحدٍ
يُقلَب وحده، وكل تركيبةٍ منها اسمٌ يخترعه أحدهم لاحقاً ليُسمّي ما اختاره.

> **البذرة:** رأيتَ ماذا تُتيح النطاقات — من تُشارِك، ومن تنفرد. لم تَرَ بعد
> **كم تأخذ** كل عمليةٍ ممّا هو متاح: أن `sleep` واحدةً تستطيع أن تحجز الذاكرة
> كلَّها، أو أن تُنجب عملياتٍ حتى يسقط النظام. تلك حزمةٌ مختلفة تماماً —
> ليست عن الرؤية، بل عن **الحدّ**.
>
> الإقليم القادم يفتحها: `cgroup v2` من الصفر.
