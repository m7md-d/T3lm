# الإقليم ٠٩ — الصورة بنيةَ بيانات

> الإقليم ٠٨ ركّب شجرةً من ثلاثة مجلّداتٍ صنعتَها بيدك. و`docker pull` لا يجد
> مجلّدات: يجد **أرشيفاتٍ مضغوطة، اسمُ كلٍّ منها بصمةُ محتواه**، وخريطةً تقول
> أيّها فوق أيّ وما الذي يُنفَّذ بعد التركيب.
>
> هذا الإقليم يفكّ تلك الخريطة حتى القاع، وينتهي عند تركيبٍ **يفشل** — والفشل
> هو الذي يكشف الوظيفةَ التي تؤدّيها الأداة ولا تذكرها.

---

## أوّلاً: تُخرَج من الخدمة أرشيفاً

الصورة عند الخدمة ليست ملفّاً تفتحه؛ هي مدخلٌ في مخزنٍ داخليّ. و`docker save`
يجعلها ملفّاً واحداً بالشكل الذي تعرفه المواصفة — فيصير ما بداخلها قابلاً للقراءة
بأدوات عاديّة:

<!-- host -->

```sh
mkdir -p .lab/img && cd .lab/img
cat > Dockerfile <<'EOF'
FROM alpine:3.20@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc
RUN echo one > /one.txt
RUN rm /one.txt && echo two > /two.txt
ENV GREETING=salam
CMD ["/bin/sh", "-c", "echo $GREETING"]
EOF
docker build -q --provenance=false -t demo:1 . > /dev/null 2>&1
docker save demo:1 -o ../demo.tar
tar tf ../demo.tar | sed 's|blobs/sha256/[0-9a-f].*|blobs/sha256/<digest>|' | sort | uniq -c
```

<!-- out @impl -->

```
   1 blobs/
   1 blobs/sha256/
   5 blobs/sha256/<digest>
   1 index.json
   1 manifest.json
   1 oci-layout
```

خمسةُ ملفّاتٍ مسمّاةٍ ببصماتها، وثلاثةٌ باسمٍ مقروء: `oci-layout` يقول إصدار
الشكل، و`index.json` هو **المدخل الوحيد** الذي تبدأ منه القراءة، و`manifest.json`
مجاملةٌ للشكل القديم يتجاوزها كلُّ ما يأتي بعده هنا.

**والمكسب:** خمسُ بصماتٍ لصورةٍ فيها ثلاث طبقات. فالفائض اثنان — وستعرف في
الفقرات القادمة من هما، ولمَ لم يكن العدد ثلاثة.

> **`--provenance=false` مقصود.** بدونه يضيف البنّاء إلى الأرشيف شهادةَ منشأ
> بمعمارية `unknown` — وهي موضوع الإقليم ٣٢، وهنا ضجيج. وشكلُ الأرشيف نفسه
> موسومٌ `@impl`: مخزن الصور المبنيّ على containerd يكتب `blobs/sha256/` كما
> تراه هنا، والمخزن القديم يكتب شكلاً آخر بنفس المحتوى.
>
> و`.lab/` عندك هو `/lab/work` داخل المختبر — كما في الإقليم ٠١.

## الاسم بصمةُ المحتوى

هذا ادّعاءٌ يُفحَص لا يُصدَّق: **اسم كل ملفٍّ في `blobs/sha256/` هو `sha256` لمحتوى
ذلك الملفّ بعينه.**

<!-- lab -->

```sh
cd work && rm -rf img && mkdir img && tar xf demo.tar -C img
cd img/blobs/sha256
for f in *; do
	if [ "$f" = "$(sha256sum < "$f" | cut -d' ' -f1)" ]
	then echo "name == sha256(content)"
	else echo "MISMATCH: $f"
	fi
done
ls | head -1
```

<!-- out -->

```
name == sha256(content)
name == sha256(content)
name == sha256(content)
name == sha256(content)
name == sha256(content)
…
```

خمسةٌ من خمسة. والسطر الأخير أحدُ تلك الأسماء كما هو: أربعةٌ وستّون محرفاً من
`0-9a-f`، لا امتداد ولا وسم ولا تاريخ.

**والمكسب أربعة، كلُّها نتيجةٌ واحدة لا أربعُ ميزات صُمِّمت:** الصورة لا تُعدَّل
لأن تعديل بايتٍ يغيّر الاسم فيصير شيئاً آخر · والفساد يُكتشَف بحسبةٍ لا بثقة ·
والمحتوى المتطابق **اسمه واحد** فيُخزَّن مرّة · ولذلك يستطيع `pull` أن يتخطّى ما
عنده قبل أن ينزّله.

## بصمةٌ واحدة لصورتين

النتيجة الثالثة أعلاه ادّعاءٌ عن التخزين، فتُقاس. ابنِ صورةً ثانية من الأساس
نفسه، واحفظ الاثنتين في أرشيفٍ واحد:

<!-- host-setup -->

```sh
cd .lab/img
cat > Dockerfile.b <<'EOF'
FROM alpine:3.20@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc
RUN echo other > /other.txt
EOF
docker build -q --provenance=false -f Dockerfile.b -t demo:b . > /dev/null 2>&1
docker save demo:1 demo:b -o ../both.tar
docker image inspect demo:1 --format '{{.Id}}' > ../image-id
```

<!-- lab -->

```sh
cd work && rm -rf both && mkdir both && tar xf both.tar -C both && cd both
echo "images: $(jq '.manifests | length' index.json)"
echo "blobs : $(ls blobs/sha256 | wc -l)"
A=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
B=blobs/sha256/$(jq -r '.manifests[1].digest' index.json | cut -d: -f2)
[ "$(jq -r '.layers[0].digest' $A)" = "$(jq -r '.layers[0].digest' $B)" ] \
	&& echo "first layer: one blob, shared" || echo "first layer: two blobs"
```

<!-- out -->

```
images: 2
blobs : 8
first layer: one blob, shared
```

صورتان، وأربع طبقاتٍ منطقيّة (ثلاثٌ وواحدة)، ومع ذلك ثمانِ بصماتٍ لا تسع: طبقة
الأساس **مذكورةٌ مرّتين ومخزَّنةٌ مرّة**.

**والمكسب:** ما تراه في `docker images` من أحجامٍ متجاورة ليس ما على قرصك. وهذا
لا يحتاج خوارزمية تخزينٍ ذكيّة — يكفي أن يكون الاسمُ البصمةَ، فيصير التطابق
تطابقَ أسماء.

## المشي على الرسم: من `index.json` إلى الأمر الذي سيُنفَّذ

الملفّات الخمسة رسمٌ مُوجَّه، وكلُّ حافةٍ فيه بصمة. امشِ عليه:

<!-- lab -->

```sh
cd work/img
M=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
C=blobs/sha256/$(jq -r '.config.digest' $M | cut -d: -f2)
echo "index.json  -> $(jq -r '.manifests[0].mediaType' index.json)"
echo "  manifest  -> config:   $(jq -r '.config.mediaType' $M)"
echo "               layers:   $(jq '.layers | length' $M) x $(jq -r '.layers[0].mediaType' $M)"
echo "  config    -> Cmd:      $(jq -c '.config.Cmd' $C)"
echo "               Env[1]:   $(jq -r '.config.Env[1]' $C)"
echo "               diff_ids: $(jq '.rootfs.diff_ids | length' $C)"
```

<!-- out -->

```
index.json  -> application/vnd.oci.image.manifest.v1+json
  manifest  -> config:   application/vnd.oci.image.config.v1+json
               layers:   3 x application/vnd.oci.image.layer.v1.tar+gzip
  config    -> Cmd:      ["/bin/sh","-c","echo $GREETING"]
               Env[1]:   GREETING=salam
               diff_ids: 3
```

فالفائضان اللذان سألتَ عنهما: **manifest** يقول ما تتركّب منه الصورة، و**config**
يقول ماذا تفعل حين تعمل. وهنا انتهى السؤال «أين يسكن `CMD`؟»: يسكن ملفَّ JSON
اسمُه بصمته، لا الطبقات ولا الشجرة.

**والمكسب:** لا شيء في الصورة يُقرأ إلا بالمشي من `index.json`. فمن يملك بصمة
`index` يملك تحديد كل بايتٍ بعدها — وهذا هو بالضبط ما يوقَّع عليه في الإقليم ٣٢،
وما يُسحَب بصمةً بصمة في الإقليم ٣٠.

## بصمتان لطبقةٍ واحدة

الـmanifest ذكر ثلاث طبقاتٍ ببصماتها. والـconfig ذكر ثلاثة `diff_ids`. **فهل هما
القائمة نفسها؟**

<!-- lab -->

```sh
cd work/img
M=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
C=blobs/sha256/$(jq -r '.config.digest' $M | cut -d: -f2)
D=$(jq -r '.layers[1].digest' $M)
ID=$(jq -r '.rootfs.diff_ids[1]' $C)
U="sha256:$(gunzip -c blobs/sha256/${D#sha256:} | sha256sum | cut -d' ' -f1)"
[ "$D" = "$ID" ] && echo "digest == diff_id" || echo "digest != diff_id"
[ "$U" = "$ID" ] && echo "sha256(gunzip layer) == diff_id" || echo "sha256(gunzip layer) != diff_id"
```

<!-- gate -->

```
digest != diff_id
sha256(gunzip layer) == diff_id
```

بصمتان لشيءٍ واحد لأنهما تجيبان سؤالين مختلفين. **`digest`** بصمةُ البايتات
المضغوطة كما تُنقَل على الشبكة وكما تُخزَّن، فهي التي تتحقّق منها عند التنزيل.
و**`diff_id`** بصمةُ الأرشيف بعد فكِّ الضغط — أي بصمةُ **التغيير نفسه**، مستقلّةً
عن أداة الضغط وإعداداتها.

**والمكسب:** أعِد ضغط الطبقة بمستوًى مختلف فيتغيّر `digest` ولا يتغيّر `diff_id`.
ولذلك سُلسِلت الخبيئة على `diff_id` لا على `digest` — وإلا لسقطت الخبيئة كلَّما
غيّر البنّاءُ ضاغطه. وهذا أوّل ما ستقيسه في الإقليم ٣١.

## و«IMAGE ID» ليست في المواصفة أصلاً

<!-- lab -->

```sh
cd work/img
ID=$(cat ../image-id)
M=$(jq -r '.manifests[0].digest' index.json)
C=$(jq -r '.config.digest' blobs/sha256/${M#sha256:})
case "$ID" in
	"$M") echo "IMAGE ID = manifest digest" ;;
	"$C") echo "IMAGE ID = config digest" ;;
	*)    echo "IMAGE ID = neither" ;;
esac
```

<!-- out @impl -->

```
IMAGE ID = manifest digest
```

العمود الذي تقرأه كلَّ يوم في `docker images` ليس حقلاً في أي ملفٍّ فككتَه للتوّ:
**المواصفة لا تعرف شيئاً اسمه «معرِّف صورة».** فالأداة تختار بصمةً من الرسم
وتسمّيها كذلك — وهذا المحرّك اختار بصمة الـmanifest، والمخزن القديم كان يختار
بصمة الـconfig، فيختلف «المعرِّف» للصورة الواحدة بلا أن يتغيّر فيها بايت.

**والمكسب:** حين تريد أن تقول «هذه الصورة بعينها» فقُلها بـ`repo@sha256:…`.
وأمّا `IMAGE ID` فاسمٌ محلّيّ عند أداتك، لا يُتراسَل به ولا يُقارَن بين جهازين.

## «كل سطرٍ في Dockerfile طبقة» — لا

الـDockerfile أعلاه فيه خمسة أسطر بعد `FROM`. والقاعدة الشائعة تقول: كل تعليمةٍ
طبقة، فلتقلّل الأسطر لتقلّل الطبقات. **فكم طبقةً تتوقّع؟**

<!-- lab -->

```sh
cd work/img
M=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
C=blobs/sha256/$(jq -r '.config.digest' $M | cut -d: -f2)
echo "history : $(jq '.history | length' $C)"
echo "diff_ids: $(jq '.rootfs.diff_ids | length' $C)"
echo
jq -r '.history[] | "\(if .empty_layer then "-" else "L" end)  \(.created_by)"' $C
```

<!-- gate -->

```
history : 6
diff_ids: 3

L  ADD alpine-minirootfs-… / # buildkit
-  CMD ["/bin/sh"]
L  RUN /bin/sh -c echo one > /one.txt # buildkit
L  RUN /bin/sh -c rm /one.txt && echo two > /two.txt # buildkit
-  ENV GREETING=salam
-  CMD ["/bin/sh" "-c" "echo $GREETING"]
```

ستّةُ أسطرٍ في السجلّ، وثلاثُ طبقاتٍ فقط. والفرق ليس تحسيناً ذكيّاً من البنّاء،
بل تقسيمٌ في بنية الصورة نفسها:

```
تعليمة في Dockerfile              history[]          rootfs.diff_ids[]
────────────────────────          ──────────         ─────────────────
FROM alpine ──────────────────►   [0] ADD  ──────►   [0] sha256:…
  (CMD موروثة من الأساس) ─────►   [1] CMD  ──┐
RUN echo one > /one.txt ──────►   [2] RUN  ──────►   [1] sha256:…
RUN rm /one.txt && … ─────────►   [3] RUN  ──────►   [2] sha256:…
ENV GREETING=salam ───────────►   [4] ENV  ──┤
CMD ["/bin/sh","-c",…] ───────►   [5] CMD  ──┘
                                             │
                                             └──►  empty_layer: true
                                                   ‏لا بصمة، ولا أرشيف،
                                                   ‏ولا بايت على القرص
```

**فالطبقةُ نتيجةُ تغييرٍ في نظام الملفّات، لا نتيجةُ سطر.** و`ENV` و`CMD`
و`LABEL` و`WORKDIR` و`ENTRYPOINT` و`USER` تُغيّر ملفَّ الـconfig وحده، فتُسجَّل
في `history` بعلامة `empty_layer: true` وتنتهي.

**والمكسب عمليّ:** دمجُ `ENV` مع `RUN` في سطرٍ واحد «لتقليل الطبقات» لا يقلّل
شيئاً. والذي يقلّل هو دمج ما **يكتب على القرص**، وهو `RUN` و`COPY` و`ADD` وحدها.

## الطبقة أرشيف، والحذف اسمٌ فيه

بقي أن تفتح الطبقات نفسها. وهنا يعود سطرٌ من الإقليم ٠٨:

<!-- lab -->

```sh
cd work/img
M=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
set -- $(jq -r '.layers[].digest' $M | cut -d: -f2)
echo "layer 0: $(tar tf blobs/sha256/$1 | wc -l) entries"
echo "layer 1:"; tar tvf blobs/sha256/$2 | awk '{print "  " $1, $NF}'
echo "layer 2:"; tar tvf blobs/sha256/$3 | awk '{print "  " $1, $NF}'
```

<!-- out -->

```
layer 0: … entries
layer 1:
  -rw-r--r-- one.txt
layer 2:
  ---------- .wh.one.txt
  -rw-r--r-- two.txt
```

الطبقة الأولى شجرةُ الأساس كاملة. والثانية أرشيفٌ فيه ملفٌّ واحد — **الفرق فقط،
لا الشجرة**. والثالثة فيها `two.txt`، ومعه ملفٌّ اسمه `.wh.one.txt`: صفرُ بايت،
وأذوناتٌ صفر.

قارِنه بالإقليم ٠٨: هناك كان الحذف **جهازاً وهميّاً `c 0,0`** في `upper`. وهنا
هو **اسمٌ يبدأ بـ`.wh.`** داخل أرشيف. لغتان مختلفتان للشيء نفسه: الأولى لغةُ
نظام الملفّات وقت التشغيل، والثانية لغةُ صيغة النقل — لأن `tar` لا يعرف كيف
يحمل جهازاً وهميّاً بلا معنًى على القرص المقابل، ولأن `overlayfs` لا يقرأ
أسماء الملفّات ليستنتج منها نيّة.

**والمكسب:** بين الأرشيف وشجرة الجبل مترجِمٌ لا بدّ منه. وأنت لم تشغّله بعد.

## الوسم مؤشّر: صورةٌ واحدة، ثماني معماريات

`index.json` عندك أشار إلى manifest واحد لأنك بنيتَ لمعماريتك وحدها. أمّا ما في
السجلّات فيُشير إلى عدّة:

<!-- host-setup -->

```sh
docker manifest inspect \
	alpine@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc \
	> .lab/alpine-index.json
```

<!-- lab -->

```sh
J=work/alpine-index.json
echo "manifests: $(jq '.manifests | length' $J)"
jq -r '.manifests[] | select(.platform.os != "unknown") | "  \(.platform.os)/\(.platform.architecture)\(.platform.variant // "")"' $J
```

<!-- out -->

```
manifests: 16
  linux/amd64
  linux/armv6
  linux/armv7
  linux/arm64v8
  linux/386
  linux/ppc64le
  linux/riscv64
  linux/s390x
```

ستّةَ عشرَ مدخلاً: ثمانيةٌ لمعمارياتٍ حقيقية، وثمانيةٌ بمعمارية `unknown` هي
شهاداتُ المنشأ التي استبعدتَها بـ`--provenance=false` في صورتك.

**فالوسم `alpine:3.20` لا يسمّي صورة، بل يسمّي فهرساً.** ومن يشغّله على x86 ومن
يشغّله على ARM ينزّلان **بايتاتٍ مختلفة تماماً**، بلا بصمةٍ مشتركةٍ واحدة تحت
الفهرس.

**والمكسب:** «ثبّتُّ الوسم فصار البناء مكرَّراً» ادّعاءٌ ناقص — الوسم يتغيّر
تحتك، وحتى تثبيتُه بالبصمة يعطيك **الفهرس** لا الصورة. وأنت ثبّتَّ بصمةَ فهرسٍ
في `FROM` أعلاه، فما وصلك منه هو مدخلُ معماريتك أنت.

## التركيب الذي يفشل

بقيت خطوة: عندك ثلاثة أرشيفات، وتعرف من الإقليم ٠٨ كيف يُركَّب `overlayfs`. فكُكّ
كلَّ أرشيفٍ في مجلّد، واجعلها `lowerdir` بترتيبها.

**قبل التشغيل: `/one.txt` أُنشئ في الطبقة ١ وحُذف في الطبقة ٢. فماذا سترى؟**

<!-- lab -->

```sh
cd work/img
M=blobs/sha256/$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
mount -t tmpfs t /mnt
i=0; LOW=""
for d in $(jq -r '.layers[].digest' $M | cut -d: -f2); do
	mkdir /mnt/l$i && tar xzf blobs/sha256/$d -C /mnt/l$i
	LOW="/mnt/l$i${LOW:+:}$LOW"
	i=$((i + 1))
done
mkdir /mnt/root
mount -t overlay overlay -o "lowerdir=$LOW" /mnt/root
echo "lowerdir=$LOW"
ls -a /mnt/root | grep -e one -e two -e wh
```

<!-- gate -->

```
lowerdir=/mnt/l2:/mnt/l1:/mnt/l0
.wh.one.txt
one.txt
two.txt
```

الشجرة قامت، والترتيب صحيح، و`two.txt` في موضعه. ومع ذلك **`one.txt` ما يزال
هناك** — والملفّ الذي كان يجب أن يمحوه جالسٌ إلى جانبه ملفّاً عاديّاً.

لأن `overlayfs` لم يرَ حذفاً قطّ: هو يبحث عن جهازٍ وهميّ `c 0,0`، وأنت سلّمتَه
ملفّاً فارغاً اسمه يبدأ بـ`.wh.`. **ففكُّ الأرشيف ليس تركيبَ الصورة.** بينهما
مترجمٌ يقرأ لغة النقل ويكتب لغة نظام الملفّات، ويصنع فوقها الطبقةَ القابلة
للكتابة.

**والمكسب:** تعرف الآن ما الذي تبحث عنه في الأداة، وباسمه: هذا هو الـsnapshotter.

## التمرين — اثنان، ولا حلول

**١.** أعد بناء `demo:1` بلا أي تغيير في الـDockerfile، واحفظها ثانيةً وقارن
بصمة **الـmanifest** مع الأولى. ثم غيّر `salam` إلى `salaam` وأعد الكرّة.
**معيار القبول:** جدولٌ من ثلاثة أسطرٍ يقول أيُّ البصمات تغيّر وأيُّها ثبت في
كلتا الحالتين — بصمة الـconfig، وبصمات الطبقات الثلاث، وبصمة الـmanifest —
وسطرٌ واحد يفسّر لماذا لا يمكن أن يثبت الـmanifest إن تغيّر الـconfig.

**٢ (الأصعب).** أصلح التركيب الفاشل أعلاه بيدك: حوّل كل `.wh.NAME` في المجلّدات
المفكوكة إلى ما يفهمه `overlayfs`، ثم أعد الجبل. **معيار القبول:** `one.txt`
اختفى و`two.txt` بقي، **دون** أن تلمس الطبقة `l1` التي أنشأت `one.txt`. وسطرٌ
يقول لماذا كان لا بدّ أن يقع الإصلاح في `l2` تحديداً.

## الخلاصة — أين نحن في الشجرة

| ما عرفتَه | العقدة التي يتعلّق بها |
|---|---|
| الاسم بصمةُ المحتوى | يفسّر بضربةٍ واحدة: عدمَ التعديل، والمشاركة، والتحقّق، وتخطّي التنزيل |
| `digest` للمنقول و`diff_id` للمفكوك | جواب: لماذا لا تسقط الخبيئة حين يتغيّر الضاغط |
| الطبقةُ تغييرٌ في الملفّات لا سطرٌ في ملفّ | فسّر لماذا لا يقلّل دمجُ `ENV` شيئاً |
| `IMAGE ID` اسمٌ عند أداتك، لا في المواصفة | استعمل `repo@sha256:…` حين تعني صورةً بعينها |
| الحذف في الأرشيف `.wh.`، وفي الشجرة `c 0,0` | يفسّر لماذا لا يكفي `tar x` لتشغيل صورة |
| الوسم يسمّي فهرساً لا صورة | فسّر كيف يعطي `docker pull` الواحدُ بايتاتٍ مختلفةً لجهازين |

> **البذرة:** بقي المترجم. مَن يفكّ الأرشيفات، ويحوّل `.wh.` إلى `c 0,0`، ويرتّب
> الـ`lowerdir`، ويضع فوقها `upper` قابلةً للكتابة، ويسلّم الشجرة إلى `runc` —
> كلُّ ذلك قبل أن يظهر لك سطرٌ واحد من `docker run`؟
>
> الإقليم القادم يمسك ذلك المترجم متلبّساً، ويقيس ما يكلّفه.
