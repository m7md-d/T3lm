# الإقليم ٢٨ — دورة الحياة

> رأيتَ الطبقات الأربع من فوق: `docker` → `dockerd` → `containerd` → الحشوة →
> `runc`. وكلُّ طلبٍ يمرّ عبرها ينتهي عند سطرٍ واحد: إشارةٌ تُرسَل، أو ملفٌّ
> يُقرأ.
>
> فماذا يحدث بالضبط حين تكتب `docker stop`؟ وأين يذهب مخرَجك حين لا تكون هناك
> طرفيّة؟ هذا الإقليم يقيس دورة الحياة كلَّها.

---

## `stop` إشارتان، لا واحدة

**الاعتقاد، صريحاً:** `docker stop` يقتل الحاوية.

جرّب على برنامجٍ يمسك الإشارة الأولى:

<!-- host-setup -->

```sh
docker rm -f l28 > /dev/null 2>&1
cat > .lab/trap.sh <<'EOF'
trap 'echo "got TERM"; exit 0' TERM
echo ready
while true; do sleep 1; done
EOF
docker run -d --name l28 -v "$PWD/.lab/trap.sh:/trap.sh" alpine:3.20 sh /trap.sh > /dev/null
```

<!-- host -->

```sh
T0=$(date +%s%N)
docker stop l28 > /dev/null
T1=$(date +%s%N)
echo "stop took : $(( (T1 - T0) / 1000000 )) ms"
docker logs l28
docker inspect l28 -f 'exit code : {{.State.ExitCode}}'
```

<!-- gate @machine -->

```
stop took : … ms
ready
got TERM
exit code : 0
```

أقلّ من ثانيةٍ ورمزُ خروجٍ صفر. لم يُرسَل `SIGKILL` قطّ — لأنه لم يلزم.

**والمكسب:** `stop` **يطلب** الخروج ولا يفرضه: يرسل `SIGTERM`، وينتظر برنامجك
ليقرّر بنفسه. وهذا هو الفرق عن `docker kill` — التي ترسل `SIGKILL` مباشرةً
بلا طلب.

## وإن لم يستجب، تنتظر ثم تفرض

<!-- host-setup -->

```sh
docker rm -f l28b > /dev/null 2>&1
cat > .lab/ignore.sh <<'EOF'
trap '' TERM
echo "ready, ignoring TERM"
while true; do sleep 1; done
EOF
docker run -d --name l28b -v "$PWD/.lab/ignore.sh:/ignore.sh" alpine:3.20 sh /ignore.sh > /dev/null
```

<!-- host -->

```sh
T0=$(date +%s%N)
docker stop -t 3 l28b > /dev/null
T1=$(date +%s%N)
echo "stop -t 3 took : $(( (T1 - T0) / 1000000 )) ms"
docker inspect l28b -f 'exit code       : {{.State.ExitCode}}'
```

<!-- gate @machine -->

```
stop -t 3 took : … ms
exit code       : 137
```

ثلاث ثوانٍ بالضبط — مهلة `-t` — ثم موتٌ بـ`137`. وهي `128 + 9`: **`SIGKILL`،
ولا يُمسَك ولا يُتجاهَل أبداً**، وهو ما فرض الموت أخيراً.

**والمكسب:** رمز الخروج نفسه دليلٌ على ما جرى. `0`–`128` خروجٌ طبيعيّ للبرنامج،
وما فوق `128` **إشارةٌ قتلته** برقمها: `137` قتلٌ، `143` (`128+15`) خروجٌ استجابةً
لـ`SIGTERM` بلا مسكٍ صريح.

## ولماذا لا يحتاج الأمر برنامجاً يتجاهل الإشارة

<!-- host-setup -->

```sh
docker rm -f l28c > /dev/null 2>&1
docker run -d --name l28c alpine:3.20 sleep 300 > /dev/null
```

<!-- host -->

```sh
T0=$(date +%s%N)
docker stop -t 3 l28c > /dev/null
T1=$(date +%s%N)
echo "sleep as pid 1, stop -t 3 : $(( (T1 - T0) / 1000000 )) ms"
docker exec t3lm-x sh -c 'echo (irrelevant, keeps session warm)' > /dev/null 2>&1 || true
```

<!-- gate @machine -->

```
sleep as pid 1, stop -t 3 : … ms
```

`sleep` لا يتجاهل `SIGTERM` بأي كودٍ كتبه مؤلّفوه — ومع ذلك استغرق الأمر ثلاث
ثوانٍ كاملة، لا أقلّ. وهذا هو **العدم الخاصّ بالعملية رقم ١** الذي رأيتَه في
الإقليمين ٠١ و٠٤: أيُّ إشارةٍ افتراضيّةُ تصرّفها «إنهاء»، ولم تُبرمَج عمليةُ
`init` صراحةً لمعالجتها، **تُتجاهَل** — بقرار النواة، لا لأن أحداً كتب
`trap`.

**والمكسب — وهو أهمّ درسٍ في هذا الإقليم:** أكثرُ صور Docker تُشغَّل بصيغة
`CMD ["myapp"]` مباشرةً، فيصير برنامجك هو العملية رقم ١، ويرث هذه الحصانة
الافتراضية سواء أراد أم لا. فإن لم يُثبِّت معالجاً لـ`SIGTERM` بنفسه فكلُّ
`docker stop` سينتظر المهلة كاملةً ثم يقتل — لا لأن البرنامج عنيد، بل لأنه لم
يُسأَل.

## أين تذهب: طرفيّةٌ واحدة أم أنبوبان

<!-- host -->

```sh
echo '--- بلا tty ---'
docker run --rm alpine:3.20 sh -c 'echo out; echo err >&2' 2> /tmp/e1
echo "stderr وحده : $(cat /tmp/e1)"
echo '--- بـ tty ---'
docker run --rm -t alpine:3.20 sh -c 'echo out; echo err >&2' 2> /tmp/e2
echo "stderr وحده : $([ -s /tmp/e2 ] && cat /tmp/e2 || echo '(فارغ)')"
```

<!-- gate -->

```
--- بلا tty ---
out
stderr وحده : err
--- بـ tty ---
out
err
stderr وحده : (فارغ)
```

بلا `-t` بقي المجريان منفصلين حتى وصلا إليك، فاستطعتَ أن تعيد توجيه كلاًّ على
حدة. **ومع `-t` اختفى الانفصال قبل أن يصل إليك أصلاً**: الطرفيّة الوهمية داخل
الحاوية دمجت الاثنين في تيّارٍ واحد — وهذه خاصّيّةُ الجهاز الطرفيّ نفسه (`tty`
line discipline)، لا سلوكاً من Docker.

**والمكسب:** برنامجٌ يفصل سجلّاته بين المجريين لغايةٍ ما (رسائل تشخيصٍ في
`stderr`، بياناتٍ في `stdout`) يفقد هذا الفصل نهائياً لو شُغِّل بـ`-t`. وهذا
سببٌ عمليّ لتجنّب `-t` في أي حاويةٍ غير تفاعلية.

## ومخرَجك يُكتَب قبل أن تسأل عنه

<!-- host-setup -->

```sh
docker rm -f l28f > /dev/null 2>&1
docker run -d --name l28f alpine:3.20 sh -c 'echo hello; echo world >&2' > /dev/null
```

<!-- host -->

```sh
#! sort
sleep 1
CID=$(docker inspect -f '{{.Id}}' l28f)
docker run --rm --privileged --pid=host -e CID="$CID" t3lm-docker-lab \
	nsenter -t 1 -m -- sh -c \
	'find /var/lib/docker/containers -name "$CID-json.log" -exec cat {} \;'
docker rm -f l28 l28b l28c l28f > /dev/null
```

<!-- gate @impl -->

```
{"log":"hello\n","stream":"stdout","time":"…"}
{"log":"world\n","stream":"stderr","time":"…"}
```

لم تطلب سجلّاً؛ الحشوة كتبته وحدها إلى **ملفٍّ على قرصك**، بشكل JSON، سطراً
لكل رسالة، ومصدرها موسوماً. و`docker logs` لا يذهب إلى الحاوية ليسألها: **يقرأ
هذا الملفّ**.

**والمكسب:** `docker logs` يعمل بعد موت الحاوية لأن مصدره ليس عمليةً حيّة، بل
ملفٌّ بقي. وهذا يفسّر أيضاً لماذا تتضخّم مساحة القرص بصمتٍ عند حاويةٍ ثرثارة:
كلُّ سطرٍ تطبعه محفوظٌ إلى الأبد ما لم تُدوَّر السجلّات صراحةً.

## التمرين — اثنان، ولا حلول

**١.** اكتب صورةً بـ`CMD ["myapp"]` (صيغة exec) وأخرى بـ`CMD myapp` (صيغة
shell)، وقس زمن `docker stop` على كلٍّ منهما ببرنامجٍ يمسك `SIGTERM` بنجاح.
**معيار القبول:** رقمان مختلفان، وسطرٌ يقول إلى أي عمليةٍ وصلت الإشارة في كل
صيغة — مسنداً إلى شجرة العمليات لا إلى تخمين.

**٢ (الأصعب).** أوقف حاويةً بأمرٍ يخصّها في cgroup (وليس `docker stop`) —
باستعمال `cgroup.kill` من الإقليم ١٢. **معيار القبول:** رمز الخروج الذي سجّله
`docker inspect`، وسطرٌ يقول لماذا لا تحصل هذه الطريقة على مهلةٍ إطلاقاً.

## الخلاصة — أين نحن في الشجرة

| ما عرفتَه | العقدة التي يتعلّق بها |
|---|---|
| `stop` إشارتان: `TERM` بمهلة، ثم `KILL` قسراً | `kill` ترسل الثانية مباشرةً |
| رمز الخروج فوق ١٢٨ يسمّي الإشارة | `137`=`KILL`، `143`=`TERM` |
| حصانة العملية رقم ١ سببُ الانتظار الكامل | صيغة `CMD` تقرّر من يستلم الإشارة |
| `-t` يدمج stdout وstderr في تيّارٍ واحد | خاصّيّةُ الطرفيّة، لا Docker |
| `docker logs` يقرأ ملفّاً لا يسأل عمليةً | يعمل بعد الموت، ويتضخّم بصمت |

> **البذرة:** انتهت حزمة «من يشغّل»: المواصفة، ثم `runc`، ثم ما فوقه، ثم
> `dockerd`، ثم دورة الحياة كاملةً. وكلُّ ما رأيتَه كان محرّكاً واحداً بعينه.
>
> فماذا لو لم يكن هناك محرّك؟ لا `dockerd`، ولا مقبسٌ واحد يملك مجموعتَه
> كاملةً، ولا خطرَ الانتقال من مستخدمٍ عاديّ إلى جذرٍ كامل بعضويّة مجموعة؟
>
> الإقليم القادم يبني نفس الحاوية بأداةٍ **بلا daemon أصلاً**.
