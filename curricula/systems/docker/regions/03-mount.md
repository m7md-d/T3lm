# الإقليم ٠٣ — `mount`: الشجرة والانتشار

> في `box` كان هذا السطر:
>
> ```c
> must(mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL), "mount /");
> ```
>
> وقلتُ وقتها: **بدونه يتسرّب كل جبلٍ تفعله إلى نظام المضيف**. هذا الإقليم لا
> يطلب منك أن تصدّق ذلك — سيسرّب أمامك جبلاً حقيقياً، ثم يمنعه بنفس السطر.
>
> وفيه أيضاً اللغز الذي أجّله الإقليم الأوّل: **لماذا لا تستطيع أن تهرب من
> `box` بالحيلة التي تهرب بها من `chroot`.**

---

## الشجرة نسخةٌ، لا قائمة

<!-- lab -->

```sh
mkdir -p /mnt/a
mount -t tmpfs t /mnt/a
findmnt -n -o TARGET,SOURCE,FSTYPE /mnt/a
```

<!-- out -->

```
/mnt/a t   tmpfs
```

`mount` ألحقت عقدةً في شجرة الجبل الحالية. **وكل عمليةٍ لها شجرتها**، ابتداءً
من نطاق `mnt` الذي تسكنه — رأيتَه رقماً في الإقليم ٠٢، وهذا محتواه.

<!-- setup -->

```sh
umount /mnt/a
```

---

## الانتشار: من يرى تعديلاتك

نطاقان مختلفان لهما شجرتا mount منفصلتان تماماً منذ لحظة `clone`. **فكيف
يتشارك المضيف وحاوياته `/etc/resolv.conf` إذاً؟** الجواب أن الانفصال ليس
مطلقاً — لكل نقطة جبلٍ **نوعُ انتشار**، وهو ما يقرّر إن كان تعديلٌ في نطاقٍ
يظهر في آخر.

```
                    نوع الانتشار
                    ─────────────

  shared    كل نسخةٍ تُخطِر أخواتها بأي جبلٍ أو فكّ جبل   (الافتراض على أكثر توزيعات لينكس)
  private   لا تُخطِر أحداً ولا تُخطَر                      (ما يطلبه box صراحةً)
  slave     تستقبل من أصلها ولا ترسل إليه                  (ما يستعمله bind mount في Docker)
```

اجبل شيئاً **مشتركاً** أوّلاً، ثم انظر ماذا يحدث حين يجبل نطاقٌ آخر بداخله:

<!-- lab -->

```sh
mkdir -p /mnt/s
mount --bind /mnt/s /mnt/s
mount --make-shared /mnt/s
findmnt -n -o TARGET,PROPAGATION /mnt/s
```

<!-- out -->

```
/mnt/s shared
```

<!-- lab -->

```sh
mkdir -p /mnt/s/x
unshare --mount --propagation unchanged \
	sh -c 'mount -t tmpfs t /mnt/s/x; touch /mnt/s/x/leaked'
ls /mnt/s/x
```

<!-- gate -->

```
leaked
```

> **توقّع قبل أن تشغّل:** الجبل والملفّ وقعا **داخل** نطاقٍ آخر تماماً — نطاقٌ
> وُلد بـ`unshare --mount`. فهل يظهر الملفّ هنا، في النطاق الأصليّ؟

**نعم.** نطاقان منفصلان، تُنشئ الشجرة في أحدهما، **وتظهر النتيجة في الآخر.**
هذا هو الانتشار: `/mnt/s` مشتركة، فكل جبلٍ تحتها — في أي نطاقٍ يشاركها — يُخطِر
البقيّة.

**ولاحظ العَلَم `--propagation unchanged`.** بدونه:

<!-- lab -->

```sh
mkdir -p /mnt/s/y
unshare --mount sh -c 'mount -t tmpfs t /mnt/s/y; touch /mnt/s/y/safe'
ls /mnt/s/y
```

<!-- gate -->

```
```

> **توقّع:** نفس التجربة بالضبط، بلا ذلك العَلَم. هل يتسرّب هذا أيضاً؟

**لا شيء.** فارغة. **لأن `unshare` نفسها تفعل ما يفعله `box`:** حين لا تُطلَب
منها صراحةً إبقاء الانتشار، تجعل الشجرة الجديدة **خاصّةً** تلقائياً — نفس
`MS_PRIVATE` الذي رأيتَه في `box.c`، وبنفس السبب: عزلٌ يفترض الأمان لا العكس.

<!-- setup -->

```sh
umount -l /mnt/s/x 2>/dev/null; umount -l /mnt/s/y 2>/dev/null; umount -l /mnt/s
```

**والمكسب هنا سطرٌ واحد صار مفهوماً بالكامل:**

```c
must(mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL), "mount /");
```

`box` لا يتّكل على افتراض `unshare` — يكتب الأمان **صراحةً**، لأن `clone` نداءٌ
أخفض مستوًى لا يحمل افتراض الأداة. وبدون هذا السطر، على مضيفٍ تكون فيه `/`
مشتركة (وهي كذلك على أكثر توزيعات لينكس)، **كل جبلٍ تفعله داخل `box` يظهر عند
المضيف** — بالضبط كما رأيتَه الآن.

## `MS_REC`: لماذا الشجرة كلّها لا الجذر وحده

ابنِ شجرةً من طابقين، واجعلهما **مشتركين** كلاهما — كما يكون الحال على أكثر
مضيف:

<!-- lab -->

```sh
mkdir -p /mnt/tree && mount -t tmpfs t /mnt/tree && mount --make-shared /mnt/tree
mkdir -p /mnt/tree/inner && mount -t tmpfs t /mnt/tree/inner
mount --make-shared /mnt/tree/inner
findmnt -n -R -o TARGET,PROPAGATION /mnt/tree
```

<!-- out -->

```
/mnt/tree         shared
`-/mnt/tree/inner shared
```

الآن اطلب private على الطابق الأعلى وحده:

<!-- lab -->

```sh
mount --make-private /mnt/tree
findmnt -n -o TARGET,PROPAGATION /mnt/tree/inner
```

<!-- gate -->

```
/mnt/tree/inner shared
```

> **توقّع قبل أن تشغّل:** طلبتَ private على `/mnt/tree`. فما انتشار
> `/mnt/tree/inner` — العقدة **تحتها**؟

**بقيت shared.** `--make-private` بلا `-R` غيّر عقدةً واحدة، وتركَ ما تحتها
كما كان — سطران في نفس الشجرة، ينتشر أحدهما ولا ينتشر الآخر. والحلّ `-R`
(المقابل لـ`MS_REC` في `mount(2)`):

<!-- lab -->

```sh
mount --make-rprivate /mnt/tree
findmnt -n -R -o TARGET,PROPAGATION /mnt/tree
```

<!-- out -->

```
/mnt/tree         private
`-/mnt/tree/inner private
```

**والشجرة قد تطول بلا حدٍّ معروف مسبقاً**: كل جبلٍ متداخل عقدة. ولذلك يحمل
سطر `box` نفسُه `MS_REC` مرّتين — على `/` كاملةً، وعلى الجذر الجديد قبل ربطه —
فلا يُترَك جبلٌ متداخلٌ ينسى القاعدة.

<!-- setup -->

```sh
umount -R /mnt/tree
```

## اللغز: لماذا لا تهرب من `box` كما تهرب من `chroot`

الحيلة الكلاسيكية ضدّ `chroot` معروفةٌ منذ التسعينيات: أنشئ مجلّداً، `chroot`
إليه، ثم اصعد بـ`..` أكثر ممّا تحتاج. `chroot` **لا تغيّر مجلّد العمل الحاليّ**،
فتصعد فوق الجذر الجديد إلى ما بعده حتى تخرج من الجذر القديم أصلاً — الذي بقي
معلّقاً بلا اسم.

<!-- part: 03-escape.c -->

```c
	mkdir("/esc", 0755);
	chroot("/esc");

	for (int i = 0; i < 64; i++)
		chdir("..");

	chroot(".");
	chdir("/");
	execlp("ls", "ls", "/", NULL);
```

سبعة عشر سطراً. جرّبها ضدّ سجنٍ حقيقيّ بُني بـ`chroot`:

<!-- lab -->

```sh
rm -rf /tmp/jail && mkdir -p /tmp/jail && cp -a work/rootfs/. /tmp/jail/
cc -static -o /tmp/jail/escape programs/03-escape.c
chroot /tmp/jail /escape
```

<!-- out @impl -->

```

dev
etc
home
lab
lib
media
mnt
opt
proc
root
run
sbin
srv
sys
tmp
usr
var
```

**`boot` و`lab`.** لا وجود لهما في `/tmp/jail`. هذه شجرة **المختبر الحقيقية**
— هرب السجين.

> **توقّع قبل أن تشغّل التالي:** نفس البرنامج بالضبط، بلا تعديل سطرٍ واحد،
> يُشغَّل الآن داخل `box` بدل `chroot` العادية. **هل يهرب؟**

<!-- lab -->

```sh
cc -std=c17 -o box programs/01-box.c
cc -static -o work/rootfs/escape programs/03-escape.c
./box work/rootfs /escape
```

<!-- out @impl -->

```
bin
dev
esc
escape
etc
home
lib
media
mnt
opt
proc
root
run
sbin
srv
sys
tmp
usr
var
```

**لا `boot`. لا `lab`.** الأسماء التي ظهرت (`esc`, `escape`) من داخل `work/rootfs`
نفسها — نفس الشجرة التي بدأ منها. **دار البرنامج ٦٤ مرّة `..` ووجد نفسه في
المكان الذي بدأ منه بالضبط.**

### لماذا

الحيلة تعمل ضدّ `chroot` لأن الجذر القديم **يبقى موجوداً** فوق الجذر الجديد —
`chroot` لا تُزيله، فقط تُخفيه عن `/`. والصعود يتجاوز نقطة الإخفاء فيصل إليه.

و`pivot_root` في `box` **لا تُخفي الجذر القديم؛ تُزيله**:

<!-- part: 01-box.c -->

```c
	must(syscall(SYS_pivot_root, ".", "."), "pivot_root");
	must(umount2(".", MNT_DETACH), "umount old");
```

السطر الثاني يفكّ الجذر القديم بعد أن صار مجلّداً عادياً تحت الجديد — **فلا
يبقى شيءٌ تصعد إليه.** الصعود بـ`..` من الجذر يعيدك إلى الجذر — هذا تعريف الجذر
في أي نظام ملفّات، لا استثناءً هنا.

**وهذا فرقٌ بنيويّ لا درجة أمان:** `chroot` تُغيّر ما تراه العملية. `pivot_root`
**تُزيل ما كان هناك.** الأولى قناع، والثانية بتر.

## التمرين — اثنان، ولا حلول

**١.** بنيتَ إثباتاً على التسرّب باتّجاهٍ واحد: من نطاقٍ فرعيّ إلى الأصليّ.
اعكسه: اجبل شيئاً في النطاق **الأصليّ** بعد أن يكون الفرعيّ قد بدأ، وتحقّق: هل
يظهر عند الفرعيّ؟ (تلميحٌ من العنوان: `shared` تُخطِر **الطرفين**، وهذا ما
يميّزها عن `slave`). **معيار القبول:** جملةٌ واحدة تقول أيّهما رأى الآخر ولماذا،
مسندةً إلى تجربة.

**٢ (الأصعب).** أضِف `MS_SLAVE` إلى تجربة الانتشار: اجعل نقطةً `slave` من
أصلٍ `shared`، ثم جرّب الاتّجاهين. **معيار القبول:** جدولٌ من صفّين يقول ما
الذي يعبر وما لا يعبر، من تجربةٍ حقيقية لا من هذا النصّ.

## الخلاصة — أين نحن في الشجرة

| ما عرفتَه | العقدة التي يتعلّق بها |
|---|---|
| الشجرة نسخةٌ لكل نطاق | فُسِّر لماذا `box` يجبل جذراً خاصّاً به بلا صدام |
| والانتشار يصل بينها | فُسِّر كيف يشارك المضيف `/etc/resolv.conf` مع حاوياته |
| و`MS_PRIVATE` يقطعه | تحقّق سطر `box.c` الأوّل تجريبياً — لا نظرياً |
| و`pivot_root` تُزيل لا تُخفي | حُسم لغز الإقليم الأوّل: الهروب الكلاسيكيّ يفشل هنا لأنه لا يوجد ما يصعد إليه |

> **البذرة:** الشجرة التي بنيتَها كلُّها في القرص الحقيقيّ للمختبر — `alpine`
> المفكوكة في `work/rootfs`. لكن الصورة التي يسحبها Docker من سجلٍّ ليست
> مجلّداً واحداً؛ هي **طبقات**، تُركَّب فوق بعضها بنظام ملفّاتٍ خاصّ يجعل
> القراءة تخترقها والكتابة تقف عند الأعلى وحدها.
>
> الإقليم القادم يفكّك overlayfs بيدك.
