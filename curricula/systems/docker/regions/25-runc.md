# الإقليم ٢٥ — `runc`

> الحزمة بياناتٌ لا تفعل شيئاً. والذي يقرؤها ويصنع منها عمليةً هو `runc`، وقد
> شغّلتَه في الإقليم السابق بأمرٍ واحد.
>
> لكنّ ذلك الأمر الواحد **ليس ما تستعمله الأدوات**. وفي الطريق عمليةٌ تعيد تنفيذ
> نفسها، وثغرةٌ حقيقية ما زال تصميمُ اليوم قائماً على علاجها.

---

## مرحلتان لا واحدة

<!-- host-setup -->

```sh

```

<!-- setup -->

```sh
mkdir -p /tmp/b25 && cd /tmp/b25
runc spec
cp -r /lab/work/rootfs .
jq '.process.terminal = false
    | .process.args = ["/bin/sh", "-c", "echo payload running; sleep 30"]' \
	config.json > c2 && mv c2 config.json
```

<!-- lab -->

```sh
cd /tmp/b25
runc --root /tmp/rc25 create c1
P=$(runc --root /tmp/rc25 state c1 | jq -r .pid)
echo "after create : $(runc --root /tmp/rc25 state c1 | jq -r .status)"
echo "cmdline      : $(tr '\0' ' ' < /proc/$P/cmdline)"
runc --root /tmp/rc25 start c1
sleep 1
echo "after start  : $(runc --root /tmp/rc25 state c1 | jq -r .status)"
```

<!-- gate -->

```
after create : created
cmdline      : runc init 
payload running
after start  : running
```

**بين الأمرين حاويةٌ موجودة ولم يعمل فيها برنامجك بعد.** لها رقم عملية، ولها
حالة، ويمكن أن تُقتَل وتُحذَف — والعملية القائمة فيها ليست `sh` بل شيءٌ اسمه
`runc init`.

**والمكسب:** كلُّ ما تعرفه من `docker create` ثم `docker start` — وكلُّ ما
يفعله Kubernetes حين يجهّز الحاوية قبل تشغيلها — يقف على هذا الانفصال. وسببُه
في الفقرة التالية.

## ولماذا انفصلتا

انظر ماذا اكتمل في تلك اللحظة، قبل أن يعمل شيء:

<!-- lab -->

```sh
cd /tmp/b25
runc --root /tmp/rc25 create c2
P=$(runc --root /tmp/rc25 state c2 | jq -r .pid)
echo "status      : $(runc --root /tmp/rc25 state c2 | jq -r .status)"
echo "pid ns same : $([ "$(readlink /proc/$P/ns/pid)" = "$(readlink /proc/self/ns/pid)" ] && echo yes || echo no)"
echo "net ns same : $([ "$(readlink /proc/$P/ns/net)" = "$(readlink /proc/self/ns/net)" ] && echo yes || echo no)"
echo "cgroup      : $(cat /proc/$P/cgroup)"
```

<!-- gate -->

```
status      : created
pid ns same : no
net ns same : no
cgroup      : 0::/c2
```

النطاقات مُنشأة، والمجموعة مُنشأة، والعملية داخلهما — **وبرنامجك لم يبدأ.**

وهذه هي النافذة كلُّها: من يشغّل `runc` يعرف الآن رقم العملية، فيستطيع أن
يدخل نطاق شبكتها ويصنع فيها `veth` (الإقليم ٢٠)، وأن يكتب حدوداً في مجموعتها
(الإقليم ١٢)، وأن يجبل فيها ما يشاء (الإقليم ١١) — **كلُّ ذلك قبل أن ينفّذ كودُ
الصورة تعليمةً واحدة.**

**والمكسب:** لو كان الأمر واحداً لوقع سباقٌ بين تجهيز الشبكة وأوّل رزمةٍ يرسلها
برنامجك. والانفصال يلغي السباق: العملية تنتظر عند بوّابة — وهي بالضبط الأنبوب
الذي اضطُررتَ إليه في الإقليم الأوّل.

## `runc init`: البرنامج يعيد تنفيذ نفسه

بقي السؤال: ما `runc init`؟ اقرأ من أين جاء:

<!-- lab -->

```sh
P=$(runc --root /tmp/rc25 state c2 | jq -r .pid)
echo "runc on disk : $(command -v runc)"
echo "init's exe   : $(readlink /proc/$P/exe)"
runc --root /tmp/rc25 delete -f c2
runc --root /tmp/rc25 kill c1 KILL 2>/dev/null
sleep 1
runc --root /tmp/rc25 delete -f c1 2>/dev/null
echo "remaining    : $(runc --root /tmp/rc25 list | tail -n +2 | wc -l)"
```

<!-- gate -->

```
runc on disk : /usr/sbin/runc
init's exe   : /memfd:runc_cloned:/proc/self/exe (deleted)
remaining    : 0
```

`runc` لا يستطيع أن يدخل النطاقات ثم يبقى هو نفسه: بعضُ الإعداد لا يُطبَّق إلا
من **داخل** النطاق، ونطاق العمليات لا يسري على من أنشأه بل على أبنائه (الإقليم
٠٤). فيتفرّع ويعيد تنفيذ **نفسه** بوسيط `init`، فيصير الابنُ داخل النطاقات ويكمل
ما بقي، ثم ينتظر البوّابة ليُنفّذ برنامجك بـ`exec`.

**والسطر الثاني هو موضع الدرس:** الملفّ الذي نُفِّذ ليس `/usr/sbin/runc`. هو
**نسخةٌ في الذاكرة** بلا اسمٍ على أي قرص.

---

## ولماذا نسخةٌ في الذاكرة: CVE-2019-5736

في `box` — وفي `runc` قبل ٢٠١٩ — كان `/proc/self/exe` داخل الحاوية يشير إلى
**ملفّ `runc` على قرص المضيف**.

والعملية داخل الحاوية تستطيع أن تفتح ذلك المسار. فلو استطاعت الكتابة فيه لكتبت
في برنامجٍ يشغّله جذرُ جهازك في **كل** حاويةٍ تالية. وهذا ما حدث: صورةٌ خبيثة
تنتظر أن يدخلها أحدٌ بـ`exec`، فتستبدل المنفّذ نفسه — **هروبٌ كامل من الحاوية
إلى المضيف بامتياز الجذر.**

والعلاج الذي تراه في اللوحة أعلاه: **`runc` ينسخ نفسه إلى `memfd`** — ملفٌّ في
الذاكرة بلا مسار — ويختمه ضدّ الكتابة، ثم ينفّذ النسخة. فالعملية داخل الحاوية
تفتح `/proc/self/exe` فتجد نسخةً مختومة لا تصل إلى قرصك، وتموت معها.

**والمكسب — وهو الدرس لا الحكاية:** الحاوية ورثت واصفاتٍ وأسماءً من المضيف بلا
أن ينتبه أحد. وكل ما ورثتَه في هذا المنهج — واصفٌ مفتوح، أو مسارٌ مجبول، أو نطاقٌ
متقاسَم — سؤالٌ من هذا النوع: **ما الذي يستطيع الداخلُ أن يفعله بما ورثه؟**

---

## التمرين — اثنان، ولا حلول

**١.** أنشئ حاويةً بـ`create` وحدها، ثم — قبل `start` — انقل عمليتها إلى مجموعة
`cgroup` أخرى وضع فيها حدَّ ذاكرة، ثم شغّلها. **معيار القبول:** إثباتٌ أن الحدّ
سرى على برنامجك، وسطرٌ يقول لماذا ما كان ليسري لو فعلتَ ذلك بعد `start`.

**٢ (الأصعب).** اقرأ `/proc/<pid>/fd` لعملية `runc init` في حالة `created`
وعدّ الواصفات المفتوحة. **معيار القبول:** قائمةٌ بما وجدتَه، وسطرٌ يقول أيُّها
هو البوّابة التي تنتظر `start` — مسنداً إلى ما يحدث لها بعد `start` لا إلى اسمها.

## الخلاصة — أين نحن في الشجرة

| ما عرفتَه | العقدة التي يتعلّق بها |
|---|---|
| `create` يبني كل شيء إلا التنفيذ | نافذةُ التجهيز: شبكة وحدود وجبول قبل أوّل تعليمة |
| `start` يفتح بوّابةً فقط | نفسُ الأنبوب الذي اضطُررتَ إليه في الإقليم الأوّل |
| `runc init` هو `runc` أعاد تنفيذ نفسه | لأن بعض الإعداد لا يُطبَّق إلا من الداخل |
| المنفَّذ نسخةٌ في `memfd` لا ملفٌّ على قرصك | علاجُ CVE-2019-5736، مرئيٌّ في `/proc/…/exe` |
| ما تورّثه للحاوية سؤالٌ أمنيّ دائماً | واصفٌ · مسارٌ · نطاقٌ متقاسَم |

> **البذرة:** `runc` ينشئ الحاوية ثم **يخرج**. جرّبها: شغّل حاويةً طويلة ثم اقرأ
> شجرة العمليات — لن تجد `runc` فيها.
>
> فمن يمسك مخرَجها إذن؟ ومن يعرف أنها ماتت؟ ومن يبقيها حيّةً حين تُحدَّث خدمةُ
> Docker وتُعاد تشغيلاً؟
>
> ثمّة عمليةٌ صغيرة بين الاثنين، وهي التي تجيب الثلاثة.
