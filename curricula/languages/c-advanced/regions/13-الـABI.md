# الفصل ١٣ — الـABI

المنهج الأوّل قال إنّ الترجمة أربع مراحل، وإنّ المُجمِّع ينتج ملفّاً كائناً. وهذا
الفصل يسأل سؤالاً لم يُسأل بعد: **حين ينادي كودٌ في ملفٍّ دالّةً في ملفٍّ آخر، على
ماذا اتّفقا؟**

المصدر لا يقول شيئاً عن هذا. `int f(int, double)` تصف الأنواع، ولا تقول أين يوضع
كلُّ وسيط.

---

## الـABI أوسع من اصطلاح النداء

**اصطلاح النداء جزءٌ منه**، وليس هو. والوثيقة تحسم أشياء أخرى تعتمد عليها كلَّ يوم:

| ما يحسمه الـABI | مثالٌ عليه |
|---|---|
| أحجام الأنواع ومحاذاتها | كم بايتاً في `long`، ومحاذاة `double` |
| تخطيط الـstruct | ترتيبُ الحقول والحشو بينها |
| **اصطلاح النداء** | أين الوسائط، وأين قيمة الإرجاع |
| السجلّات المحفوظة | من يحفظ أيَّها عبر النداء |
| محاذاة الـstack | كم يجب أن يكون `sp` مُحاذًى عند النداء |
| صيغة الملفّ الكائن | ELF هنا، Mach-O هناك |
| ظهور الرموز وربطها | عامّ · محلّيّ · ضعيف |
| فكُّ المكدّس عند الخطأ | جداولُ لا يراها كودك |
| نموذج ذاكرة الخيط | كيف يُوصَل إلى `_Thread_local` |

**ولا تعرّفه اللغة.** ISO C تقول إنّ النداء يعمل، وتترك «كيف» للمنصّة. ولذلك
يُترجَم ملفّان بمترجمين مختلفين ويرتبطان — ما داما يتبعان الوثيقة نفسها.

**والـABI المعتمَد في هذا المنهج AAPCS64** على لينكس/aarch64، وهو ما تراه في كل
لوحةٍ هنا. وما سواه يدخل للمقارنة عند موضعٍ يختلف فيه، ولا يصير مساراً موازياً.

---

## تنبّأ، ثم اقرأ

<!-- runs: 13-abi -->

```c
struct small { int a; int b; };          /* ٨ بايتات */
struct big   { long a[4]; };             /* ٣٢ بايتاً */

struct big f(int a, double b, struct small c, long d);

void caller(void) {
    struct small s = { 1, 2 };
    struct big r = f(7, 2.5, s, 9);
}
```

**قبل أن تقرأ الـassembly، أجب:** أين يقع `7`؟ وأين `2.5`؟ وكيف يُمرَّر `s` وهو
ثمانية بايتات؟ **وأين تُكتَب `r` وهي اثنان وثلاثون بايتاً — والسجلّ ثمانية؟**

ثم: `cc -std=c17 -O1 -c -o abi.o abi.c` و`objdump -d --disassemble=caller abi.o`.

**المخرَج**

<!-- out @abi: AAPCS64 على aarch64؛ gcc 14.2 بـ‎-O1 -->

```

4:	910003fd 	mov	x29, sp
```

اقرأه سطراً سطراً:

| السطر | ما يفعله | القاعدة |
|---|---|---|
| `mov w0, #0x7` | الوسيط الأوّل الصحيح | الصحيحُ في `x0`–`x7` |
| `fmov d0, #2.5` | الـ`double` | **مصرفُ سجلّاتٍ منفصل**: `d0`–`d7` |
| `bfxil` ثم `bfi` على `x1` | حقلا `s` يُحشَران في سجلٍّ واحد | struct صغيرٌ يُمرَّر في سجلّات |
| `mov x2, #0x9` | الـ`long` | ويأخذ السجلّ التالي في المصرف الصحيح |
| `add x8, sp, #0x10` | عنوانُ موضعٍ في مكدّس المُنادي | **الإرجاع الكبير**: المُنادي يحجز المكان، ويعطي عنوانه في `x8` |

**والـ`double` لم يزاحم الصحيح على `x1`.** المصرفان منفصلان، ولكلٍّ عدّادُه — وهذا
يفسّر لماذا لا يتغيّر موضع الوسيط الصحيح بإضافة وسيطٍ عشريّ قبله.

**والإرجاع الكبير ليس في سجلّ أصلاً.** الاثنان والثلاثون بايتاً لا تسع في ثمانية،
فالـABI يقلب المسؤولية: **المُنادي** يحجز، والمُستدعى يكتب في العنوان الذي أُعطي.

## من يحفظ ماذا

```c
int keeps(int x) {
    int a = g(x);
    int b = g(x + 1);
    return a + b;
}
```

`x` يجب أن يبقى بعد النداء الأوّل، و`a` بعد الثاني. وسجلّات الوسائط `x0`–`x7`
**يجوز للمُستدعى أن يدمّرها**. فأين يضعهما المترجم؟

```
0000000000000038 <keeps>:
38:	a9be7bfd 	stp	x29, x30, [sp, #-32]!
40:	a90153f3 	stp	x19, x20, [sp, #16]
44:	2a0003f4 	mov	w20, w0
48:	94000000 	bl	0 <g>
4c:	2a0003f3 	mov	w19, w0
50:	11000680 	add	w0, w20, #0x1
54:	94000000 	bl	0 <g>
58:	0b000260 	add	w0, w19, w0
5c:	a94153f3 	ldp	x19, x20, [sp, #16]
```

`x19` و`x20` من **السجلّات التي يحفظها المُستدعى**: من يستعملها يُعيدها كما وجدها.
فالمترجم حفظهما أوّل الدالّة، ونقل إليهما ما يجب أن يعبر النداء، ثم أعادهما.

**وهذا هو الفرق بين صنفَي السجلّات**، وهو من الـABI لا من المعمارية:

| | يحفظه المُنادي (caller-saved) | يحفظه المُستدعى (callee-saved) |
|---|---|---|
| من يحمي | من يحتاج القيمة بعد النداء | الدالّة التي تستعمل السجلّ |
| على AAPCS64 | `x0`–`x18` | `x19`–`x28` |
| الأثر في الكود | حفظٌ حول كل نداء | حفظٌ مرّةً عند الدخول |

## الوسائط المتغيّرة

```c
void call_v(void) { vf(3, 11, 22, 33); }
```

```
70:	52800423 	mov	w3, #0x21
74:	528002c2 	mov	w2, #0x16
78:	52800161 	mov	w1, #0xb
7c:	52800060 	mov	w0, #0x3
80:	94000000 	bl	0 <vf>
```

الوسائط المتغيّرة مرّت في السجلّات كالثابتة — **على هذا الـABI**.

**وهنا سببُ غرابة `va_list`.** الدالّة المستقبِلة لا تعرف كم وسيطاً جاء ولا أين
استقرّ كلٌّ منه؛ فالماكرو `va_start` يبني بنيةً تتتبّع **عدّادَي المصرفين وموضع
المكدّس** معاً، و`va_arg` يقرأ من الموضع الصحيح بحسب النوع الذي تطلبه. ولذلك هي
ماكرو لا دالّة، ولذلك تختلف بنيتها بين الـABIين.

## معمارية واحدة، وعقدان

الـISA يقول ما التعليمات وما السجلّات. **والـABI يقول كيف تُستعمَل** — وهما طبقتان:

| | AAPCS64 (Arm) | Apple ARM64 |
|---|---|---|
| red zone | لا يعرّفها | ١٢٨ بايتاً تحت `sp` |
| الوسائط المتغيّرة | في السجلّات، كما رأيت | على المكدّس |

**معالجٌ واحد يفهم التعليمات نفسها، وكودٌ مترجَمٌ لأحدهما لا يستطيع مناداة كودٍ
مترجَمٍ للآخر.** فالتوافق البنائيّ ليس في المعمارية؛ هو في الوثيقة.

⚠ ولوحاتُ هذا الفصل من AAPCS64 على لينكس. وجدولُ المقارنة أعلاه من وثيقتَي الـABI،
ولم يُشغَّل الطرف الثاني هنا.

---

## التمرين

غيّر `struct small` إلى ثلاثة `int` (اثنا عشر بايتاً)، ثم إلى خمسة (عشرون).
**أعد الترجمة واقرأ `caller` في كل مرّة.**

عند أيّ حجمٍ يتوقّف المترجم عن تمريره في السجلّات ويبدأ بتمرير عنوانه؟ ثم افتح
AAPCS64 وابحث عن الحدّ المكتوب. **هل يطابق ما قِسته؟**

**الفصل التالي:** الاتفاق الذي قرأتَه الآن مكتوبٌ في وثيقة، وأثرُه محفوظٌ في ملفٍّ
على قرصك. وذلك الملفّ بنيةُ بيانات — وقد وعدتك البديهية الثامنة بأن تقرأها.
