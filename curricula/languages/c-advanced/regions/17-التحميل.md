# الفصل ١٧ — التحميل

الملفّ يحمل `NEEDED: libgreet.so` — اسماً بلا مسار. والرابط الذي كتبه كان يعرف
أين وجد المكتبة، ولم يكتب ذلك.

فمن يبحث عنها يوم التشغيل، وأين، وبأي ترتيب؟

---

## الرابط يكتب سلسلةً، والمحمّل يقرّر الترتيب

راية `-rpath` تجعل الرابط يضع مساراً في الملفّ. وما يفعله المحمّل بذلك المسار
قرارٌ آخر:

<!-- part: 17-search -->

```c
/* المكتبة نفسُها مبنيّةٌ مرّتين، وكلٌّ تقول من أين جاءت */
cc -fPIC -shared -DWHERE='"lib/"'   -o lib/libgreet.so   greet.c
cc -fPIC -shared -DWHERE='"other/"' -o other/libgreet.so greet.c
cc -o progr main.c -Llib -lgreet -Wl,-rpath,'$ORIGIN/lib'
```

**المخرَج**

<!-- out @impl: ld.so من glibc 2.41 وGNU ld 2.44 -->

```
$ ./prog
prog: error while loading shared libraries: libgreet.so: cannot open shared object file: No such file or directory
$ LD_LIBRARY_PATH=lib ./prog
greet: from lib/

$ readelf -dW progr | grep -E "RPATH|RUNPATH"
0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN/lib]
$ ./progr
greet: from lib/
$ LD_LIBRARY_PATH=other ./progr
greet: from other/

$ readelf -dW progo | grep -E "RPATH|RUNPATH"     # --disable-new-dtags
0x000000000000000f (RPATH)              Library rpath: [$ORIGIN/lib]
$ LD_LIBRARY_PATH=other ./progo
greet: from lib/
```

`-rpath` واحدة، ومدخلتان مختلفتان. الراية الافتراضية هنا تكتب `RUNPATH`،
و`--disable-new-dtags` تكتب `RPATH` — والفرق يظهر في السطر الأخير من كل زوج.

**والقاعدة مشروطة، فلا تُنقَل جملةً عامّة.** هذا نصُّها كما يعمل بها glibc:

| الحالة | موضعُ مدخلة الملفّ من `LD_LIBRARY_PATH` |
|---|---|
| `DT_RPATH` وحده، بلا `DT_RUNPATH` | يُبحَث فيه **قبل** المتغيّر |
| `DT_RUNPATH` موجود | يُبحَث فيه **بعد** المتغيّر |
| الوسمان في ملفٍّ واحد | `DT_RPATH` يُهمَل كلُّه، ويعمل `DT_RUNPATH` وحده |
| تنفيذٌ مؤمَّن (secure-execution) | متغيّرات البيئة تُهمَل أو تُقيَّد، فيسقط طرفُ المقارنة |

فالصفّ الأوّل يصحّ **بشرطه**: `DT_RPATH` يسبق المتغيّر ما لم يكن في الملفّ
`DT_RUNPATH`. ووجودُ الأخير يلغي الأوّل، فلا يبقى للترتيب طرفان.

⚠ والصفّان الأوّلان مقيسان في اللوحة، والأخيران من `ld.so(8)` لـglibc 2.41 ولم
يُشغَّلا هنا: binutils 2.44 يكتب أحد الوسمين لا كليهما، والتنفيذُ المؤمَّن يحتاج
ملفّاً بامتيازٍ لا يُنشأ في هذا المختبر.

**والرابط لم يقرّر شيئاً من هذا.** كتب السلسلة في مدخلةٍ بوسمٍ أو بآخر، وترتيبُ
البحث كلُّه من `ld.so`.

و`$ORIGIN` تكشف الفكرة: سلسلةٌ يوسّعها المحمّل وقت التشغيل إلى مجلّد الملفّ
نفسه. فالملفّ يحمل وصفةً، والمحمّل يطبخها.

## والعنوان يتغيّر كل تشغيلة

البرنامج الذي بُني `ET_DYN` يُحمَّل مثل المكتبة المشتركة: في أي موضعٍ يختاره
النظام. والذي بُني `ET_EXEC` يحمل عنوانه في ملفّه.

<!-- part: 17-aslr -->

```c
int g = 1;                                   /* في صورة البرنامج */
int main(void) {
    int x = 0;
    void *h = malloc(1);
    printf("image %p\nstack %p\nheap  %p\n", (void *) &g, (void *) &x, h);
}
```

**المخرَج**

<!-- out @os: Linux 6.12 في حاوية؛ والقيم مقارَنةٌ لا منقولة -->

```
$ cat /proc/sys/kernel/randomize_va_space
2
$ readelf -hW pie | grep Type ; readelf -hW nopie | grep Type
Type:                              DYN (Position-Independent Executable file)
Type:                              EXEC (Executable file)

same binary, two runs:
         image     stack     heap
pie      differs   differs   differs
nopie    same      differs   differs
nopie image address, both runs: 0x420040

$ setarch -R ./pie
setarch: failed to set personality to (null): Operation not permitted
```

اللوحة تقارن ولا تنقل العناوين: القيمة المتغيّرة بين تشغيلين لا تُكتَب في كتاب،
والذي يُكتَب حكمُ المقارنة.

**والصفّان يفصلان الجهتين.** `pie` و`nopie` بُنيا من مصدرٍ واحد، والفرق بينهما
نوعُ ELF الذي **اختاره الرابط**. أمّا تحريك الصورة في كل تشغيلة فمن النواة،
وإعدادُها معروضٌ في السطر الأوّل.

ولاحظ الصفّ الثاني: `nopie` صورتُه ثابتة، ومكدّسه وكومتُه يتحرّكان. فالعشوائيّ
ليس خاصّيةً للبرنامج؛ هو سياسةٌ تُطبَّق على كل ما تملك النواة اختيار موضعه، وصورةُ
`ET_EXEC` خارجةٌ عنه لأن موضعها مطلوبٌ في الملفّ.

⚠ والسطر الأخير طبقةٌ ثالثة: `setarch -R` يطلب `personality` ليطفئ العشوائيّ،
وسياسة الحاوية ترفض النداء. فحتى إطفاء السياسة سياسة.

## والإزاحة عند التحميل

المحمّل يبني **نطاق بحثٍ** مرتَّباً ويحلّ كل رمزٍ بأوّل تعريفٍ يجده فيه.
و`LD_PRELOAD` تدسّ كائناً في صدر ذلك النطاق:

<!-- part: 17-preload -->

```c
/* greet.c */ void greet(void) { puts("greet: the one it was linked against"); }
/* fake.c  */ void greet(void) { puts("greet: the one that was preloaded"); }
```

**المخرَج**

<!-- out @impl: ld.so من glibc 2.41 -->

```
$ ./prog
greet: the one it was linked against
$ LD_PRELOAD=./libfake.so ./prog
greet: the one that was preloaded
$ readelf -dW prog | grep NEEDED
0x0000000000000001 (NEEDED)             Shared library: [libgreet.so]
0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]

$ LD_PRELOAD=./libfake.so ./stat
greet: the one it was linked against
```

ثلاثة أشياء في هذه اللوحة. الأوّل أنّ الملفّ التنفيذيّ **لم يتغيّر**: مدخلاته
تسمّي `libgreet.so` قبل الإزاحة وبعدها. والثاني أنّ `libfake.so` لم تُذكَر في
الملفّ أصلاً، ومع ذلك أجابت.

والثالث حاسمٌ في الإسناد: النسخة الساكنة تتجاهل المتغيّر. الملفّ الساكن يُشغَّل
بلا `ld.so`، فلا جهة تقرأ `LD_PRELOAD` أصلاً. **فالإزاحة قدرةُ المحمّل**، لا
خاصّيةٌ في الربط ولا في اللغة.

⚠ ويقابلها على macOS `DYLD_INSERT_LIBRARIES` بقيودٍ يفرضها حارس النظام على برامج
بعينها. ولم تُشغَّل هنا.

## من يقرّر ماذا

| القرار | الجهة | ومتى |
|---|---|---|
| أيُّ مكتبةٍ تُذكَر في `NEEDED` | الرابط | البناء |
| نصُّ `RPATH` أو `RUNPATH` ووسمُها | الرابط | البناء |
| `ET_DYN` أم `ET_EXEC` | الرابط | البناء |
| ترتيب البحث عن الملفّ | `ld.so` | التحميل |
| نطاق البحث عن الرمز وأوّليّةُ الإزاحة | `ld.so` | التحميل |
| موضع الصورة والمكدّس والكومة | النواة | التشغيل |
| متى يُملأ موضع `.got` | `ld.so` بسياسةٍ معلَنة | التحميل أو النداء الأوّل |

والخلط بين الصفّين الأوّل والرابع يولّد السؤال المعتاد: «البرنامج يعمل عندي ولا
يعمل عنده». الملفّ واحد؛ والذي اختلف ما وجده المحمّل في الترتيب الذي يتبعه.

## التمرين

في `programs/17-preload` اجعل `fake.c` تطبع سطراً ثم تنادي `greet` الأصلية.
ستحتاج `dlsym` بالوسيط `RTLD_NEXT` — وهو امتدادٌ من GNU يعطيك **التعريف التالي**
في النطاق بعد الحاليّ.

هل تعمل من أوّل محاولة؟ وما الذي يحدث إن نسيتَ `RTLD_NEXT` ونادَيتَ `greet`
باسمها مباشرة؟ **جرّب، واقرأ ما يقوله المخرَج عن نطاق البحث.**

**الفصل التالي:** كل ما مضى وقع قبل أن يعمل `main` أو عند أوّل نداء. ويبقى بابٌ
ثالث: أن يطلب برنامجُك ملفّاً لم يُذكَر في `NEEDED` أصلاً، بعد أن بدأ العمل —
ويسأل عن رمزٍ باسمه نصّاً.
