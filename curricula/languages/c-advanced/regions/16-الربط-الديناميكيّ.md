# الفصل ١٦ — الربط الديناميكيّ

الفصل السابق انتهى بملفٍّ واحدٍ يحمل كل ما يحتاجه. وبرامج جهازك ليست كذلك:
`ldd` على أيٍّ منها يعدّ مكتباتٍ تسكن خارجه.

فماذا يفعل الرابط حين يجد الرمز في مكتبةٍ مشتركة؟ يضع في الملفّ **طلباً مؤجَّلاً**
بدل العنوان.

---

## الطلب يبقى في الملفّ

هذا برنامجٌ واحد بُني مرّتين: مرّةً مقابل `libgreet.so`، ومرّةً مقابل أرشيفٍ
ساكنٍ فيه الكود نفسه.

<!-- part: 16-dyn -->

```c
/* greet.c */ void greet(void) { puts("greet: from the shared library"); }
/* main.c  */ void greet(void);
              int main(void) { puts("MARK: before the first call"); greet(); }
```

**المخرَج**

<!-- out @env: glibc 2.41 · binutils 2.44 · aarch64 -->

```
$ LD_LIBRARY_PATH=. ./dyn   |   ./stat
greet: from the shared library
greet: from the shared library
size   dyn 70568   stat 705232   bytes

$ readelf -dW dyn | grep NEEDED
0x0000000000000001 (NEEDED)             Shared library: [libgreet.so]
0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
$ readelf -rW dyn | grep greet
0000000000020018  0000000800000402 R_AARCH64_JUMP_SLOT    0000000000000000 greet + 0

$ readelf -dW stat | head -2

There is no dynamic section in this file.
$ readelf -rW stat | grep -c greet
0
$ readelf -SW stat | grep " .plt"
[ 4] .plt              PROGBITS        0000000000400290 000290 000050 00  AX  0   0 16
$ readelf -rW stat | grep -o "R_AARCH64_[A-Z_]*" | sort -u
R_AARCH64_IRELATIVE
```

في النسخة الديناميكية شيئان: مدخلة `NEEDED` تحمل **اسم** المكتبة، وتنقيلٌ
(relocation) من نوع `JUMP_SLOT` يسمّي `greet` وقيمتُه صفر. الأولى تقول «سأحتاج
ملفّاً بهذا الاسم»، والثاني يحجز موضعاً يُملأ لاحقاً.

**والاسم اسمٌ لا مسار.** الرابط لم يكتب أين وجد `libgreet.so`؛ كتب اسمه وترك
العثور عليه لطبقةٍ أخرى — وذلك موضوع الفصل التالي.

وفي النسخة الساكنة لا قسمَ ديناميكياً، ولا تنقيل يذكر `greet`: العنوان وُضع في
الكود عند الربط، والملفّ عشرةُ أضعافٍ في الحجم.

### وهنا تنهار قاعدةٌ شائعة

القاعدة المتداوَلة أنّ `.plt` و`.got` علامتا الربط الديناميكيّ. واللوحة تكذّبها:
الملفّ الساكن يحمل `.plt`، وتنقيلاتُه من نوع `R_AARCH64_IRELATIVE`.

فالـPLT **آليةُ قفزٍ عبر موضعٍ يُملأ وقت التشغيل**، ومن يملؤه ومتى سؤالٌ منفصل.
هنا يملؤه كود بدء التشغيل في libc نفسها: تختار بين تنفيذاتٍ متعدّدة لدالّةٍ
واحدة بحسب ما يدعمه المعالج. آليةٌ واحدة، وغرضان.

---

## متى يُملأ الموضع المحجوز

الموضع المحجوز يسكن `.got`، والنداء يمرّ بمدخلةٍ في `.plt` تقرأ منه. فمتى يُكتَب
فيه العنوان الحقيقيّ؟ أضف علامتين حول النداء الأوّل واسأل المحمّل أن يسجّل ما
يربط:

<!-- part: 16-lazy -->

```c
setvbuf(stdout, NULL, _IONBF, 0);      /* حتى يبقى الترتيب هو ترتيب الكتابة */
puts("MARK: before the first call");
greet();
puts("MARK: after the first call");
greet();
```

**المخرَج**

<!-- out @impl: ld.so من glibc 2.41؛ والافتراض من هذا البناء -->

```
$ LD_DEBUG=bindings ./prog
MARK: before the first call
binding file ./prog [0] to ./libgreet.so [0]: normal symbol `greet'
greet: from the shared library
MARK: after the first call
greet: from the shared library

$ LD_BIND_NOW=1 LD_DEBUG=bindings ./prog
binding file ./prog [0] to ./libgreet.so [0]: normal symbol `greet'
MARK: before the first call
greet: from the shared library
MARK: after the first call
greet: from the shared library
```

الترتيب هو الدرس. في التشغيلة الأولى وقع الربط **بين** العلامة والمخرَج: النداء
الأوّل قفز إلى مدخلة `.plt`، فوجدها تحيل إلى المحمّل، فبحث عن `greet` وكتب
عنوانه في `.got` ثم قفز إليه. والنداء الثاني لم يربط شيئاً؛ الموضع صار مملوءاً.

وفي الثانية سبق الربطُ `main` كلَّها: `LD_BIND_NOW` يجعل المحمّل يملأ المواضع
قبل أن يسلّم التنفيذ.

**والمقايضة صريحة.** التأجيل يوزّع الكلفة على الاستعمال، ويدفع ثمنَ فحصٍ عند كل
نداءٍ أوّل، ويؤجّل اكتشاف الرمز المفقود إلى لحظة استعماله. والتعجيل يقلب الثلاثة.

⚠ والتأجيل هنا سياسةُ هذا البناء: `ld.so` من glibc 2.41 وملفٌّ رُبط بلا `-z now`.
وبناءٌ يضيفها — وكثيرٌ من التوزيعات يضيفها — يربط عند التحميل بلا متغيّر بيئة.

## و`-fPIC` ليست رايةً تُرضي الرابط

الاسم يوحي بأن المطلوب كودٌ «مستقلٌّ عن الموضع». وعلى aarch64 الشكلان
مستقلّان عن الموضع: كلاهما يبني العنوان بالإزاحة من `pc`. فما الفرق؟

<!-- part: 16-pic -->

```c
int value = 3;                       /* رمزٌ عامّ — قد يُزاح عند التحميل */
int get(void) { return value; }
```

**المخرَج**

<!-- out @impl: gcc 14.2 وGNU ld 2.44 على aarch64 -->

```
$ readelf -rW g_pic.o   # -fPIC
  R_AARCH64_ADR_GOT_PAGE R_AARCH64_LD64_GOT_LO12_NC R_AARCH64_PREL32
$ readelf -rW g_np.o    # -fno-pie -fno-PIC
  R_AARCH64_ADD_ABS_LO12_NC R_AARCH64_ADR_PREL_PG_HI21 R_AARCH64_PREL32

$ cc -shared -o g.so g_np.o
ld: g_np.o: relocation R_AARCH64_ADR_PREL_PG_HI21 against symbol `value' which may bind externally can not be used when making a shared object; recompile with -fPIC

$ cc -shared -o leaf.so leaf_np.o     # المصدر نفسُه بلا رمزِ بياناتٍ عامّ
  (linked)
```

مع `-fPIC` يمرّ الوصول إلى `value` بمدخلةٍ في `.got` — وهذا معنى اسمَي التنقيلين
الأوّلين. وبدونها يبني الكود عنوان `value` مباشرةً.

والرابط يرفض الثاني ويقول سببه: `value` **قد يُزاح خارجياً**. أي أنّ كائناً
آخر قد يعرّف `value` ويفوز به عند التحميل، فيجب أن يمرّ كل وصولٍ بموضعٍ واحدٍ
يُملأ حينها. والعنوان المبنيّ في الكود يسدّ هذا الباب.

**والسطر الأخير يقيّد القاعدة.** ملفٌّ كائنٌ بُني بالرايتين نفسيهما، وليس فيه
وصولٌ إلى رمز بياناتٍ عامّ، رُبط مكتبةً مشتركة بلا اعتراض. فالحاجة إلى `-fPIC`
تتبع **ما يلمسه الكود**.

⚠ واللوحة من aarch64 بـGNU ld. وما تسمح به معماريةٌ أخرى أو رابطٌ آخر من تنقيلاتٍ
في مكتبةٍ مشتركة سؤالٌ يُسأل هناك.

---

## ثلاثة أسئلة تُفصَل

| السؤال | من يجيب | متى |
|---|---|---|
| هل لهذا الاسم تعريف؟ | الرابط الساكن | عند البناء |
| وأين هو الآن؟ | `ld.so` | عند التحميل، أو عند النداء الأوّل |
| وأعطني عنوانه باسمه | `dlsym` | حين يطلبه برنامجُك (الفصل `18`) |

وخلطُ الأوّلين يولّد الحيرة المعتادة: برنامجٌ رُبط بلا خطأ ثم فشل عند التشغيل
بـ`symbol not found`. الرابط أجاب سؤاله وحده: وجد التعريف في `.so` يومَ البناء.
وفي يوم التشغيل مِلفٌّ آخر بالاسم نفسه، ولا تعريف فيه.

---

## التمرين

في `programs/16-dyn` احذف `greet` من `greet.c` بعد بناء `libgreet.so`، ثم أعد
بناء المكتبة وحدها بلا إعادة ربط `dyn`.

شغّل `./dyn`: **متى يظهر الخطأ — قبل `MARK` أم بعدها؟** ثم شغّله بـ`LD_BIND_NOW=1`
وأعد السؤال. وما الذي يقوله الفرق عن ثمن التأجيل؟

**الفصل التالي:** الملفّ يحمل اسم `libgreet.so` بلا مسار، ونحن أعطيناه
`LD_LIBRARY_PATH=.` لنجده. فمن يبحث، وأين، وبأي ترتيب — ومن يقرّر أن يحمّله عند
عنوانٍ يتغيّر كل تشغيلة؟
