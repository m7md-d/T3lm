# الفصل ١٥ — الرمز والربط الساكن

جدول الأقسام أعطى البايتات أسماءَ أقسام. وداخل تلك الأقسام أسماءٌ من نوعٍ آخر:
`square` كتبتَه في ملفّ، و`square` استعملتَه في ملفٍّ ثانٍ. ومن قرّر أنهما واحد؟

الجواب في جدولٍ ثالث يحمله الملفّ الكائن: `.symtab`.

---

## أربعة أصناف في جدولٍ واحد

وحدة ترجمةٍ واحدة فيها دالّةٌ `static` ودالّةٌ عادية ودالّةٌ موسومةٌ بـ`weak`
ونداءٌ لـ`puts` الذي لم يُعرَّف هنا. اقرأ `.symtab` كما قرأتَ الأقسام:

<!-- part: 15-sym -->

```c
unsigned info = buf[o + 4], sx = U16(o + 6);   /* st_info · st_shndx */
unsigned b = info >> 4, t = info & 0xf;        /* binding · type     */
if (sx == SHN_UNDEF)       snprintf(where, n, "UND");
else if (sx == SHN_COMMON) snprintf(where, n, "COMMON");
else                       snprintf(where, n, "%u", sx);
```

**المخرَج**

<!-- out @env: binutils 2.44 · gcc 14.2 · aarch64 -->

```
$ ./symread unit.o
name       bind    type    shndx
hidden     LOCAL   FUNC    1
shared     GLOBAL  FUNC    1
maybe      WEAK    FUNC    1
uninit     GLOBAL  OBJECT  4
greet      GLOBAL  FUNC    1
puts       GLOBAL  NOTYPE  UND

$ nm unit.o
0000000000000024 T greet
0000000000000000 t hidden
000000000000001c W maybe
                 U puts
0000000000000008 T shared
0000000000000000 B uninit
```

ثلاثةُ حقولٍ تحسم كل شيء:

| الحقل | يقول | وأثرُه عند الرابط |
|---|---|---|
| `binding` | `LOCAL` · `GLOBAL` · `WEAK` | من يُرى خارج الملفّ، ومن يُزاح |
| `type` | `FUNC` · `OBJECT` · `NOTYPE` | ما الشيء المسمّى |
| `shndx` | رقمُ قسمٍ، أو `UND`، أو `COMMON` | أين يسكن — و`UND` طلبٌ لا عرض |

فـ`hidden` بـ`static` صار `LOCAL`: موجودٌ في الجدول ليقرأه المنقّح، ولا يُعرَض
للربط. و`puts` مذكورٌ بلا قسمٍ وبلا نوع: هذا الملفّ **يطلبه** ولا يقدّمه.

وحروف `nm` اختصارٌ للجدول نفسه: صغيرةٌ للمحلّيّ، وكبيرةٌ للعامّ، و`U` للمطلوب،
و`W` للضعيف، و`B` لما يسكن `.bss`. والفاحص يقارن الحرفَ بما قرأناه من البنية.

⚠ وسترى في الجدول رموزاً بأسماء `$x` و`$d` رشّحها البرنامج قبل الطباعة: علاماتُ
ترسيمٍ يفرضها ABI الـaarch64 على ELF لتفصل الكود عن البيانات داخل القسم الواحد.

## التعريف المؤقّت: أين تنتهي اللغة ويبدأ المترجم

`int counter;` في نطاق الملفّ بلا قيمةٍ ابتدائية **تعريفٌ مؤقّت**
(tentative definition، ISO C §6.9.2). وداخل وحدة الترجمة حكمُه واضح: إن لم يظهر
لها تعريفٌ آخر، فكأنّ لها قيمةً ابتدائيةً صفراً.

والسؤال يبدأ حين تتكرّر في وحدتين. وهنا نصّان يجب ألّا يختلطا:

| الطبقة | ماذا تقول |
|---|---|
| **ISO C §6.9p5** | للاسم ذي الربط الخارجيّ المستعمَل **تعريفٌ خارجيٌّ واحد** في البرنامج |
| **ISO C ملحق J.5.11** | وتعدُّدُ التعاريف الخارجية **امتدادٌ شائع** موصوف، لا ضمانٌ في اللغة |
| **المترجم** | يختار أيَّ الوجهين ينفّذ، ويُعلن اختياره في راية |

<!-- part: 15-common -->

```c
/* a.c */  int counter;   void bump(void);
/* b.c */  int counter;   void bump(void) { counter += 7; }
```

**المخرَج**

<!-- out @impl: gcc 14.2؛ والافتراض راية يعلنها المترجم -->

```
$ cc -Q --help=common | grep -w -- -fcommon
-fcommon [disabled]

$ cc -o prog a.o b.o                 # الافتراض هنا
ld: b.o:(.bss+0x0): multiple definition of `counter'; a.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status

$ cc -fcommon -o prog ac.o bc.o && ./prog
counter = 7

$ nm bc.o | grep counter        # -fcommon
0000000000000004 C counter
$ nm b.o  | grep counter        # الافتراض
0000000000000000 B counter
```

الحرف يقول القصّة. مع `-fcommon` يخرج الرمز `C`: **رمزٌ مشترك** لم يُوضَع في قسمٍ
بعد، والرابط يدمج ما تكرّر منه في كائنٍ واحد. ومع الافتراض يخرج `B`: تعريفٌ كاملٌ
في `.bss`، واثنان منه تعارضٌ يرفضه الرابط.

والبرنامج نفسه لم يتغيّر بين السطرين. الذي تغيّر **سياسةُ المترجم** — وهي تتحوّل
بين الإصدارات، فيصير كودٌ كان يُبنى بالأمس يُرفَض اليوم. ولذلك يسأل الفاحص
المترجمَ عن افتراضه ولا يفترضه عنه.

والصياغة التي لا تعتمد على الراية: `extern int counter;` في الوحدة الثانية —
إعلانٌ يطلب ولا يعرّف.

## الأرشيف، والترتيب

الرابط يقرأ ما تعطيه **من اليسار إلى اليمين**، ويحتفظ بقائمةِ أسماءٍ مطلوبةٍ لم
تُحَلّ بعد. والملفّ الكائن يدخل البناء كاملاً حين يُذكَر. أمّا الأرشيف `.a` فهو
رفٌّ من الملفّات الكائنة: يُفتَح، ويُؤخَذ منه العضو الذي يحلّ اسماً **مطلوباً
الآن**، ويُترَك سواه.

<!-- part: 15-order -->

```c
/* mainA.c */  int square(int);
               int main(void) { printf("square(7) = %d\n", square(7)); }
/* sq.c     */  int square(int x) { return x * x; }     →  ar rcs libsq.a sq.o
```

**المخرَج**

<!-- out @impl: GNU ld 2.44 — وهذه نتيجةُ هذا الرابط -->

```
$ ld --version | head -1
GNU ld (GNU Binutils for Debian) 2.44

$ cc -o A mainA.o -L. -lsq   &&  ./A
square(7) = 49

$ cc -o A2 -L. -lsq mainA.o
mainA.c:(.text+0xc): undefined reference to `square'

$ cc -o B mainB.o weak.o        &&  ./B
hook: the weak one
$ cc -o B2 mainB.o weak.o strong.o  &&  ./B2
hook: the strong one
$ cc -o B3 mainB.o strong.o weak.o  &&  ./B3
hook: the strong one
```

في السطر الثاني فُتح الأرشيف قبل أن يُطلَب `square`، فلم يُؤخَذ منه شيء. ثم جاء
`mainA.o` وطلبه، وقد مضى الرفّ. الملفّان أنفسهما، والترتيب وحده فرّق.

والمقارنة تكمل الصورة: `B2` و`B3` يعطيان الجواب نفسه. الملفّات الكائنة تدخل
كلُّها مهما رُتِّبت، فالتعريف القويّ يزيح الضعيف بلا نظرٍ إلى موضعه في السطر.
**فالترتيب يخصّ الأرشيف** لأنه اختيارٌ من رفّ، لا ضمّاً لملفّ.

⚠ واللوحة من `ld` بإصدارٍ مذكور. وترتيبُ الحلّ واختيارُ الأعضاء من تنفيذ الرابط،
و`lld` و`mold` لم يُشغَّلا هنا فلا يُنسَب إليهما شيء.

## التمرين

في `programs/15-order` أضف إلى الأرشيف عضواً ثانياً `unused.c` فيه دالّةٌ لا
يناديها أحد، وضع فيها `printf` عند الترجمة يعرّفك أنها دخلت.

هل تظهر في `nm A`؟ ثم أضف نداءً لها في `mainA.c` وأعد الربط. **ما الذي تغيّر في
حجم الملفّ التنفيذيّ؟** ثم فسّر بجملةٍ لماذا يصغر برنامجٌ يربط أرشيفاً كبيراً.

**الفصل التالي:** كل ما مضى انتهى بملفٍّ واحدٍ مكتفٍ بنفسه. وبرامجُ جهازك ليست
كذلك: `ldd` على أيٍّ منها يعدّ مكتباتٍ تسكن خارجه. فماذا يبقى في الملفّ حين
يُترَك الرمز بلا حلّ؟
