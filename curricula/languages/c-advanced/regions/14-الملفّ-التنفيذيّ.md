# الفصل ١٤ — الملفّ التنفيذيّ

الاتفاق الذي قرأتَه في الفصل السابق مكتوبٌ في وثيقة، وأثرُه محفوظٌ في ملفٍّ على
قرصك: أينَ يبدأ الكود، وأيُّ بايتاتٍ تُنسخ إلى الذاكرة، وبأيّ أذون.

والبديهية الثامنة تقول إنّ ذلك الملفّ بنيةُ بيانات. والبنيةُ تُقرأ.

---

## اقرأها بنفسك، ثم اسأل الأداة

`readelf` يقرأ الملفّ ويعرض ما فيه. وهو يقرأ **عنك**، فتبقى البنية عنده لا عندك.
والفصل يبدأ من الطرف الآخر: افتح الملفّ `fopen`، واقرأ بايتاته، وفكّكها بإزاحاتٍ
مكتوبةٍ في gABI.

<!-- part: 14-elf -->

```c
/* إزاحاتٌ من gABI، لا حقولٌ من <elf.h> */
#define E_ENTRY 24
#define E_SHOFF 40
#define E_SHNUM 60

static unsigned long long rd(long off, int n) {       /* عددٌ صغيرُ النهاية */
    unsigned long long v = 0;
    for (int i = n - 1; i >= 0; i--) v = (v << 8) | buf[off + i];
    return v;
}

long sh = shoff + i * shent;                     /* ترويسة القسم رقم i */
unsigned long ty = U32(sh + SH_TYPE);            /* 1 = PROGBITS · 8 = NOBITS */
const char *nm = (const char *) buf + strtab + U32(sh + SH_NAME);
```

**المخرَج**

## قسمٌ وsegment: جدولان، وقارئان

الملفّ يحمل جدولين يصفان البايتات نفسها. ولكلٍّ منهما قارئٌ آخر:

| | القسم (section) | الـsegment |
|---|---|---|
| من يقرأه | الرابط، حين يبني الملفّ | المحمّل، حين يشغّله |
| ما يحمله | اسمٌ ونوعٌ ووحدةُ ربط | مدًى يُنقَل إلى الذاكرة بإذنٍ واحد |
| موضعُ وصفه | جدول ترويسات الأقسام | جدول ترويسات الـsegments |
| عددُه هنا | ٢٩ | ١٠، منها اثنان من نوع `PT_LOAD` |

فتسعةٌ وعشرون قسماً تسكن `PT_LOAD`ين. و`.text` و`.rodata` في الأوّل لأن قراءتهما
وتنفيذهما بإذنٍ واحد `r-x`، و`.data` و`.bss` في الثاني `rw-`.

**والاسم للرابط.** أمّا المحمّل فينظر إلى الإزاحة والعنوان والحجم والأذون: ينسخ
مدًى من الملفّ إلى مدًى في الذاكرة. `.text` عنده بايتاتٌ في `PT_LOAD` الأوّل.

---

## `.bss`: حجمٌ في الذاكرة، وصفرُ بايتٍ في الملفّ

قسمٌ من نوع `SHT_NOBITS` يقول: لي حجمٌ وعنوان، ولا بايتات لي في الملفّ. وحجمه
هنا ٢٤ بايتاً، ومع ذلك:

| الحقل | القيمة | ماذا يعني |
|---|---|---|
| `sh_size` | `0x18` | ٢٤ بايتاً في صورة الذاكرة |
| `sh_addr` | `0x20098` | وعنوانُها هناك |
| `sh_offset` | `0x10098` | موضعٌ مسجَّل في الملفّ — **وليس محجوزاً** |

وبرهانُ السطر الأخير في اللوحة نفسها: `.comment` يبدأ عند `0x10098`. البايتات
التي «يشير» إليها `.bss` يملكها قسمٌ آخر فعلاً.

**فمن أين تأتي الأصفار؟** من الفرق `memsz - filesz` في الـ`PT_LOAD` الثاني:
`0x2f0 - 0x2d8 = 0x18`. المحمّل ينسخ `filesz` بايتاً من الملفّ، ثم يمدّ الـmapping
إلى `memsz` بصفحاتٍ مجهولة — وهي التي تصل إليك مصفَّرة (الفصل `02`).

وهذا يشرح ما يبدو مصادفةً: متغيّرٌ عامٌّ بلا قيمةٍ ابتدائية يبدأ بصفر لأن الصفحة
التي سكنها جاءت مصفَّرة، لا لأنّ أحداً كتب أصفاراً في ملفّك.

## والدليل الحاسم: امحُ جدول الأقسام

إن كانت الأقسام للرابط والـsegments للمحمّل، فبرنامجٌ فقد جدول أقسامه يجب أن
يعمل. خذ نسخةً واكتب أصفاراً في ثلاثة حقولٍ من ترويسة ELF:

<!-- part: 14-shdr -->

```c
unsigned char zero[8] = { 0 };
fseek(f, 40, SEEK_SET); fwrite(zero, 1, 8, f);   /* e_shoff    */
fseek(f, 60, SEEK_SET); fwrite(zero, 1, 2, f);   /* e_shnum    */
fseek(f, 62, SEEK_SET); fwrite(zero, 1, 2, f);   /* e_shstrndx */
```

**المخرَج**

<!-- out @env: نفس البيئة؛ والحجم يتبع هذا البناء -->

```
$ ./hello   ;   ./blind
hello, and pad[7] = x
hello, and pad[7] = x

sections   hello 30   blind 0
PT_LOAD    hello 2   blind 2
file size  hello 70488   blind 70488   (bytes, unchanged)

$ readelf -SW blind | head -2

There are no sections in this file.
```

`readelf` يقول إنّ الملفّ بلا أقسام، والبرنامج يعمل ويطبع سطرَه. لم يتغيّر حجم
الملفّ بايتاً: البايتات في مواضعها، والذي سقط **وصفُها**.

⚠ والذي يخسره الملفّ بهذا حقيقيّ: `nm` و`objdump -d` والمنقّح ورسائل الأعطال —
كلُّها تقرأ الأقسام. والتشغيل وحده لا يحتاجها.

## Mach-O: الطبقتان نفسُهما، بالاسم

على macOS الصيغة Mach-O، والتقسيم نفسه — إلّا أنّ الاحتواء مكتوبٌ صراحةً: كل
قسمٍ يذكر اسم الـsegment الذي يسكنه.

<!-- shell -->

```
$ cc -std=c17 -o hello hello.c && otool -l hello
  segname __DATA
   vmaddr 0x0000000100008000
   vmsize 0x0000000000004000
  fileoff 0
 filesize 0
Section
  sectname __bss
   segname __DATA
      addr 0x0000000100008000
      size 0x0000000000001000
    offset 0
     flags 0x00000001
```

⚠ **هذه اللوحة من مضيف المختبر** — macOS على arm64 بـApple clang ١٧ — لا من
الحاوية، وخارج الفاحص الآليّ.

| | ELF | Mach-O |
|---|---|---|
| وحدة الرابط | section باسمٍ مثل `.data` | section باسمٍ مثل `__bss` |
| وحدة المحمّل | segment من نوع `PT_LOAD` | segment باسمٍ مثل `__DATA` |
| الاحتواء | يُستنتَج من تطابق المديات | مكتوبٌ في كل قسم: `segname` |
| «بلا بايتاتٍ في الملفّ» | `SHT_NOBITS` | `S_ZEROFILL` بالراية `0x1` |

و`__DATA` هنا يقول `filesize 0` و`vmsize 0x4000`: أربع صفحاتٍ في الذاكرة بلا
بايتٍ واحدٍ خلفها في الملفّ. وهو الفرق `memsz - filesz` نفسه.

## التمرين

في `programs/14-shdr/hello.c` غيّر `static char pad[4096];` إلى
`static char pad[4096] = { 1 };`، ثم أعد الترجمة و`wc -c` الملفّ.

كم كبر؟ وفي أيّ قسمٍ صار `pad` الآن، وما نوعه؟ ثم اجعل القيمة الابتدائية
`{ 0 }` بدل `{ 1 }` وأعد القياس: **أين استقرّ هذه المرّة، ولماذا؟**

**الفصل التالي:** جدول الأقسام يعطي البايتات أسماءَ أقسام. وداخل تلك الأقسام
أسماءٌ من نوعٍ آخر: `printf` في ملفّك، و`printf` في مكانٍ لم تكتبه. ومن قرّر
أنهما واحد؟
