# الفصل ٢٤ — نموذج ذاكرة C

القفل في الفصل السابق نقل الحالة سليمةً بين الخيوط. وحين تريد نقلها بلا قفل
تحتاج أن تعرف ما الذي تضمنه اللغة بالضبط — لا ما يفعله معالجُك اليوم.

والمفردات أربع، وكلُّها معرَّفةٌ في ISO C §5.1.2:

| المصطلح | ما هو |
|---|---|
| `sequenced-before` | ترتيبٌ بين تقييمين **داخل خيطٍ واحد** — ما يعرفه كودُك عن نفسه |
| `modification order` | لكل كائنٍ ذرّيّ ترتيبٌ كلّيٌّ لتعديلاته، تتّفق عليه الخيوط كلُّها |
| `synchronizes-with` | علاقةٌ **بين خيطين**: عمليةُ release تتزامن مع عمليةِ acquire بشرط |
| `happens-before` | ما يُبنى من الأولى والثالثة بالتعدّي — وهو الذي يحسم ما تراه |

**والأخيرة هي الحكم.** الوصولان اللذان لا يرتّبهما `happens-before` إمّا data race
(الفصل `21`) وإمّا قراءةٌ لا تضمن شيئاً.

---

## تمرير رسالة: ثلاث صياغات

الكاتب يضع البيانات ثم يرفع العلم. والقارئ يرى العلم ثم يقرأ البيانات. والسؤال:
متى يضمن له النموذج أنّ البيانات وصلت؟

<!-- runs: 24-mp -->

```c
/* relaxed  */ store(&data,42,relaxed);  store(&flag,1,relaxed);
/* release  */ store(&data,42,relaxed);  store(&flag,1,release);
/* fences   */ store(&data,42,relaxed);  thread_fence(release); store(&flag,1,relaxed);
```

**المخرَج**

<!-- out @machine: aarch64 في حاوية؛ الأعداد تختلف بين تشغيلين -->

```
120000 rounds: writer sets data then flag; reader spins on flag then reads data

relaxed / relaxed        message seen   72658   flag without data      0   flag never read   47342
release / acquire        message seen   68956   flag without data      0   flag never read   51044
release fence / acquire fence message seen   67928   flag without data      0   flag never read   52072

relaxed rounds that saw flag=1 with data=0: 0
```

الصفّان الثاني والثالث **مفحوصان**: العمود الأوسط صفرٌ، وهو ثابتٌ يفرضه النموذج.
سقوطُه يُفشِل اللوحة.

**والاتجاه واحد.** الصفر هنا لا يُنشئ الضمان ولا يقوّيه؛ مصدرُه §5.1.2.4 وحدها.
وما يستطيعه التشغيل أن **يكذّب** تنفيذاً خالف، ولا يستطيع أن يُثبت مطابقته.

**والصفّ الأوّل ليس مفحوصاً، ولا يُقرأ برهاناً.** النموذج **يجيز** لـrelaxed أن
تُظهر العلم بلا البيانات، وهذه الآلة لم تُظهرها في مئةٍ وعشرين ألف جولة. والقاعدة من
الفصل `21`: الغياب في التشغيل ليس منعاً. **والمسموح والممنوع من النموذج، والتشغيل
شاهدٌ على ما ظهر.**

⚠ ولذلك لا يُصرَّح هنا بشيءٍ عن relaxed: لا أنها آمنة، ولا أنها فشلت.

## الشرط الذي يُنسى: الـacquire يجب أن **تقرأ** القيمة

العمود الأخير في اللوحة — «العلم لم يُقرأ» — يحمل نصف الدرس. في تلك الجولات
نفّذ القارئ عمليةَ acquire كاملة، ولم يتزامن معها شيء.

**فوجودُ release في خيطٍ وacquire في آخر لا ينشئ تزامناً.** والشرط في التعريف:

> عمليةُ release على الكائن `M` تتزامن مع عمليةِ acquire على `M` **إذا قرأت
> الثانية القيمة التي كتبتها الأولى** — أو قيمةً من **سلسلة الإطلاق**
> (release sequence) التي تبدأ بها.

وسلسلة الإطلاق هي تلك الكتابة، وما يليها في ترتيب تعديل `M` ممّا كتبه الخيط
نفسه، أو ما كتبته عمليات read-modify-write من أي خيط.

| الحالة | هل وقع تزامن |
|---|---|
| الـacquire قرأت `1` التي كتبتها الـrelease | نعم — و`data` مضمونة |
| الـacquire قرأت `0` الابتدائية | لا — ولا تدّعي شيئاً عن `data` |
| الـacquire على كائنٍ **آخر** غير الذي أُطلق | لا — العلاقة على كائنٍ بعينه |

**ولهذا تُكتب الحلقة.** القارئ يعيد القراءة حتى يقرأ قيمة الكاتب؛ وبدونها يكون قد
نفّذ acquire بلا فائدة.

## الترتيبات الستّة، وما يطلبه كلٌّ منها

الترتيب وصفٌ لما تريده من النموذج. وترجمتُه إلى تعليمات شأن المترجم والمعمارية:

<!-- part: 24-orders -->

```c
int  ld_relaxed(void)  { return atomic_load_explicit(&x, memory_order_relaxed); }
int  ld_acquire(void)  { return atomic_load_explicit(&x, memory_order_acquire); }
void st_release(int v) { atomic_store_explicit(&x, v, memory_order_release); }
void fence_acquire(void) { atomic_thread_fence(memory_order_acquire); }
```

**المخرَج**

<!-- out @machine: aarch64، gcc 14.2 بـ‎-O2؛ وهذه كلفةُ تنفيذٍ لا دلالةُ لغة -->

```
$ objdump -d orders.o   — the instruction each order asked for
ld_relaxed     ldr
ld_consume     ldar
ld_acquire     ldar
ld_seqcst      ldar
st_relaxed     str
st_release     stlr
st_seqcst      stlr
rmw_relaxed    __aarch64_ldadd4_relax
rmw_acqrel     __aarch64_ldadd4_acq_rel
rmw_seqcst     __aarch64_ldadd4_acq_rel
fence_release  dmb ish
fence_acquire  dmb ishld
fence_seqcst   dmb ish
```

| الترتيب | ما يعِد به | ويُطلَب على |
|---|---|---|
| `relaxed` | ذرّيةُ العملية وترتيبُ تعديل الكائن، **ولا ترتيبَ مع غيره** | تحميلٌ عاديّ |
| `consume` | اعتمادُ البيانات — نيّةٌ لم تنجح | تُرقّى acquire عملياً |
| `acquire` | ما بعدها لا يسبقها، وترى ما أطلقه من قرأتَ منه | تحميلٌ مرتَّب |
| `release` | ما قبلها لا يتأخّر عنها، ويصير مرئياً لمن قرأ | تخزينٌ مرتَّب |
| `acq_rel` | الاثنان معاً على عملية read-modify-write | روتينُ تعديلٍ مرتَّب |
| `seq_cst` | زيادةً على ذلك: **ترتيبٌ كلّيٌّ واحد** لكل عمليات `seq_cst` | هنا كما acquire/release |

**و`relaxed` تُترجَم إلى تحميلٍ عاديّ.** هذا هو الشاهد المشروع على أنّ البرنامج
لم يطلب ترتيباً: لا أنّ العتاد سيعيد الترتيب، بل أنّ الكود لم يمنعه.

⚠ و`consume` أعطت `ldar` نفسها هنا. نيّتُها كانت أرخص من acquire على معمارياتٍ
ضعيفة الترتيب، وتعريفُها بالاعتماد لم يصمد للتنفيذ، فأصدرت اللجان توجيهاً بتجنّبه.
**وترقيتُه إلى acquire اختيارُ تنفيذ**، والنصّ يصف شيئاً آخر.

**والحاجز أداةٌ لا ترتيبٌ سابع.** `atomic_thread_fence` يفصل الترتيب عن العملية:
تكتب تخزيناً relaxed وتضع الحاجز قبله، فتحصل على ما تحصل عليه من `release` — وهو
الصفّ الثالث في لوحة تمرير الرسالة، وقد نجح كما نجح الثاني.

## و`volatile` ليس تزامناً

الكلمة يُظنّ بها أنها تمنع التحسين فتكفي للمشاركة. وهي تمنع المترجم من حذف
الوصول أو دمجه، **ولا تفعل شيئاً من الثلاثة المطلوبة**: لا تجعل العملية ذرّية،
ولا تنشئ `happens-before`، ولا تمنع إعادة الترتيب مع وصولٍ آخر.

<!-- runs: 24-volatile -->

```c
static volatile int n;   for (int i = 0; i < 100000; i++) n++;
static _Atomic  int n;   atomic_fetch_add_explicit(&n, 1, memory_order_relaxed);
```

**المخرَج**

<!-- out @ub: نسخةُ volatile فيها data race؛ ورقمُها مسجَّلٌ لا موعود -->

```
$ under -fsanitize=thread
volatile int           data race reported
_Atomic int            silent, printed 200000

$ without the detector, two threads x 100000 increments
volatile int           101266
_Atomic int            200000
```

الكاشف يحسم الادّعاء: النسخة الأولى **ما زالت** data race بتعريف §5.1.2.4، و
`volatile` لم تغيّر شرطاً من شروطه الأربعة.

والرقم `101266` مسجَّلٌ لا موعود: البرنامج خرج من ضماناته، فلا يُحسَب له «أسوأ
حالة» ولا يُقارَن رقمُه بشيء. **والمقارنة المشروعة في اللوحة** أنّ النسخة
الذرّية أعطت العدد الذي طلبه البرنامج.

⚠ و`volatile` تبقى أداةً لموضعها: ذاكرةُ أجهزةٍ يتغيّر محتواها خارج البرنامج،
والوصولُ الذي يجب ألّا يُحذَف. وذلك غيرُ التزامن.

## التمرين

في `programs/24-mp/mp.c` أضف صيغةً رابعة: `seq_cst` في الطرفين، وقارن أعمدتها
بأعمدة `release/acquire`.

كائنين مختلفين بـ`seq_cst` وانظر التعليمات. وما الذي يشتريه الترتيب الكلّيّ فوق
release/acquire — ومتى تحتاجه فعلاً؟

**الفصل التالي:** عرفتَ ما تضمنه العمليات الذرّية. وبناءُ بنيةٍ مشتركةٍ بها يفتح
مشكلاتٍ لا تحلّها العمليةُ الذرّية وحدها.
