# الفصل ٢٥ — بلا قفل

العمليات الذرّية تضمن ما قاله الفصل السابق. وبناءُ بنيةٍ مشتركةٍ بها يفتح أربع
مشكلاتٍ منفصلة، وخلطُها في مثالٍ واحد هو ما يجعل الموضوع يبدو غامضاً:

| # | المشكلة | يحلّها |
|---|---|---|
| ١ | ماذا ترجع `compare_exchange` بالضبط، وماذا تكتب في `expected` | فهمُ العقد |
| ٢ | `weak` أم `strong`، وترتيبان لا واحد | اختيارٌ في موضعه |
| ٣ | مؤشّرٌ عاد إلى قيمته وقد تغيّر ما تحته — **ABA** | وسمٌ يرافق المؤشّر |
| ٤ | متى يصحّ تحرير العقدة — **إعادة التدوير** | خارج هذا الفصل، ويُعلَن |

---

## ١ — العقد، و«ذرّيّ» لا تعني «بلا قفل»

<!-- part: 25-cas -->

```c
long expected = 3;
int ok = atomic_compare_exchange_strong(&y, &expected, 9);   /* وy تساوي 5 */
```

**المخرَج**

<!-- out @impl: gcc 14.2 على aarch64، بلا ‎-march يرفع الأساس -->

```
atomic_is_lock_free   int 1   long 1   16-byte struct 0   32-byte struct 0
strong CAS, expected 3 against 5: returned 0, expected now 5, object still 5
weak CAS with no contention: 0 retries in 3000000 attempts
```

السطر الثاني يحمل العقد كلَّه: العملية فشلت، **وكتبت القيمة الحالية في
`expected`**، وتركت الكائن كما هو. ولهذا تُكتَب الحلقة بلا إعادة قراءة:

```c
long cur = atomic_load(&y);
while (!atomic_compare_exchange_weak(&y, &cur, f(cur))) { }   /* cur مُحدَّثة */
```

والسطر الأوّل يهدم اعتقاداً: **`_Atomic` صفةٌ على المعنى قبل أن تكون وعداً بالتنفيذ.**
بنيةٌ من ستّة عشر بايتاً `_Atomic` تعمل صحيحةً، وتنفيذُها هنا قفلٌ داخل
مكتبةٍ تُربَط بـ`-latomic`. فإن كان الـlock-free شرطاً في تصميمك، اسأل
`atomic_is_lock_free` ولا تفترضه من الصفة.

---

## ٢ — `weak` و`strong`، وترتيبان

`compare_exchange_weak` يجوز أن تفشل **وقيمةُ الكائن مطابقة**. هذا مسموحٌ ليُبنى
على حلقات LL/SC حيث يقطع أيُّ حدثٍ وسيطٍ المحاولة.

| | `weak` | `strong` |
|---|---|---|
| الفشل الكاذب | جائز | ممنوع |
| موضعها | **داخل حلقةٍ تعيد المحاولة** | حين لا تريد حلقةً |
| الكلفة | أرخص على معمارية LL/SC | قد تخفي حلقةً بداخلها |

⚠ واللوحة أعلاه سجّلت صفر فشلاً كاذباً في ثلاثة ملايين محاولة. **وهذا شاهدٌ لا
قاعدة**: هذا البناء يستعمل روتيناً يختار تعليمة `cas` الواحدة حين يدعمها المعالج،
ولا فشلَ كاذبٌ فيها. وغيابُه هنا لا يرفع الإذن، والحلقة تبقى.

ولكلّ `compare_exchange` ترتيبان: واحدٌ للنجاح — وهي عملية read-modify-write
حينئذٍ — وواحدٌ للفشل، وهي قراءةٌ فقط. ولذلك يقيّد المعيار الثاني، والمترجم يقول لك:

```c
#include <stdatomic.h>
int main(void) {
    _Atomic int x = 0;
    int e = 0;
    return atomic_compare_exchange_strong_explicit(
        &x, &e, 1, memory_order_acq_rel, memory_order_acq_rel);
}
```

<!-- warn -->

```
warning: invalid failure memory model ‘memory_order_acq_rel’ for ‘__atomic_compare_exchange_4’
note: valid failure models are ‘memory_order_relaxed’, ‘memory_order_seq_cst’, ‘memory_order_acquire’, ‘memory_order_consume’
```

**فترتيب الفشل لا يكون `release` ولا `acq_rel`**، لأن العملية الفاشلة لا تكتب
شيئاً فلا معنى لإطلاقٍ فيها.

## ٣ — ABA: القيمة عادت، والمعنى تغيّر

مكدّس Treiber: الرأس مؤشّر، والـ`pop` تقرأ الرأس وتاليه ثم تبدّل. وبين القراءة
والتبديل قد يجري العالم كلُّه.

<!-- part: 25-aba -->

```c
unsigned long h = atomic_load(&head);
int i = slot_of(h);
int next = pool[i].next;
/* … هنا يعمل خيطٌ آخر … */
atomic_compare_exchange_strong(&head, &h, pack(next, tag_of(h) + 1));
```

**المخرَج**

<!-- out @impl: التداخل مثبَّتٌ بحاجزين، فالنتيجة تتكرّر -->

```
stack C -> B -> A; one thread pauses mid-pop while another
pops two nodes and pushes the first one back

untagged  popped: B C   still on the stack: B A   (1 counted twice, 0 lost)
tagged    popped: B C   still on the stack: A   (0 counted twice, 0 lost)
```

في السطر الأوّل ظهرت `B` **مرّتين**: سُلِّمت لخيطٍ بوصفها منتزَعة، وهي في الوقت
نفسه على المكدّس. الـCAS نجحت لأن الرأس كان يساوي ما قرأه الخيط البطيء — وهو
`C`، وقد عاد إلى الرأس بعد أن غادره.

**والـCAS تقارن قيمةً لا تاريخاً.** فالمعالجة أن تُضاف إلى القيمة معلومةٌ تتغيّر
مع كل تعديل: عدّادٌ يرافق المؤشّر في الكلمة نفسها. والسطر الثاني نتيجتُه.

### والوسم حدٌّ، لا حلٌّ غيرُ محدود

العدّاد يدور. فإذا بلغ سعته وعاد إلى قيمةٍ رآها الخيط البطيء، عاد ABA كما كان:
**الوسم يجعل الحالة نادرةً بقدر عرضه، ولا يمنعها رياضياً.**

| ما يقرّره العرض | في هذا المثال |
|---|---|
| كم تعديلاً قبل الدوران | ٣٢ بت ⇒ نحو أربعة مليارات تعديلٍ على الرأس |
| ما الذي يجعلها محسوسة | وسمٌ ضيّق، أو خيطٌ يتوقّف طويلاً بين قراءته وتبديله |
| والحدّ الأعلى للعرض | ما تسع له عمليةُ التبديل الذرّية عندك |

⚠ والوسم هنا في النصف العلويّ من كلمةٍ من ٦٤ بت، والعقد **فهارس** في مجموعةٍ
ثابتة. ولو كان الرأس مؤشّراً كاملاً لاحتجتَ تبديلاً بعرضٍ مضاعف — وقد رأيتَ في
اللوحة الأولى أنه ليس lock-free في هذا البناء.

## ٤ — وإعادة التدوير مشكلةٌ مستقلّة

نجاحُ الخوارزمية لا يجعل `free(node)` آمناً. الخيط البطيء في اللوحة أعلاه كان
يحمل فهرس عقدةٍ ويقرأ `next` منها **بعد** أن انتزعها خيطٌ آخر. ولو كانت العقدة
ذاكرةً محرَّرة لكانت تلك قراءةً لذاكرةٍ عادت إلى الـallocator.

| السؤال | جوابه هنا |
|---|---|
| هل نجت البنية من هذا السيناريو بالوسم | نعم — واللوحة تفحص هذا السيناريو وحده |
| هل صارت البنية آمنةً في كل شيء | **لا**: الوسم يخصّ ABA، ومحدودٌ بعرضه |
| هل يجوز تحرير عقدةٍ بعد انتزاعها | **لا يُعرَف** من الخوارزمية وحدها |
| ما الذي يجعله معلوماً | إجراءٌ يثبت أنّ لا خيطَ يحمل إشارةً إليها |

**ومثالُ هذا الفصل يتجنّب المشكلة ولا يحلّها.** والقيد صريح: العقد ثلاثٌ في
مصفوفةٍ ساكنة، **ولا تُحرَّر ولا يُعاد تدويرها أثناء التنافس** — فلا لحظةَ يقرأ
فيها خيطٌ `next` من عقدةٍ عادت إلى المخصِّص. ولذلك لا تشهد اللوحة على
إعادة التدوير بشيء، سلباً ولا إيجاباً.

وهذا خيارٌ مشروع في تصميمٍ حقيقيّ — مجموعةٌ بحجمٍ معلوم لا تُعاد إلى النظام —
ويبقى قيداً يُعلَن مع التصميم.

والحلول العامّة لها أسماء — hazard pointers، وepoch-based reclamation — **وهي
خارج هذا المنهج**، ولا تُختصَر في فقرة.

## التمرين

في `programs/25-aba.c` احذف الوسم من الدفع وحده وأبقِه في الانتزاع، ثم أعد
السيناريو.

هل يكفي نصفُ العلاج؟ ثم اجعل الوسم ثمانية بتات بدل اثنين وثلاثين، وشغّل
السيناريو في حلقةٍ طويلة. متى يعود ABA؟ وما الذي يقوله ذلك عن عرض الوسم
المطلوب؟

**الفصل التالي:** اجتمعت الحِزَم الأربع. والختام مشروعٌ واحد يجمعها: allocator
يُستعمَل من خيوطٍ كثيرة، ثم يُبنى مكتبةً ويحلّ محلّ `malloc` تحت برنامجٍ حقيقيّ —
وهو الوعد الذي قطعه الفصل `00`.
