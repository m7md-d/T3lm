# الفصل ١٨ — `dlopen` وعقد الإضافة

كل ما مضى وقع قبل `main` أو عند أوّل نداء. والمحمّل في الحالتين كان ينفّذ ما
كُتب في الملفّ: أسماءٌ في `NEEDED`، ومواضعُ محجوزةٌ في `.got`.

وهذا الفصل يفتح باباً ثالثاً: أن يطلب برنامجُك ملفّاً لم يُذكَر في الملفّ أصلاً،
بعد أن بدأ العمل، ويسأل عن رمزٍ باسمه نصّاً.

---

## ملفٌّ لا يعرفه الملفّ

<!-- part: 18-dlopen -->

```c
void *h = dlopen("./libplug.so", RTLD_NOW);
int (*fn)(int, int);
*(void **) &fn = dlsym(h, "add");         /* الصيغة التي يوصي بها POSIX */
printf("add(3,4) = %d\n", fn(3, 4));
dlclose(h);
```

**المخرَج**

<!-- out @impl: glibc 2.41 على لينكس -->

```
$ readelf -dW probe | grep NEEDED
0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
$ ./probe
before dlopen: mapped=0
after  dlopen: mapped=1
add(3,4) = 7
dlsym(nope) = (nil), dlerror = ./libplug.so: undefined symbol: nope
after  dlclose: mapped=0
```

الملفّ التنفيذيّ يسمّي `libc.so.6` وحدها. و`libplug.so` غيرُ مذكورةٍ فيه، ومع
ذلك دخلت فضاء العناوين وخرجت منه — والبرنامج يقرأ `/proc/self/maps` بنفسه ليريك
دخولها.

**والخطأ هنا قيمةٌ تُفحَص.** `dlsym` باسمٍ مجهولٍ يعطي مؤشّراً صفرياً، ويترك
الوصف في `dlerror`. فالفشل يصل إليك في وقت التشغيل بدل أن يُرفَض عند البناء.

⚠ وخروجُها عند `dlclose` سلوكُ هذا التنفيذ. POSIX يصف إنقاص عدّاد مراجع، ويترك
إفراغ الكائن لتنفيذٍ بعينه — وglibc تُبقي كائناتٍ بصفاتٍ معيّنة محمَّلةً بعدها.

⚠ و`-ldl` غير مذكورةٍ في أوامر هذا الفصل: منذ glibc 2.34 صارت هذه الواجهات في
`libc` نفسها. وعلى libc آخر قد تلزم الراية.

---

## `void *` إلى مؤشّر دالّة: سؤال سلطة

`dlsym` ترجع `void *`. والذي تريده مؤشّرُ دالّة. وبين الاثنين خلافٌ بين طبقتين:

| الطبقة | ماذا تقول |
|---|---|
| **ISO C §6.3.2.3** | تعرّف التحويل بين مؤشّر كائنٍ و`void *`، وتسكت عن مؤشّر الدالّة |
| **POSIX** | يوجب أن يعمل ما ترجعه `dlsym` مؤشّرَ دالّةٍ حين يكون الرمز دالّة |

والمترجم يرسم الحدّ بنفسه حين تسأله:

```c
//! cc: -pedantic
#define _GNU_SOURCE
#include <dlfcn.h>
int main(void) {
    void *h = dlopen("./libplug.so", RTLD_NOW);
    int (*fn)(int, int) = (int (*)(int, int)) dlsym(h, "add");
    return fn(1, 2);
}
```

<!-- warn -->

```
warning: ISO C forbids conversion of object pointer to function pointer type [-Wpedantic]
```

فالتحويل المباشر يعمل على هذه المنصّة، ويقول المترجم إنّ اللغة لا تضمنه. ولذلك
كُتبت برامج هذا الفصل بالصيغة الأخرى:

```c
int (*fn)(int, int);
*(void **) &fn = dlsym(h, "add");
```

وهي تنقل البايتات إلى موقع المؤشّر بدل أن تحوّل نوعاً إلى نوع. وهذه **حيلةٌ
تسكت المترجم**، والضمان يبقى من POSIX لا من اللغة: على منصّةٍ يختلف فيها عرض
مؤشّر الدالّة عن عرض `void *` تسقط الصيغتان معاً.

## عقد الإضافة: الرمز، أو الجدول

للمضيف طريقان إلى إضافته. أن يسأل عن كل دالّةٍ باسمها `dlsym`، أو أن يسأل عن
مدخلٍ واحدٍ يرجع بنيةً من مؤشّرات الدوال.

**والثاني تقنيةُ تصميمٍ فوق `dlopen`، لا متطلَّبٌ له.** والذي يشتريه ظاهر:
نداءٌ واحد لـ`dlsym` بدل عشرة، وموضعٌ واحد يُفحَص فيه التوافق. والذي يدفعه ثمناً
أنّ **تخطيط تلك البنية صار ABI** — بالمعنى الحرفيّ من الفصل `13`.

<!-- part: 18-abi -->

```c
struct api {                       /* عقد الإصدار ٢ */
    int version;
    unsigned size;                 /* sizeof كما رآه من بنى الإضافة */
    int (*add)(int, int);
    int (*mul)(int, int);
};
const struct api *get_api(void);   /* الاسم الوحيد الذي يسأل عنه المضيف */
```

**المخرَج**

<!-- out @abi: تخطيط البنية من ABI المنصّة؛ والأرقام من aarch64 -->

```
$ nm -D p_old.so p_new.so | grep get_api
p_old.so: 00000000000005a8 T get_api
p_new.so: 00000000000005c8 T get_api

$ ./host
./p_old.so   version 1  size 16  (host expects 2 / 24)
./p_old.so   refused: the struct it was built against is not mine
./p_new.so   version 2  size 24  (host expects 2 / 24)
./p_new.so   add(3,4)=7  mul(3,4)=12
```

الإضافتان تصدّران الاسم نفسه، ونوعُه في `nm` واحد: `T get_api`. ولا شيء في جدول
الرموز يقول إنّ إحداهما بُنيت على بنيةٍ من ١٦ بايتاً والأخرى على ٢٤.

**والمضيف يعرف لأنهما اتّفقا مسبقاً** على حقلين في صدر البنية: رقمِ إصدار وحجم.
ولو سقط هذا الاتفاق لقرأ المضيف `mul` من موضعٍ لم تكتبه الإضافة القديمة، ولقفز
إلى ما يجده هناك.

فترتيب الحقول والحشو بينها — وهي التي يقرّرها الـABI — صارت جزءاً من عقدٍ بين
ملفّين يُبنيان في وقتين مختلفين، وربّما بمترجمين مختلفين.

## ثلاث لحظاتٍ يُحَلّ فيها الرمز

| | الرابط الساكن | `ld.so` | `dlsym` |
|---|---|---|---|
| متى | البناء | التحميل، أو النداء الأوّل | حين يطلبه كودُك |
| ما المدخَل | جدول الرموز في الملفّات | `NEEDED` ونطاق البحث | سلسلةُ اسمٍ ومقبض |
| صيغة الفشل | خطأُ بناءٍ يوقف الرابط | رسالةٌ توقف التشغيل | مؤشّرٌ صفريّ و`dlerror` |
| من يملك القرار | تنفيذ الرابط | تنفيذ المحمّل | تنفيذ المحمّل، بطلبك |

الفرق بين الثاني والثالث أنّ الثاني **سياسة** تجري على ما أعلنه الملفّ، والثالث
**نداءٌ** تكتبه أنت وتفحص نتيجته. ولذلك تصلح الإضافات لبناءٍ لا يعرف أجزاءه
مسبقاً، ولذلك يصير الخطأ فيها شأن برنامجك لا شأن المحمّل.

## التمرين

في `programs/18-abi` احذف فحص `size` من `host.c` وأبقِ فحص `version` وحده، ثم
غيّر `p_old.c` ليقول `version` يساوي ٢ بينما بنيتُه من ١٦ بايتاً.

**ماذا يطبع المضيف الآن؟** شغّله تحت `-fsanitize=address` وانظر ماذا يقول. ثم
أعد الفحص المحذوف وفسّر بجملةٍ لماذا لا يكفي رقم الإصدار وحده.

**الفصل التالي:** انتهت الحزمة الثالثة. صار بين يديك الطريق من وحدة الترجمة إلى
عمليةٍ تعمل: اتفاقٌ يمرّر الوسائط، وملفٌّ يحمل بنيته، ورابطٌ يحلّ ما يقدر، ومحمّلٌ
يكمل الباقي. والحزمة القادمة تسأل عمّا يحدث حين يصير خيطُ التنفيذ اثنين — وأوّلُها
العتاد الذي تجري عليه.
