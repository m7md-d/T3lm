# الفصل ٠٠ — الخريطة والمصادر

أنهيتَ المنهج الأوّل و`shell` تعمل بين يديك. وفي طريقك إليها استعملتَ أشياءَ لم
تُفتَح: `malloc` أعطاك عنواناً ولم يقل من أين، والمترجم أنتج ملفّاً تنفيذياً ولم
تقرأ داخله، والنظام شغّله ولم تعرف كيف وصل إلى الذاكرة.

هذا الفصل يفتح الأغلفة ولا يشرح ما تحتها. كلُّ ما فيه سطرٌ واحد من فصلٍ قادم،
ومهمّته أن تدخل الفصول ومعك خريطةٌ تعلّق عليها.

وشرطُه على نفسه شرطُ الفصل صفر في المنهج الأوّل: لا شيء يُطلَب تصديقه. كل
ادّعاءٍ هنا معه برنامجٌ يعمل، ومخرَجُه منقولٌ كما خرج.

بيئة اللوحات — تُعلَن مرّةً وتنطبق على المنهج كلّه:

```
Debian 13.6 · gcc 14.2.0 · glibc 2.41 · Linux 6.12.76 · aarch64
```

وملفُّ بنائها في `lab/Dockerfile`. وما تغيّر بتغيّرها موسومٌ في موضعه.

## الخريطة كما تراها النواة

في المنهج الأوّل رُسمت العملية أربع مناطق: الكود، والثوابت، والـheap، والـstack.
ذلك الرسم كان كافياً حينها. وهذه هي الخريطة الحقيقية لبرنامجٍ يقرأ خريطة نفسه:

**البرنامج**

<!-- runs: 00-map -->

```c
FILE *f = fopen("/proc/self/maps", "r");
while (fgets(line, sizeof line, f)) fputs(line, stdout);
```

**المخرَج**

<!-- out @os: العناوين تتغيّر بين تشغيلين -->

```
aaaae2030000-aaaae2031000 r-xp 00000000 00:2d 27      /w/map
aaaae204f000-aaaae2050000 r--p 0000f000 00:2d 27      /w/map
aaaae2050000-aaaae2051000 rw-p 00010000 00:2d 27      /w/map
aaaafaeb7000-aaaafaed8000 rw-p 00000000 00:00 0       [heap]
ffffb5720000-ffffb58bc000 r-xp 00000000 00:35 820     libc.so.6
ffffb58bc000-ffffb58cd000 ---p 0019c000 00:35 820     libc.so.6
ffffb58cd000-ffffb58d0000 r--p 0019d000 00:35 820     libc.so.6
ffffb58d0000-ffffb58d2000 rw-p 001a0000 00:35 820     libc.so.6
ffffb58e7000-ffffb590f000 r-xp 00000000 00:35 800     ld-linux-aarch64.so.1
ffffb5921000-ffffb5923000 r--p 00000000 00:00 0       [vvar]
ffffb5923000-ffffb5925000 r-xp 00000000 00:00 0       [vdso]
ffffd5ef2000-ffffd5f13000 rw-p 00000000 00:00 0       [stack]
```

الوحدة هنا **mapping**؛ والرسم السابق كان يسمّيها منطقة. ولكلٍّ مدًى وأذوناتٌ
ثلاثة وملفٌّ خلفه أو لا شيء. وبرنامجُك الذي كتب سطراً واحداً يسكن ثلاثة mappings بأذونٍ مختلفة، وlibc
يسكن أربعة، وأحدها `---p` بلا إذنٍ أصلاً.

والأسئلة التي يفتحها هذا السطر الواحد توزّعت على الفصول: ما وحدةُ هذه الأذون
(`01`)، ومن أنشأها (`02`)، ولماذا `---p` (`04`)، وأين حدُّ الـ`[stack]` (`05`)،
ومن حمّل `libc` (`17`).

## من قرّر؟ — مصادر السلطة

في المنهج الأوّل كان السؤال «من قرّر: المواصفة أم المترجم؟». وهنا يتّسع، لأن
الأطراف صارت أكثر:

| المصدر | يقرّر |
|---|---|
| **ISO C** | ما تضمنه اللغة لأي تنفيذٍ مطابق |
| **POSIX** | ما تضمنه الواجهة على نظامٍ متوافق |
| **الـABI** | تمرير الوسائط والإرجاع والمحاذاة والسجلّات المحفوظة |
| **نظام التشغيل** | الـmappings والصفحات والاستدعاءات وسياساتها |
| **libc** | تنفيذ الواجهة في مكتبةٍ بإصدارٍ بعينه |
| **تنفيذ الـallocator** | البنى الداخلية والعتبات وسلوك التجزئة |
| **المترجم** | ما يختاره ضمن ما تسمح به المواصفة |
| **تنفيذ الـlinker والـloader** | ترتيب الحلّ واختيار أعضاء الأرشيف والافتراضات |
| **الـISA** | ضمانات ترتيب الوصول إلى الذاكرة، وتعليمات الـatomics |
| **الـmicroarchitecture** | حجم الـcache line وبنية الـcache والـstore buffers |

والقائمة مفتوحة. وأهمُّ ما فيها أنّ الادّعاء الواحد قد يتوزّع: تحدّد المواصفة
الضمان، ويقرّر تنفيذٌ بعينه الكيفية، وتقيّد طبقاتٌ أخرى النتيجة والثمن.

وكل لوحةٍ في هذا المنهج تحمل مصدرها: `@posix` و`@abi` و`@os` و`@impl` و`@env` —
وما بلا وسمٍ تضمنه ISO C.

## البديهية ٦ — العنوان لا يحدّد موضعاً في RAM

الـ`virtual address` يسمّي موضعاً في virtual address space الخاصّ بعمليّتك. ولا
يحدّد بنفسه موضعاً ثابتاً في RAM.

وبرهانُه: اربط الملفّ نفسه مرّتين. يعطيك النظام عنوانين مختلفين،
والذاكرة التي خلفهما واحدة.

**البرنامج**

<!-- runs: 00-shared -->

```c
char *a = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
char *b = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

strcpy(a, "written through a");
printf("b reads: %s\n", b);
```

**المخرَج**

<!-- out @posix: العناوين تتغيّر بين تشغيلين -->

```
a = 0xffffb17ca000
b = 0xffffb17c9000
a == b : no
b reads: written through a
```

عنوانان مختلفان، وكتابةٌ عبر أحدهما تظهر في الآخر. فالعلاقة بين العنوان والذاكرة
**mapping** يملكه النظام ويغيّره — وهذا ما تبنيه الفصول `01`–`03`.

## البديهية ٧ — الـallocator برنامجٌ عاديّ

`malloc` ليست تعليمةً في اللغة ولا خدمةً في النواة. هي **دالّةٌ في libc** كتبها
إنسان، ويمكن أن تحلّ محلّها دالّةٌ تكتبها أنت.

**البرنامج** — مخصِّصٌ كامل، يحجز من مصفوفةٍ ساكنة ولا يحرّر شيئاً:

<!-- runs: 00-alloc -->

```c
static char  arena[64u << 20];
static size_t off;

void *malloc(size_t n) {
    size_t need = (n + 15u) & ~(size_t)15;
    char *p = arena + off + 16;
    ((size_t *)p)[-1] = n;       /* حجمُنا نحن، في تخطيطٍ نعلنه */
    off += need + 16;
    return p;
}
void free(void *p) { (void)p; }
```

يُبنى مكتبةً ويوضع تحت برنامجٍ لا يعرف شيئاً عنه:

<!-- out @os: العنوان يتغيّر بين تشغيلين -->

```
من مخصِّصنا: 0xffffa90c0070
date under it:            works
objdump -d libc.so.6:     out of memory allocating 4064 bytes after a total of 0 bytes
mymalloc: 2 calls
```

ولاحظ السطر `((size_t *)p)[-1]`. يجوز هنا لأن نحن من وضع ذلك الحقل وأعلن
تخطيطه. وقراءةُ ما قبل مؤشّرٍ أعادته `malloc` الحقيقية شيءٌ آخر: خارج
حدود الكائن، وهو undefined behavior مهما صحّ التخمين. والفرق بينهما درسُ الفصل
`07`، وطريقُه المشروع هناك الـdebugger أو قراءة مصدر التنفيذ.

وهو يحمل `date` ولا يزيد. واللوحة تضعه تحت عملٍ حقيقيّ — `objdump -d` على
libc — فيقف عند أوّل طلبٍ لا يجد له موضعاً: المصفوفة نفدت، لأن `free` عندنا
لا تفعل شيئاً. والفصول `09`–`11` تقول ما الذي ينقص هذا العقد، **والفصل `26`
يبنيه حتى يحمل ذلك العمل**.

## البديهية ٨ — الملفّ التنفيذيّ بنيةُ بيانات

الملفّ الذي أنتجه المترجم ليس كتلةً معتِمة. هو بنيةٌ موصوفة في مواصفةٍ منشورة،
وتستطيع قراءتها بـ`fread`.

**البرنامج** — يقرأ أوّل ٦٤ بايتاً من نفسه:

<!-- part: 00-elf -->

```c
FILE *f = fopen("/proc/self/exe", "rb");
unsigned char h[64];
fread(h, 1, sizeof h, f);

printf("class   : %s\n", h[4] == 2 ? "ELF64" : "ELF32");
printf("type    : %u\n", (unsigned)(h[16] | h[17] << 8));
```

توقّع قبل أن تشغّل: ما الذي يطبعه حقل `type`؟

**المخرَج:**

<!-- gate @env: الترجمة على Debian تبني PIE افتراضاً، و‎0xb7 هو aarch64 -->

```
magic   : 7f ELF
class   : ELF64
type    : 3
machine : 0xb7
```

وأربعة أسطرٍ من أربعة مصادر. الحرفان الأوّلان تفرضهما مواصفة ELF. و`ELF64`
يقرّره الهدف. و`machine = 0xb7` هو `EM_AARCH64` — معمارية. أمّا `type = 3`
فهو `ET_DYN` لا `ET_EXEC`، وقرارُ سلسلة الأدوات: gcc على Debian يبني
`position-independent executable` افتراضاً. فالبرنامج الذي كتبتَه يُحمَّل كما
تُحمَّل المكتبة المشتركة — وذلك بابُ الفصل `17`.

## البديهية ٩ — بين المصدر والعملية مرحلتان

`translation units` تصير برنامجاً عبر مراحل لا يشرحها الـsource code. والـlinking
منها المرحلة الثامنة من الـtranslation بنصّ ISO C؛ أمّا الـloading فخارج اللغة
كلّها.

وثلاثة أوامر تُري المراحل الثلاث على برنامجٍ من سطرين:

<!-- runs: 00-link -->

```c
#include <stdio.h>
int main(void) { puts("hi"); return 0; }
```

**المخرَج**

<!-- out @os: العناوين تتغيّر بين تشغيلين، ورقمُ العملية مُزال -->

```
$ nm main.o
0000000000000000 T main
                 U puts
$ ldd hi
	linux-vdso.so.1 (0x0000ffff880d5000)
	libc.so.6 => /lib/aarch64-linux-gnu/libc.so.6 (0x0000ffff87ea0000)
	/lib/ld-linux-aarch64.so.1 (0x0000ffff88090000)
$ LD_DEBUG=bindings ./hi
binding file ./hi [0] to /lib/aarch64-linux-gnu/libc.so.6 [0]: normal symbol `puts' [GLIBC_2.17]
```

الحرف `U` يقول: المترجم أنهى عمله وهو لا يعرف أين `puts`. و`ldd` يقول من
سيُسأل. والسطر الثالث يقول إنّ الجواب لم يُحسم إلا بعد أن بدأ البرنامج.

وهذه المسافة — بين `U` وبين `binding` — هي الحزمة `13`–`18` كلّها.

## البديهية ١٠ — التزامن لا يعطي ترتيباً ضمنياً

خيطان، كلٌّ يكتب متغيّراً ثم يقرأ الآخر:

<!-- runs: 00-order -->

```c
/* الخيط ٠ */  atomic_store_explicit(&x, 1, memory_order_relaxed);
               r0 = atomic_load_explicit(&y, memory_order_relaxed);

/* الخيط ١ */  atomic_store_explicit(&y, 1, memory_order_relaxed);
               r1 = atomic_load_explicit(&x, memory_order_relaxed);
```

بالتفكير التسلسليّ: أحدهما كتب أوّلاً، فلا بدّ أن يرى الثاني كتابتَه. فحالة
`r0 == 0 && r1 == 0` مستحيلة.

توقّع قبل أن تشغّل: كم مرّةً تقع تلك الحالة في مئتَي ألف دورة؟

**المخرَج**

<!-- out @machine: على aarch64؛ والعدد يتغيّر بين تشغيلين — قِيس ٩١ و٢٣ و١٨٢ -->

```
r0 == 0 && r1 == 0  :  91 / 200000
```

والبرنامج سليم: كل الوصولات `atomic`، فلا data race فيه ولا undefined
behavior. وما رأيتَه **يجيزه C memory model** — لأن `memory_order_relaxed` لا يَعِد
بترتيب.

وثلاثة مصادر في نتيجةٍ واحدة: ISO C يقول ما الذي يجوز أن تراه، والـISA
يقول ما تضمنه المعمارية، والـmicroarchitecture تقول لماذا وقع الآن. والفصول `19`
و`21` و`24` تفصل الثلاثة.

⚠ والعدد ليس ثابتاً، وقد يكون صفراً على معماريةٍ أخرى — على x86-64 يندر ظهوره
بهذه المِرْقاة. **وغيابُ الملاحظة ليس ضماناً**، وهذا نصفُ الدرس.

## الطريق

أربع حِزَم، كلٌّ تفتح ما تركته السابقة:

| | | |
|---|---|---|
| `01–06` | **الذاكرة الافتراضية** | من الـmapping إلى الصفحة إلى الـstack |
| `07–12` | **الـallocator** | يُشرَّح تنفيذٌ حقيقيّ، ثم تكتب بديلَه وتقيسه |
| `13–18` | **من الكود إلى العملية** | الـABI ثم الـobject files والـlinker والـloader |
| `19–26` | **التزامن** | العتاد، ثم الخيوط، ثم نموذج ذاكرة اللغة |

ولكل لوحةٍ من هنا مصدرٌ موسوم. فإن قرأتَ ادّعاءً ولم تعرف من يضمنه، فذلك عيبٌ
في اللوحة لا فيك.

**الفصل التالي:** الـmapping الذي رأيتَه له وحدةٌ لا تنقسم — وحجمُها يقرّر كم من
الذاكرة تدفع مقابل بايتٍ واحد.
