# الإقليم ١٨ — من النصّ إلى الملفّ التنفيذيّ

> في الإقليم ٠١ قلتُ إن في جدول أوّل ملفٍّ **كذبةً مؤقّتة**: أن `#include` جلبَ
> شيئاً. حان وقت كسرها.
>
> `cc main.c` ليس أمراً واحداً، بل **أربعة برامج** يمرّ نصّك عليها بالترتيب. وكل
> خطأٍ محيّر في C تقريباً يصير مفهوماً حين تعرف **أيّ الأربعة اشتكى**.
>
> وفي آخره تقسّم برنامج الإقليم ٠١ على ملفّات، وتعرف أخيراً ما يعنيه `static`
> على مستوى الملفّ.

---

## أربعة، لا واحد

```
main.c ──▶ preprocessor ──▶ compiler ──▶ assembler ──▶ linker ──▶ main
           نصٌّ إلى نصّ      نصّ إلى        تجميع إلى     ‎.o إلى
                            تجميع          ‎.o           تنفيذيّ
```

| الوقفة | الأمر | ماذا يخرج |
|---|---|---|
| بعد الأول | `cc -E main.c` | نصُّ C موسَّعاً |
| بعد الثاني | `cc -S main.c` | ملفّ `.s` بلغة الآلة |
| بعد الثالث | `cc -c main.c` | ملفّ `.o` — كودٌ ثنائيّ وجدولُ أسماء |
| بعد الرابع | `cc main.o` | ملفٌّ تنفيذيّ |

**والفائدة عمليّة لا ثقافية.** «undefined symbol» لا تأتي من الـcompiler أبداً —
هي شكوى الـlinker، وسببها في ملفٍّ آخر أو في غيابه. و«undeclared function» عكسها
تماماً: شكوى الـcompiler، وسببها سطرُ إعلانٍ ناقص في هذا الملفّ.

---

## `#include` نسخٌ ولصق

ملفّان: `greet.h` فيه سطرٌ واحد، و`main.c` يضمّه.

<!-- part: 18-pp -->

```c
/* greet.h */
int add(int a, int b);

/* main.c */
#include "greet.h"

int main(void)
{
	return add(1, 2);
}
```

ثم `cc -E main.c`:

<!-- out @impl -->

```
int add(int a, int b);
int main(void)
{
 return add(1, 2);
}
```

**السطر اختفى، ومحلّه محتوى الملفّ.** لا استيراد، ولا وحدات، ولا شيء يعرف أن
`greet.h` كان موجوداً — بعد هذه المرحلة **لا وجود له**.

و`#include <stdio.h>` تفعل الشيء نفسه بألفٍ من الأسطر. ولهذا يبطؤ بناء C مع
كثرة الترويسات: نفس الملفّ يُقرأ ويُوسَّع في **كل** وحدة ترجمة.

**والفرق بين القوسين والعلامتين موضعُ البحث:** `<...>` في مسارات النظام، و`"..."`
في مجلّد الملفّ أوّلاً ثم مسارات النظام.

---

## ولذلك يوجد الحارس

إن ضمّ ملفّان ترويسةً واحدة، ثم ضمّهما ثالث — يُلصَق محتواها مرّتين. وتعريفُ
`struct` مرّتين خطأٌ عند الـcompiler.

```c
#ifndef TABLE_H
#define TABLE_H

/* ... محتوى الترويسة ... */

#endif
```

**والآلية بسيطة تماماً:** أوّل مرّة لا يكون `TABLE_H` معرَّفاً، فيدخل المحتوى
ويُعرَّف الاسم. وفي كل مرّةٍ بعدها يكون معرَّفاً، فيُحذف المحتوى كلّه.

وهذا **ليس ميزةً في اللغة**، بل حيلةٌ اصطلح عليها الناس فوق أداة استبدالٍ نصّيّ.
والإقليم ١٩ يفكّك تلك الأداة كاملة.

---

## ما يدخل الترويسة، وما لا يدخل

القاعدة تنبع من كون `#include` نسخاً ولصقاً:

| في الترويسة | في الـ`.c` |
|---|---|
| **إعلانات** الدوالّ | **تعريفاتها** |
| `struct` و`enum` و`typedef` | المتغيّرات العامّة |
| `#define` للثوابت | كل ما هو `static` |
| `extern int x;` | `int x;` |

**والسبب واحد:** ما يُنسَخ إلى عشرة ملفّات يجب أن يكون **إعلاناً** — وصفاً بلا
حجز. فإن وضعتَ `int x;` في ترويسةٍ ضمّها ملفّان، حجزتَ `x` مرّتين، **ولن يشتكي
الـcompiler** — سيشتكي الـlinker باسمٍ مكرَّر.

---

## شكوى الـlinker

اترك `add` معلَنةً بلا تعريف، ثم اربط:

<!-- part: 18-undef -->

```c
/* main.c — يعلن add ولا يعرّفها، ولا ملفّ آخر معه */
#include "greet.h"

int main(void)
{
	return add(1, 2);
}
```

```
cc -std=c17 -c main.c -o main.o     # ينجح
cc main.o -o prog                    # يفشل
```

<!-- out @machine -->

```
Undefined symbols
  "_add", referenced from:
      _main in main.o
ld: symbol(s) not found
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

**لاحظ أن الترجمة نجحت.** الـcompiler رأى الإعلان فصدّقه، وترك في `main.o`
**طلباً باسم**: «أحتاج `_add`، ولا أعرف أين».

والـlinker مهمّته أن يطابق الطلبات بالعروض. ولا يعرف أنواعاً ولا مواصفةً — يعرف
**أسماء** فقط. ولذلك لا تخبرك رسالته بسببٍ أعمق من «لم أجد».

**والشرطة السفلية في `_add`** اصطلاح المنصّة: يُضاف حرفٌ إلى الاسم في جدول
الرموز. وهي التي تجعل رسائل الـlinker تبدو غريبةً أوّل مرّة.

---

## داخل ملفّ `.o`

الآن اقسم برنامج الإقليم ٠١: `table.h` و`table.c` و`main.c`.

<!-- part: 18-nm -->

```c
/* table.c — ما بداخله */
static struct Item items[64];
static int         used = 0;
static struct Item *find(const char *key) { … }

void        table_set(const char *key, const char *value) { … }
const char *table_get(const char *key) { … }
int         table_count(void) { … }
```

ثم `nm table.o`:

<!-- out @machine -->

```
00000000000000d0 t _find
                 U _free
0000000000000270 b _items
                 U _malloc
                 U _strcmp
                 U _strlen
00000000000001dc T _table_count
0000000000000180 T _table_get
0000000000000000 T _table_set
0000000000000870 b _used
```

**الحرف هو الدرس كلّه:**

| | |
|---|---|
| `T` كبيرة | كودٌ **يراه** الـlinker من خارج هذا الملفّ |
| `t` صغيرة | كودٌ **لا يراه** أحد — `static` |
| `b` | بياناتٌ مصفَّرة، وهي `static` هنا فصغيرة |
| `U` | **طلبٌ** لم يُلبَّ بعد: `malloc` و`strcmp` من المكتبة |

الثلاثة الكبيرة هي **الواجهة**. وكل ما عداها مِلك الملفّ: لا يستطيع ملفٌّ آخر أن
ينادي `find` ولو أعلنه بنفسه — الـlinker لن يجد اسماً يطابقه.

**وهذا ما تملكه C بدل `private`.** رأيتَ الكلمة في الإقليم ١٠، وهذه أوّل مرّةٍ
ترى أثرها.

---

## النوع المُعتِم

وأقوى ما يُبنى على هذا: **نوعٌ يستعمله غيرك ولا يعرف ما بداخله.**

`table.h` لا يذكر `struct Item` أصلاً — يذكر ثلاث دوالّ. ولو أراد المستعمل أن
يمسك بسجلٍّ لكتبتَ في الترويسة:

```c
struct Item;                     /* إعلانٌ بلا تعريف */
struct Item *table_find(const char *key);
```

والمستعمل يستطيع أن يحمل `struct Item *`، **ولا يستطيع** أن يكتب `it->key` ولا
`sizeof(struct Item)` — لأن النوع **غير مكتمل** عنده.

**والمكسب أن تخطيط الـstruct يصير قابلاً للتغيير** بلا إعادة ترجمة من يستعملها.
**وثمنه** أنه لا يستطيع أن ينشئ واحدةً على الـstack — لا يعرف حجمها — فيجب أن
تعطيه دالّة إنشاء.

هذا هو نموذج `FILE *` الذي ستراه في الإقليم ٢١: تحمله وتمرّره، ولا تعرف ما فيه.

## من يبني، ومتى

```makefile
CC     = cc
CFLAGS = -std=c17 -Wall -Wextra

cmd: main.o table.o
	$(CC) main.o table.o -o cmd

main.o: main.c table.h
	$(CC) $(CFLAGS) -c main.c

table.o: table.c table.h
	$(CC) $(CFLAGS) -c table.c

clean:
	rm -f *.o cmd
```

<!-- part: 18-split -->

```c
/* main.c */
table_set("name", "ali");
table_set("lang", "c");
table_set("name", "sara");
```

<!-- out -->

```
sara
c
0x0
2
```

**كل سطرٍ في `Makefile` جملةٌ واحدة:** هذا الهدف يعتمد على هذه الملفّات، وإن كان
أحدها أحدثَ منه فنفّذ هذا الأمر.

**ولاحظ `table.h` في سطرَي الاعتماد.** بلا هذا، تغييرُ الترويسة لا يعيد بناء
شيء — فيبقى `main.o` مبنياً على واجهةٍ قديمة، ويربطه الـlinker بلا شكوى. وهي
واحدة من أخبث حالات «يعمل عندي».

**والفرق عن `cc *.c`** أن هذا يعيد بناء الملفّات المتغيّرة وحدها. وفي مشروعٍ من
مئة ملفّ يصير الفرق بين ثانيتين ودقيقتين.

---

## قبل أن تكمل

> **١.** ضع `int x;` في ترويسةٍ يضمّها ملفّان، واربطهما. من اشتكى — الـcompiler
> أم الـlinker؟ ثم اجعلها `extern int x;` وعرّفها في ملفٍّ واحد.
>
> **٢.** احذف `table.h` من سطر اعتماد `main.o` في `Makefile`، ثم غيّر توقيع
> `table_get` في الترويسة والـ`.c` معاً. ابنِ وشغّل — ماذا يحدث، ولماذا لم يشتكِ
> أحد؟
>
> **٣.** شغّل `cc -S table.c` واقرأ أوّل عشرين سطراً. ابحث عن اسم `_table_set`،
> ثم عن `_find` — أيّهما موسومٌ بأنه عالميّ، وبأي تعليمة؟
