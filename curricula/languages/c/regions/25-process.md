# الإقليم ٢٥ — الـprocess

> في الإقليم ١٠ رسمتَ خريطة الذاكرة: منطقةٌ ساكنة، وstack، وheap. وقلتُ إن
> المواصفة لا تعرف شيئاً من هذا، وإن النظام هو من يرسمها.
>
> هذا الإقليم عن الشيء الذي تخصّه تلك الخريطة: **الـprocess**. وفيه سطرٌ واحد
> **يعود مرّتين** — وهو أغرب سطرٍ في هذا المنهج كلّه، وأكثره فائدة.
>
> وبنهايته تملك كل ما يلزم لتشغيل برامج النظام من حلقة أوامرك.

---

## ما الذي يملكه البرنامج العامل

| | |
|---|---|
| **مساحة عناوين** | الخريطة التي رأيتَها: ساكن · stack · heap |
| **جدول descriptors** | صفرٌ وواحدٌ واثنان وما فتحتَه — الإقليم ٢٣ |
| **رقمٌ** (pid) | يعرفه به النظام |
| **حالةٌ صغيرة** | مجلّدٌ حاليّ، بيئة، أذونات |

**والعناوين التي تطبعها ليست عناوين الرقاقة.** كل process يرى مساحته وحدها،
مرقّمةً من الصفر كأنها الآلة كلّها. والنظام يترجم.

**ولذلك ظهرت العناوين مختلفةً في كل تشغيل** (الإقليمان ٠٩ و١٠): النظام يزحزحها
عمداً في كل مرّة.

---

## `fork`: نداءٌ يعود مرّتين

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
	printf("قبل fork\n");
	fflush(stdout);

	pid_t pid = fork();

	if (pid < 0)
		return 1;
	if (pid == 0) {
		printf("أنا الابن، وfork أعطتني %d\n", pid);
		return 7;
	}

	int status;

	waitpid(pid, &status, 0);
	printf("أنا الأب، وfork أعطتني رقم الابن\n");
	if (WIFEXITED(status))
		printf("خرج الابن برمز %d\n", WEXITSTATUS(status));
	return 0;
}
```

<!-- out @posix -->

```
قبل fork
أنا الابن، وfork أعطتني 0
أنا الأب، وfork أعطتني رقم الابن
خرج الابن برمز 7
```

**`fork` تُنادى مرّةً وتعود مرّتين** — في عمليتين. والذي يفرّق بينهما **قيمةُ
الإرجاع وحدها**:

| العائد | من أنت |
|---|---|
| `0` | الابن |
| `> 0` | الأب، والقيمة رقم الابن |
| `< 0` | فشل، ولا ابن |

**والابن نسخةٌ كاملة**: نفس الكود، ونفس القيم، ونفس موضع التنفيذ — من السطر الذي
يلي `fork` بالضبط. لا يبدأ من `main`.

**و`waitpid` تنتظر ابناً بعينه**، وتضع في `status` رقماً **ليس رمز الخروج**: هو
حزمةُ بتّاتٍ تُقرأ بماكروات — `WIFEXITED` هل خرج طبيعياً، و`WEXITSTATUS` برمزٍ
كم. وهذه هي القناة التي رأيتَها من الطرف الآخر في الإقليم ٢٢.

**ومن لا يُنتظَر يبقى في الجدول** بعد موته — رمزُ خروجه محفوظٌ لأحد، ولا أحد
يسأل. اسمه **zombie**، وثمنه مدخلٌ في جدول النظام لا يُستردّ.

## نسخةٌ لا مشاركة

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int shared = 1;

int main(void)
{
	int   local = 10;
	pid_t pid   = fork();

	if (pid == 0) {
		shared = 99;
		local  = 99;
		printf("الابن:  %d %d\n", shared, local);
		return 0;
	}
	wait(NULL);
	printf("الأب:   %d %d\n", shared, local);
	return 0;
}
```

<!-- out @posix -->

```
الابن:  99 99
الأب:   1 10
```

**الابن غيّر متغيّراً عامّاً، ولم يتغيّر عند الأب.**

وهذه هي **البديهية الثالثة على مستوى النظام**: كل تمريرٍ نسخ — حتى تمرير برنامجٍ
كامل. لا ذاكرة مشتركة إلا بطلبٍ صريح.

**والنسخ لا يقع فعلاً عند `fork`.** النظام يشير الاثنين إلى نفس الصفحات ويسمها
«للقراءة»، وينسخ الصفحة **عند أوّل كتابة** عليها. فـ`fork` رخيصةٌ مهما كبر
برنامجك، والثمن يُدفَع بمقدار ما تكتب.

**والذي يُشارَك فعلاً: جدول الـdescriptors.** الابن يرث نسخةً من الجدول تشير إلى
**نفس** الملفّات المفتوحة — بنفس الموضع. وهذا ما يجعل التوجيه ممكناً، وسيصير أساس
الـpipe بعد قليل.

## والـbuffer يُنسَخ معه

هذه أخبث نتيجةٍ في الباب، وتربط الإقليم السابق بهذا:

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
	printf("سطرٌ واحد\n");
	if (fork() == 0)
		return 0;
	wait(NULL);
	return 0;
}
```

<!-- out @machine: و`./main > out.txt` -->

```
سطرٌ واحد
سطرٌ واحد
```

**`printf` مرّةً واحدة، وسطران في الملفّ.**

لأن `stdout` موجَّهٌ إلى ملفّ ⇒ مخزَّنٌ بالكتلة ⇒ لم يُفرَغ عند `\n`. فحين وقعت
`fork` كان السطر **في الـbuffer**، فنُسخ الـbuffer مع كل شيء. ثم أفرغ كلٌّ من
الأب والابن نسخته عند الخروج.

**والبرنامج نفسه على terminal:**

```c
//! pty
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
	printf("سطرٌ واحد\n");
	if (fork() == 0)
		return 0;
	wait(NULL);
	return 0;
}
```

<!-- out @machine -->

```
سطرٌ واحد
```

**مرّةً واحدة** — لأن النمط سطريّ، فعبر السطر قبل `fork`.

**فالقاعدة: `fflush(NULL)` قبل كل `fork`.** أو `_exit` في الابن بدل `return`،
فلا يُفرِغ شيئاً. وستفعل الاثنين في مشروع التخرّج.

## `exec`: أن تصير برنامجاً آخر

`fork` تعطيك عمليةً ثانية تنفّذ **نفس** الكود. و`exec` تستبدل الكود:

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
	pid_t pid = fork();

	if (pid == 0) {
		char *argv[] = { "echo", "من", "execvp", NULL };

		execvp(argv[0], argv);
		perror("execvp");
		_exit(127);
	}
	int status;

	waitpid(pid, &status, 0);
	printf("رمز echo = %d\n", WEXITSTATUS(status));
	return 0;
}
```

<!-- out @posix -->

```
من execvp
رمز echo = 0
```

**`execvp` لا تعود عند النجاح.** لا تنشئ عمليةً جديدة — تستبدل محتوى هذه: كودها
وبياناتها وstack. **ويبقى الرقم، ويبقى جدول الـdescriptors.**

**ولذلك السطران بعدها للفشل وحده.** إن نُفِّذت فلن يصل إليهما شيء؛ وإن وصلا فقد
فشلت، و`errno` يقول لماذا — `ENOENT` لا يوجد، `EACCES` لا إذن.

**و`_exit(127)` لا `exit`** — لأن الابن يحمل نسخةً من buffers الأب، و`exit`
تُفرِغها فيُطبَع ما طُبع مرّتين.

**واسم `execvp` وصفٌ للتوقيع:** `v` تأخذ **array** من الوسائط، و`p` تبحث في
`PATH`. وأخواتها `execl` بقائمةٍ متغيّرة، و`execve` بجدول بيئةٍ صريح.

**ولاحظ `NULL` في آخر `argv`** — هي علامة النهاية التي رأيتَها في الإقليم ١٤ حين
سألتَ عن `argv[argc]`. **وهنا سببها**: `execvp` لا تأخذ `argc`.

**واصطلاح `argv[0]`** أن يكون اسم البرنامج، وهو الذي يظهر في `ps`. وليس ملزماً أن
يطابق ما نفّذته فعلاً.

## `fork` + `exec` + `wait` = shell

الثلاثة معاً هي كل ما تفعله أي shell في العالم:

```
اقرأ سطراً        ← الإقليم ٠١
قسّمه كلماتٍ       ← الإقليم ٠١ (split)
fork              ← نسخة
    الابن:  execvp(argv[0], argv)
    الأب:   waitpid — وانتظر
اعرض المحثّ ثانيةً
```

**وهذا كل شيء.** الفرق بين `bash` وحلقة الإقليم ٠١ ليس في هذا القلب، بل فيما
حوله: التوجيه، والـpipes، والوظائف، والتوسيع.

## الـpipe: قناةٌ بين اثنين

```c
#include <stdio.h>
#include <unistd.h>
#include <string.h>
#include <sys/wait.h>

int main(void)
{
	int fd[2];

	if (pipe(fd) < 0)
		return 1;

	pid_t pid = fork();

	if (pid == 0) {
		close(fd[0]);
		const char *s = "رسالةٌ من الابن\n";

		write(fd[1], s, strlen(s));
		close(fd[1]);
		_exit(0);
	}
	close(fd[1]);

	char    buf[128];
	ssize_t n = read(fd[0], buf, sizeof buf);

	close(fd[0]);
	wait(NULL);
	printf("الأب قرأ %zd بايتاً: %.*s", n, (int)n, buf);
	return 0;
}
```

<!-- out @posix -->

```
الأب قرأ 29 بايتاً: رسالةٌ من الابن
```

`pipe(fd)` تعطيك **descriptorين**: `fd[0]` للقراءة و`fd[1]` للكتابة، وبينهما
buffer في النظام.

**ولا تفيد وحدها** — تفيد لأن `fork` تنسخ الجدول، فيصير الطرفان عند عمليتين.

**وسطرا `close` ليسا تنظيفاً؛ هما شرطُ العمل:**

كل طرفٍ يغلق ما لا يستعمل. **فلو أبقى الأب `fd[1]` مفتوحاً** لبقيت هناك جهةٌ
قادرةٌ على الكتابة، فلا يرى الأب نهايةً أبداً و`read` تنتظر إلى الأبد.

**فالقاعدة: `read` على pipe تُرجع صفراً حين يُغلَق آخر طرف كتابة.** وهذه هي «نهاية
الملفّ» في الـpipes، ونسيان `close` واحدٍ يعلّق البرنامج.

**و`ls | grep x` هي هذا بالضبط**، وقد أُضيف إليه `dup2` من الإقليم ٢٣: الابن
الأول ينسخ `fd[1]` فوق ١، والثاني ينسخ `fd[0]` فوق ٠. ثم `execvp` لكلٍّ منهما،
ولا يعرف أيٌّ منهما أن هناك pipe أصلاً.

## الإشارة

آخر ما تحتاجه من هذا الباب: رسالةٌ غير متزامنة من النظام إلى عمليتك.

| | |
|---|---|
| `SIGINT` | `Ctrl-C` — الافتراضيّ: إنهاء |
| `SIGTERM` | طلبُ إنهاءٍ مهذّب |
| `SIGSEGV` | عنوانٌ ليس لك — رأيتَه في الإقليم ١١ |
| `SIGCHLD` | مات ابن |
| `SIGKILL` | **لا يُلتقَط ولا يُتجاهَل** |

**والتقاطها ممكن**، وما يجوز داخل المُلتقِط ضيّقٌ جداً: `printf` غير مسموحة، و
`malloc` غير مسموحة — لأن الإشارة قد تصل **وسط** واحدةٍ منهما.

**والمسموح المضمون:** كتابة قيمةٍ في متغيّرٍ من نوع
`volatile sig_atomic_t`، والحلقة الرئيسية تقرؤه.

وهذا كل ما ستحتاجه في مشروع التخرّج: أن يلتقط الـshell `Ctrl-C` فلا يموت هو، بل
يمرّرها لمن يشغّله.

## قبل أن تكمل

> **١.** ثلاث `fork` متتابعة بلا شرط — كم process تنتج؟ ارسمها، ثم اطبع
> `getpid()` في كلٍّ منها وتحقّق.
>
> **٢.** احذف `close(fd[1])` من الأب في لقطة الـpipe وشغّل. ماذا يحدث بالضبط،
> وأي سطرٍ يقف عنده البرنامج؟
>
> **٣.** أضِف إلى الإقليم ٠١: إن لم يكن الأمر معروفاً، جرّب تشغيله بـ`fork` و
> `execvp` بدل طباعة `?`. هذه أوّل خطوةٍ نحو مشروع التخرّج — وستكتشف بها ثلاثة
> أشياء ناقصة.
