# الإقليم ٢٤ — الـbuffer

> منذ الإقليم ٠١ وأنت تحمل سؤالاً: **لماذا `fflush(stdout)` في سطرٍ لم يطلبه
> أحد؟**
>
> جوابه هنا، وهو أوسع من السطر: `printf` **لا تكتب**. تنسخ إلى ذاكرةٍ في
> برنامجك، ويقرّر غيرها متى تعبر إلى النظام. وذلك القرار يتغيّر بحسب **إلى أين
> يذهب مخرَجك** — لا بحسب ما كتبتَه.

---

## لماذا يوجد الـbuffer أصلاً

قلنا في الإقليم السابق إن كل `write` عبورُ حدّ. وهذا قياسُه:

<!-- runs -->

```c
#include <stdio.h>
#include <unistd.h>
#include <time.h>

static double secs(void)
{
	struct timespec ts;

	clock_gettime(CLOCK_MONOTONIC, &ts);
	return ts.tv_sec + ts.tv_nsec / 1e9;
}

int main(void)
{
	FILE  *f  = fopen("a.bin", "wb");
	double t0 = secs();

	for (int i = 0; i < 200000; i++)
		fputc('x', f);
	fclose(f);
	double t1 = secs();

	FILE  *g  = fopen("b.bin", "wb");
	int    fd = fileno(g);
	double t2 = secs();

	for (int i = 0; i < 200000; i++)
		write(fd, "x", 1);
	fclose(g);
	double t3 = secs();

	printf("buffered %.3f  raw %.3f  نسبة %.0f\n",
	       t1 - t0, t3 - t2, (t3 - t2) / (t1 - t0));
	return 0;
}
```

<!-- out @machine: من جهازٍ واحد — **والثابت هو النسبة** -->

```
buffered 0.008  raw 0.321  نسبة 40
```

**مئتا ألف بايتٍ في الحالتين.** الفرق أن الأولى عبرت الحدّ نحو خمسين مرّة،
والثانية مئتي ألف.

**فالـbuffer ليس تفصيلاً في التنفيذ** — هو سبب وجود `<stdio.h>` فوق `write`
أصلاً. وثمنه أن ما «كتبتَه» ليس مكتوباً.

---

## ثلاثة أنماط، ومن يختار

| النمط | متى يُكتَب | من يستعمله افتراضياً |
|---|---|---|
| **بلا buffer** (`_IONBF`) | فوراً، كل نداء | `stderr` |
| **بالسطر** (`_IOLBF`) | عند `\n`، أو عند الامتلاء | `stdout` **إن كان terminal** |
| **بالكتلة** (`_IOFBF`) | عند الامتلاء وحده | `stdout` **إن كان ملفّاً أو pipe**، وكل ملفّ |

**والسطر الأوسط هو المفتاح.** المكتبة تسأل `isatty` — الدالّة نفسها التي رأيتَها
في الإقليم السابق — وتقرّر بحسب الجواب.

**والمنطق سليم:** الإنسان أمام الشاشة يريد أن يرى فوراً، وثمن ذلك عبورٌ لكل سطر.
والملفّ لا أحد ينتظره، فيُجمَع ويُكتَب دفعةً.

**والنتيجة أن برنامجك يتصرّف تصرّفين** بحسب ما لم يكتبه أحدٌ فيه.

---

## البرهان: البرنامج نفسه، ومخرَجان

```c
//! pty
#include <stdio.h>
#include <unistd.h>

int main(void)
{
	printf("سطرٌ مكتمل\n");
	printf("سطرٌ بلا نهاية");
	_exit(0);
}
```

<!-- out @machine: مشغَّلاً في terminal -->

```
سطرٌ مكتمل
```

**السطر الثاني ضاع.** كُتب في الـbuffer، ولا `\n` فيه ليُفرِغه، و`_exit` تنهي
العملية **بلا إفراغ** (الإقليم ٢٢).

والآن **نفس البرنامج**، ومخرَجه إلى ملفّ:

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
	printf("سطرٌ مكتمل\n");
	printf("سطرٌ بلا نهاية");
	_exit(0);
}
```

<!-- out @machine: و`./main > out.txt` — ثم `cat out.txt` -->

```

```

**الملفّ فارغ.** ضاع السطران معاً، لأن `stdout` صار مخزَّناً بالكتلة، فلم يُفرِغه
حتى `\n`.

**وهذا هو أخطر ما في هذا الباب:** برنامجٌ ينهار بعد `printf` تشخيصية **لا تجد
منها شيئاً في السجلّ** — لا لأنها لم تُنفَّذ، بل لأنها لم تعبر. فتبحث عن العطب في
المكان الخطأ.

## وأخيراً: `fflush(stdout)`

عُد إلى الإقليم ٠١:

```c
printf("> ");
fflush(stdout);
if (fgets(line, sizeof line, stdin) == NULL)
	break;
```

**`"> "` بلا `\n`.** فحتى على terminal — حيث النمط بالسطر — لا شيء يُفرِغها.
فتنتظر `fgets` دخلاً، والمستعمل ينتظر محثّاً لا يراه. **كلاهما ينتظر الآخر.**

**والمواصفة لا تنقذك:** تقول إن الدخل من مجرىً قد يُفرِغ المجاري المرتبطة به —
**«قد»** لا «يجب». ونصف التنفيذات تفعل ونصفها لا. فالسطر الذي كتبتَه بلا شرح هو
الفرق بين برنامجٍ يعمل في كل مكانٍ وبرنامجٍ يعمل عندك.

| | |
|---|---|
| `fflush(f)` | اكتب ما في buffer هذا المجرى الآن |
| `fflush(NULL)` | **كل** مجاري الخرج المفتوحة |

**ومتى تُفرِغ إذن؟** عند محثٍّ بلا سطرٍ جديد، وقبل عملٍ طويل تريد أن يُرى
تقدّمُه، وقبل `dup2` كما في الإقليم السابق، وقبل `fork` — وذلك الأخير موضوع
الإقليم القادم وله هناك ثمنٌ غريب.

## أن تختار بنفسك

```c
#include <stdio.h>

int main(void)
{
	setvbuf(stdout, NULL, _IONBF, 0);
	printf("بلا buffer");
	printf(" — يظهر فوراً\n");
	return 0;
}
```

<!-- out -->

```
بلا buffer — يظهر فوراً
```

`setvbuf(stream, buf, mode, size)` تبدّل النمط. **وشرطها أن تُنادى قبل أي قراءةٍ
أو كتابةٍ على المجرى** — بعدها سلوكٌ غير معرَّف.

**ومتى تستحقّ؟**

- **`_IONBF` لبرنامجٍ يُنقَّح**، أو لسجلٍّ يجب أن ينجو من الانهيار.
- **`_IOFBF` ببuffer كبير** لبرنامجٍ يكتب كثيراً إلى ملفّ.
- **وفي غير ذلك، اتركها.** الافتراضات مضبوطة، وتغييرها بلا سببٍ مقيس تشويش.

**والبديل الأسهل لمشكلة السجلّ:** اكتبه إلى `stderr`. هو بلا buffer أصلاً، وهذا
سببٌ ثانٍ لوجوده مستقلّاً — غير الذي ذكرتُه في الإقليم ٢١.

## متى يُفرَغ الـbuffer

اجمع الباب كلّه في قائمةٍ واحدة تُراجَع عند أي «أين ذهب مخرَجي»:

| يُفرَغ | لا يُفرَغ |
|---|---|
| امتلأ | انتهت الدالّة |
| `\n` **في النمط السطريّ وحده** | مرّ وقت |
| `fflush` | `\n` في النمط الكتليّ |
| `fclose` | `_exit` · `abort` (متروكٌ للتنفيذ) |
| `exit` أو `return` من `main` | انهيارٌ بإشارة |

**والصفّ الأخير على اليمين هو الذي يكلّف ساعات.** برنامجٌ مات بـ`SIGSEGV` يفقد كل
ما لم يعبر — وآخر سطرٍ تراه في مخرَجه **ليس آخر سطرٍ نفّذه**.

---

## قبل أن تكمل

> **١.** أضِف إلى الإقليم ٠١ سطراً يطبع رقم كل أمرٍ بلا `\n`، ثم اقتل البرنامج
> بـ`Ctrl-C`. كم رقماً ترى؟ ثم أعِد التجربة و`stdout` موجَّهٌ إلى ملفّ.
>
> **٢.** احذف `fflush(stdout)` وشغّل `./cmd` في terminal ثم `./cmd < cmds.txt`.
> صِف الفرق في كل حالة، وأيّهما يبدو «يعمل».
>
> **٣.** اكتب برنامجاً يطبع نقطةً كل ثانيةٍ عشر مرّات. ثم شغّله موجَّهاً إلى
> `cat`. متى تظهر النقاط، ولماذا؟ وأيّ سطرٍ واحدٍ يصلحه؟
