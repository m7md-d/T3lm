# الإقليم ٠٥ — الفشل

> البذرة الثانية من الإقليم ٠١: مفكِّكك يذعر على مدخَلٍ من المستخدم، وتوقيعه يقول
> `Result<i64, EvalError>` **وهو يكذب**.
>
> هنا تجعل التوقيع صادقاً. وستخرج بقاعدةٍ واحدة تفصل: **الخطأ حالةٌ متوقَّعة تُعاد،
> والذعر عقدٌ مكسور.**

## البذرة: توقيعٌ يكذب

`parse().unwrap()` في المفكِّك:

```rust
fn main() {
    let big = "99999999999999999999";
    println!("قبل");
    let n: i64 = big.parse().unwrap();
    println!("{n}");
}
```

<!-- out: بعده سطر backtrace، والخروج بالرمز ١٠١ -->

```
قبل

thread 'main' panicked at d01.rs:4:30:
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: PosOverflow }
```

**`parse` أعادت `Err`، و`unwrap` حوّلتها إلى ذعر.** فالمعلومة كانت موجودة، وأنت
رميتَها.

ولاحظ أن `println!("قبل")` طُبعت: **الذعر يقع في منتصف العمل**، وما بعده لا يقع.
وهذا أوّل سببٍ لتجنّبه في مسارٍ يعالج مدخلات.

## `Result` قيمةٌ لا استثناء

`parse` تُرجع `Result`، والمطابقة تفرغه:

```rust
use std::num::ParseIntError;

fn total(src: &str) -> Result<i64, ParseIntError> {
    let mut acc = 0;
    for w in src.split_whitespace() {
        acc += w.parse::<i64>()?;
    }
    Ok(acc)
}

fn main() {
    println!("{:?}", total("12 30 2"));
    println!("{:?}", total("12 ثلاثون 2"));
}
```

<!-- out -->

```
Ok(44)
Err(ParseIntError { kind: InvalidDigit })
```

**و`?` سطرٌ واحد يقول:** إن كانت `Ok` فخذ ما فيها وتابع، وإن كانت `Err` فاخرج
بها الآن.

ولا `try` ولا مكدّس استثناءات ولا مسارٌ خفيّ. **المسار الفاشل مكتوبٌ في النوع
المُرجَع**، ومن قرأ التوقيع عرف أن هذه الدالّة قد تفشل قبل أن يفتح جسدها.

## الفيض معرَّف، وسلوكه علمٌ في سطر الأمر

في C فيض العدد الصحيح المُوقَّع **سلوكٌ غير معرَّف**. وفي Rust له جوابان
معلومان:

```rust
use std::hint::black_box;

fn main() {
    let a: i64 = black_box(9_000_000_000_000_000_000);
    println!("قبل");
    let sum = a + a;
    println!("{sum}");
}
```

<!-- out: بلا `-O` -->

```
قبل

thread 'main' panicked at d03.rs:6:15:
attempt to add with overflow
```

ثم شغّل الأمرين وقارن:

```bash
rustc --edition 2024 d03.rs && ./d03                       # يذعر
rustc --edition 2024 -O d03.rs && ./d03                    # -446744073709551616
rustc --edition 2024 -O -C debug-assertions=on d03.rs      # يذعر مرّةً أخرى
```

**والثالث هو المهمّ:** الفارق ليس `-O` — هو علم `debug-assertions` الذي يرفعه
`-O` ضمناً. فالسلوك **قرارُ بناءٍ تملكه**، لا مفاجأةٌ من المعالج.

## اطلب الجواب بلا ذعر

لكل عملية حسابية أربعُ صور:

```rust
fn main() {
    let a: i64 = 9_000_000_000_000_000_000;
    println!("checked_add: {:?}", a.checked_add(a));
    println!("checked_add: {:?}", 12i64.checked_add(30));
    println!("saturating : {}", a.saturating_add(a));
    println!("wrapping   : {}", a.wrapping_add(a));
    println!("overflowing: {:?}", a.overflowing_add(a));
}
```

<!-- out -->

```
checked_add: None
checked_add: Some(42)
saturating : 9223372036854775807
wrapping   : -446744073709551616
overflowing: (-446744073709551616, true)
```

| الصورة | متى تختارها |
|---|---|
| `checked_*` | الفيض خطأٌ يجب أن يصل المستخدم |
| `saturating_*` | القمّة جوابٌ مقبول — عدّادات، ألوان |
| `wrapping_*` | الالتفاف مقصود — تجزئة، تشفير، عدّادٌ دوريّ |
| `overflowing_*` | تريد النتيجة **وعِلمَ** أنها التفّت |

**والمكسب أن الاختيار صار مكتوباً في الكود.** في C كلّها `+`، ونيّتك في رأسك.

## خطؤك أنت، بأسمائه

`ParseIntError` خطأ المكتبة. وخطأ **مفكِّكك** يسمّي حالاته هو:

<!-- part: 05-eval-error -->

```rust
#[derive(Debug)]
enum EvalError {
    Empty,
    NotANumber(String),
    BadOperator(char),
    Overflow,
}

impl fmt::Display for EvalError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            EvalError::Empty => write!(f, "تعبيرٌ فارغ"),
            EvalError::NotANumber(w) => write!(f, "ليس عدداً: {w}"),
            EvalError::BadOperator(c) => write!(f, "عاملٌ غير مدعوم: {c}"),
            EvalError::Overflow => write!(f, "فيضٌ في الحساب"),
        }
    }
}

impl std::error::Error for EvalError {}
```

<!-- out -->

```
Empty  ←  تعبيرٌ فارغ
NotANumber("ثلاثون")  ←  ليس عدداً: ثلاثون
BadOperator('-')  ←  عاملٌ غير مدعوم: -
Overflow  ←  فيضٌ في الحساب
```

**وجهان لكل خطأ:** `Debug` للمبرمج — بنيةٌ حرفية يقرؤها في السجلّ. و`Display`
للمستخدم — جملةٌ بلغته.

وسمة `Error` علامةٌ فارغة تقريباً، **وهي التي تجعل خطأك يدخل في `Box<dyn Error>`
وفي `?`**. تنفيذها سطرٌ واحد لأن `Display` و`Debug` أدّيا العمل.

## `?` تحوّل النوع في طريقها

`?` تفعل أكثر من الخروج المبكر: تستدعي `From` على الخطأ.

<!-- part: 05-question-mark -->

```rust
fn run(src: &str) -> Result<i64, Box<dyn Error>> {
    let w = src.split_whitespace().next().ok_or(Bad(String::from("فارغ")))?;
    let n: i64 = w.parse()?;
    Ok(n * 2)
}

fn main() -> Result<(), Box<dyn Error>> {
    println!("{}", run("21 + 1")?);
    println!("{}", run("سعر")?);
    Ok(())
}
```

<!-- out: الخروج بالرمز ١ -->

```
42
Error: ParseIntError { kind: InvalidDigit }
```

`w.parse()` تُرجع `ParseIntError`، والدالّة تُرجع `Box<dyn Error>`. **و`?` جسّرت
بينهما** لأن `Box<dyn Error>` تنفّذ `From` لكل ما ينفّذ `Error`.

**و`main` نفسها تُرجع `Result`**: فيطبع وقت التشغيل `Error:` مع `Debug` ويخرج
بالرمز ١. برنامج سطر أمرٍ صحيح، بلا سطرٍ واحدٍ من إدارة الخروج.

## `Option` أخٌ لا يحمل سبباً

`Option` غيابٌ بلا تعليل، و`?` تعمل عليها كذلك:

```rust
fn first_num(src: &str) -> Option<i64> {
    let w = src.split_whitespace().next()?;
    w.parse().ok()
}

fn main() {
    println!("{:?}", first_num("12 + 30"));
    println!("{:?}", first_num("   "));
    println!("{:?}", first_num("سعر 12"));

    println!("{:?}", first_num("   ").ok_or("لا رمز"));
    println!("{}", first_num("سعر").unwrap_or(0));
    println!("{}", first_num("سعر").unwrap_or_default());
}
```

<!-- out -->

```
Some(12)
None
None
Err("لا رمز")
0
0
```

**والسطران الأخيران هما الفرق العمليّ:** `None` تخبرك أن لا قيمة، ولا تخبرك
لماذا. فالنصّ فارغ؟ أم فيه كلمةٌ ليست عدداً؟ المخرَجان `None` سواء.

و`ok_or` هي الجسر: تحوّل الغياب إلى خطأٍ يحمل سبباً — **وهي أكثر ما ستكتبه حين
تنتقل من دالّةٍ داخلية إلى واجهةٍ يستعملها غيرك.**

## المهايئات: أن تبني الخطأ في مكانه

`map_err` و`ok_or_else` تصنعان الخطأ حيث تعرف السياق:

```rust
use std::num::ParseIntError;

fn total(src: &str) -> Result<i64, String> {
    let mut acc: i64 = 0;
    for w in src.split_whitespace() {
        let n: i64 = w.parse().map_err(|e: ParseIntError| format!("«{w}»: {e}"))?;
        acc = acc.checked_add(n).ok_or_else(|| String::from("فيض"))?;
    }
    Ok(acc)
}

fn main() {
    println!("{:?}", total("12 30 2"));
    println!("{:?}", total("12 ثلاثون"));
    println!("{:?}", total("9000000000000000000 9000000000000000000"));
}
```

<!-- out -->

```
Ok(44)
Err("«ثلاثون»: invalid digit found in string")
Err("فيض")
```

**`map_err` تضيف ما لا تعرفه المكتبة**: `ParseIntError` تعرف أن الرقم فاسد، ولا
تعرف **أي كلمة** كانت. فأضفتَها أنت في موضعك.

و`ok_or_else` تأخذ **مغلَّفاً** لا قيمة، فلا يُبنى الخطأ إلا عند الفشل. (و`ok_or`
تبنيه دائماً — ففرّق بينهما حين يكون بناء الخطأ مكلفاً.)

## متى تُذعر إذن

الذعر ليس ممنوعاً. له موضعٌ واحد:

| الحالة | الجواب |
|---|---|
| مدخَلٌ من مستخدمٍ أو ملفٍّ أو شبكة | `Result` — قد يقع، فأعلِنه |
| فرضٌ يضمنه كودك نفسه، وكسرُه عيبُ برمجة | `panic!` · `unwrap` · `assert!` |
| مثالٌ أو اختبارٌ أو نموذجٌ سريع | `unwrap` — والمترجم لا يمانع |

**والفارق الحقيقيّ:** الخطأ حالةٌ توقّعتَها فأعطيتَها اسماً. والذعر إعلانٌ أن
**افتراضاً في رأسك كان خاطئاً**، وأن المتابعة ستُنتج جواباً كاذباً.

و`expect("رسالة")` أفضل من `unwrap()` دائماً حين تُذعر عمداً — لأنها تكتب
الافتراض المكسور في الرسالة.

## المفكِّك: خطآن، لأن الطبقتين اثنتان

خطأ التفكيك غير خطأ الحساب، **فلهما نوعان**:

<!-- part -->

```rust
#[derive(Debug)]
enum LexError {
    BadNumber(String, ParseIntError),
}

#[derive(Debug)]
enum EvalError {
    Empty,
    NotANumber,
    BadOperator(char),
    Overflow(char),
}

fn lex(src: &str) -> Result<Vec<Token<'_>>, LexError> { /* … */ }
fn eval(tokens: &[Token]) -> Result<i64, EvalError> { /* … */ }

fn run(src: &str) -> Result<i64, Box<dyn std::error::Error>> {
    let tokens = lex(src)?;
    Ok(eval(&tokens)?)
}
```

**`LexError::BadNumber` تحمل الخطأ الأصليّ** إلى جانب الكلمة. وهذه هي **السلسلة**:
الطبقة العليا تضيف سياقها ولا تمحو ما تحتها.

و`run` تجمع النوعين في `Box<dyn Error>` عند الحدّ الخارجيّ. **فالداخل أنواعٌ
دقيقة، والحدّ نوعٌ واحد** — وهو النمط الذي تراه في كل مكتبةٍ ناضجة.

## الملفّ كاملاً: مفكِّكٌ لا يذعر

مئةٌ وستّة أسطر. وكل ما فيها مرّ عليك في هذا الإقليم:

```rust
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug, PartialEq)]
enum Token<'a> {
    Word(&'a str),
    Num(i64),
    Sym(char),
}

#[derive(Debug)]
enum LexError {
    BadNumber(String, ParseIntError),
}

#[derive(Debug)]
enum EvalError {
    Empty,
    NotANumber,
    BadOperator(char),
    Overflow(char),
}

impl fmt::Display for LexError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LexError::BadNumber(w, e) => write!(f, "عددٌ لا يُقرأ «{w}»: {e}"),
        }
    }
}

impl fmt::Display for EvalError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            EvalError::Empty => write!(f, "تعبيرٌ فارغ"),
            EvalError::NotANumber => write!(f, "كان المنتظَر عدداً"),
            EvalError::BadOperator(c) => write!(f, "عاملٌ غير مدعوم: {c}"),
            EvalError::Overflow(c) => write!(f, "فيضٌ عند العامل {c}"),
        }
    }
}

impl std::error::Error for LexError {}
impl std::error::Error for EvalError {}

fn lex(src: &str) -> Result<Vec<Token<'_>>, LexError> {
    let mut out = Vec::new();
    for w in src.split_whitespace() {
        let c = w.chars().next().unwrap();
        if c.is_ascii_digit() {
            let n = w.parse().map_err(|e| LexError::BadNumber(w.to_owned(), e))?;
            out.push(Token::Num(n));
        } else if c.is_alphabetic() {
            out.push(Token::Word(w));
        } else {
            out.push(Token::Sym(c));
        }
    }
    Ok(out)
}

fn eval(tokens: &[Token]) -> Result<i64, EvalError> {
    let mut it = tokens.iter();

    let mut acc = match it.next() {
        None => return Err(EvalError::Empty),
        Some(Token::Num(n)) => *n,
        Some(_) => return Err(EvalError::NotANumber),
    };

    while let Some(op) = it.next() {
        let sym = match op {
            Token::Sym(c) => *c,
            _ => return Err(EvalError::NotANumber),
        };
        let rhs = match it.next() {
            Some(Token::Num(n)) => *n,
            _ => return Err(EvalError::NotANumber),
        };
        acc = match sym {
            '+' => acc.checked_add(rhs),
            '*' => acc.checked_mul(rhs),
            other => return Err(EvalError::BadOperator(other)),
        }
        .ok_or(EvalError::Overflow(sym))?;
    }

    Ok(acc)
}

fn run(src: &str) -> Result<i64, Box<dyn std::error::Error>> {
    let tokens = lex(src)?;
    Ok(eval(&tokens)?)
}

fn main() {
    for src in [
        "12 + 30 * 2",
        "9000000000000000000 + 9000000000000000000",
        "99999999999999999999 + 1",
        "7 - 1",
        "",
    ] {
        match run(src) {
            Ok(n) => println!("[{src}] = {n}"),
            Err(e) => println!("[{src}] ✗ {e}"),
        }
    }
}
```

<!-- out -->

```
[12 + 30 * 2] = 84
[9000000000000000000 + 9000000000000000000] ✗ فيضٌ عند العامل +
[99999999999999999999 + 1] ✗ عددٌ لا يُقرأ «99999999999999999999»: number too large to fit in target type
[7 - 1] ✗ عاملٌ غير مدعوم: -
[] ✗ تعبيرٌ فارغ
```

**خمسة مدخلات، وخمسة أجوبة، وصفر ذعر.** والبرنامج الذي كان ينهار على `9e18` صار
يقول لماذا.

**والبذرة الثانية مُغلَقة**: التوقيع `Result<i64, EvalError>` صار صادقاً، وكل
مسارٍ فيه ينتهي بقيمة.

## بذرة

بقيت البذرة الثالثة، ولم يمسّها شيءٌ ممّا فعلناه: `12 + 30 * 2` **لا تزال تعطي
٨٤**.

وقد رأيتَها الآن مرّةً أخرى في مخرَج الأعلى. وهي ليست خطأ برمجةٍ يُصلَح بحارس:
`Vec<Token>` بنيةٌ مسطّحة **لا تستطيع أن تحمل أسبقية**.

فالمطلوب شكلٌ يحملها: تعدادٌ يحوي نفسه. **والتعداد الذي يحوي نفسه يحتاج حجماً
معلوماً** — والإقليم القادم يبدأ من هناك.
