# ١٦ — القفل

الفصل `00` قال إن واجهة C المفتوحة جعلت عدّاد المراجع جزءاً من العقد، وإن عدّاداً
مشتركاً يحتاج قفلاً. هذا الفصل يقيس أثر القفل.

---

## ما هو

الـGIL (global interpreter lock) قفلٌ واحدٌ للمفسّر: **خيطٌ واحدٌ ينفّذ البايت-كود
في اللحظة الواحدة**. الخيوط موجودةٌ وحقيقية — يجدولها نظام التشغيل — لكن واحداً
منها يحمل القفل.

ولم يوجد ليبطئ برنامجك. وُجد ليحمي عدّاداً يعدّله كلُّ سطرٍ من الفصل `15`، وتعدّله
امتداداتُ C بيدها.

---

## أثره على الحساب

**توقّع** قبل أن تقرأ: خيطان على أربعة ملايين جمعةٍ لكلٍّ، مقابل تنفيذهما
تتابعاً. كم يكون الفرق بين الزمنين؟

<!-- part: 16-gil -->

```python
def burn(n):
    x = 0
    for _ in range(n):
        x += 1
    return x


def serial():
    burn(N)
    burn(N)


def threaded():
    ts = [threading.Thread(target=burn, args=(N,)) for _ in range(2)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
```

المخرَج:

<!-- runs: 16-gil -->

```
تتابعاً :   131.8 ms
بخيطين  :   129.5 ms   ×1.02
```

الزمن لم ينقص. الأرقام من جهازٍ واحد، والثابت هو النسبة.

**والقياس نفسه يحتاج احتياطاً**: الدالّة `best` في
[`programs/16-gil.py`](../programs/16-gil.py) تشغّل جولةَ تسخينٍ ثم تأخذ أقلَّ
ثلاث جولات. والسبب أن المفسّر يخصّص الكود بعد أوّل تشغيل، فقياسُ الجولة
الأولى يقيس التخصيص مع العمل.

**المكسب:** `threading` لا تعطي توازياً في الحساب. وما تعطيه في الفقرة التالية.

---

## أثره على الانتظار

الخيط يطلق القفل حين ينتظر: قراءةَ ملفّ، أو ردَّ شبكة، أو `sleep`.

**مثال**

<!-- part: 16-io -->

```python
def wait():
    time.sleep(NAP)


ts = [threading.Thread(target=wait) for _ in range(N)]
for t in ts:
    t.start()
for t in ts:
    t.join()
```

**المخرَج**

<!-- runs: 16-io -->

```
تتابعاً :   433.8 ms
بـ8 خيوط:    55.8 ms   ×7.78
```

ثمانيةُ انتظاراتٍ بـ٧٨٪ من زمنِ واحد. النسبة تقارب عدد الخيوط.

**وهذا هو الحدّ:** القفل يخصّ تنفيذ البايت-كود. وما ينتظر خارجَ المفسّر لا يحمله،
فالخيوط تتراكب.

**المكسب:** القاعدة التي تُبنى عليها القرارات: **انتظارٌ ⇒ خيوط. حسابٌ ⇒ عمليات
أو C.** والحزمة الخامسة تفتح الطريق الثاني.

---

## الحالات

### القيد ليس أبدياً، والبناء يُسأل

<!-- part: 16-check -->

```python
import sys
import sysconfig

print("الإصدار:", sys.version.split()[0])
print("بناءٌ حرّ الخيوط:", bool(sysconfig.get_config_var("Py_GIL_DISABLED")))
print("القفل يعمل الآن:", sys._is_gil_enabled())
```

<!-- out -->

```
الإصدار: 3.14.7
بناءٌ حرّ الخيوط: False
القفل يعمل الآن: True
```

أبنيةٌ بلا قفل (free-threaded) صارت موجودةً منذ 3.13، وهذا البناء ليس منها.

**والسطران الأخيران مختلفان:** الأول يقول أيُّ بناءٍ هذا، والثاني يقول حالته
الآن — لأن البناء الحرّ يستطيع تشغيل القفل عند الحاجة.

**وأرقام هذا الفصل تخصّ البناء المُعلَن في السطر الأول.** إن شغّلتَ بناءً حرّاً
فقِس بنفسك.

### الحساب بـ`multiprocessing` يتوازى

<!-- part: 16-procs -->

```python
if __name__ == "__main__":
    burn(1000)

    t0 = time.perf_counter()
    for _ in range(4):
        burn(N)
    seq = time.perf_counter() - t0

    with Pool(4) as p:
        p.map(burn, [1000] * 4)
        t0 = time.perf_counter()
        p.map(burn, [N] * 4)
        par = time.perf_counter() - t0
```

<!-- runs: 16-procs -->

```
تتابعاً  :   260.3 ms
٤ عمليات :    80.7 ms   ×3.23
```

عمليةٌ لكل نواة، ولكلٍّ مفسّرها وقفلُها. والربح ×٣٫٢٣ بأربع عمليات — دون الأربعة
لأن تشغيل العمليات ونقل النتائج يكلّفان.

**ولاحظ سطرَي التسخين:** `burn(1000)` قبل القياس، و`p.map(burn, [1000] * 4)` قبل
القياس الثاني. بلا الثاني يُقاس بناءُ العمليات مع العمل، وهو أغلى منه على
الأحجام الصغيرة.

**والثمن أن البيانات تُنسَخ** بين العمليات بالتسلسل. وذلك موضوع الفصل `22`.

**ومنذ 3.12 يمكن تشغيل مفسّرين في العملية الواحدة** بقفلٍ لكلٍّ، وواجهتُهما في
`concurrent.interpreters`. والحدُّ أن مشاركة الكائنات بينهما مقيّدة.

## تمرين

اقسم `burn` على أربع عملياتٍ بـ`multiprocessing` وقِس، ثم اقسمها على أربعة خيوط
وقِس.

<!-- task -->

```python
from multiprocessing import Pool

with Pool(4) as p:
    p.map(burn, [N] * 4)
```

ثم اسأل: عند أي حجمٍ لـ`N` يصير ربحُ العمليات أقلَّ من كلفة إنشائها ونقل النتائج؟
اعرض الرقم.
