# ٢٤ — الملكية عبر الحدّ

الفصل `15` قال إن الكائن يُحرَّر حين يبلغ عدّاده صفراً. والفصل `23` انتهى بأن
مؤشّر C لا يزيد أي عدّاد. هنا يُحسَم من يحرّر ماذا.

---

## ثلاث حالاتٍ لا رابعة

كل دالّة C تعبر الحدّ تقع في واحدةٍ من ثلاث، **ويجب أن تعرف أيَّها قبل النداء**:

| ما تفعله الدالّة | من يملك | ما عليك |
|---|---|---|
| تقرأ مخزنك | Python | أن يبقى اسمٌ حياً على الكائن أثناء النداء |
| تكتب في مخزنك | Python | أن يكون المخزن قابلاً للكتابة (`readonly=False`) |
| تخصّص وتعيد مؤشّراً | C | أن تنادي دالّة التحرير التي تقابلها |

والصفّان الأوّلان هما ما فعله الفصل `23`. والثالث هو هذا الفصل.

---

## المخزن الذي يملكه C

**مثال**

<!-- part: 24-own -->

```python
a = np.arange(5, dtype=np.int64)
src = ffi.cast("long long *", ffi.from_buffer(a))

out = lib.px_scaled(src, a.size, 10)
print("عاد مؤشّرٌ:", ffi.typeof(out).cname)

view = np.frombuffer(ffi.buffer(out, a.size * 8), dtype=np.int64)
print("قراءةٌ بلا نسخ:", view, "| base:", type(view.base).__name__)

owned = view.copy()
lib.px_free(out)
print("بعد px_free، النسخة سليمة:", owned)

kept = ffi.gc(lib.px_scaled(src, a.size, 3), lib.px_free)
print("بـffi.gc:", np.frombuffer(ffi.buffer(kept, a.size * 8), dtype=np.int64))
print("والتحرير يتبع عدّاد المراجع، بلا نداءٍ منك.")
```

**المخرَج**

<!-- out -->

```
عاد مؤشّرٌ: long long *
قراءةٌ بلا نسخ: [ 0 10 20 30 40] | base: buffer
بعد px_free، النسخة سليمة: [ 0 10 20 30 40]
بـffi.gc: [ 0  3  6  9 12]
والتحرير يتبع عدّاد المراجع، بلا نداءٍ منك.
```

**`np.frombuffer` لا تنسخ:** `base` صار كائن `buffer` من cffi، والمصفوفة تقرأ
ذاكرة `malloc` مباشرةً.

**والترتيب في السطرين الثالث والرابع مقصود:** `view.copy()` **قبل** `px_free`.
ولو انعكس الترتيب لقرأت `copy` ذاكرةً محرَّرة.

**و`ffi.gc` هي الحلّ الصحيح:** تربط المؤشّر بدالّة التحرير، فينادَى `px_free`
حين يبلغ عدّاد مراجع `kept` صفراً. عدّادُ Python صار يحرّر ذاكرة C.

**المكسب:** `ffi.gc` تنقل المِلكية إلى نظام Python بسطرٍ واحد. وبلا ذلك كلُّ
مسار خطأٍ في كودك تسريبٌ محتمل، لأن `px_free` بعد `raise` لا تُنادى.

---

## الخطأ صامتٌ ومتأخّر

استعمالُ ذاكرةٍ محرَّرة لا يفشل في الحال. البايتات تبقى كما هي حتى يُعاد تخصيصها
لشيءٍ آخر، فيقرأ برنامجك قيماً صحيحةً **ثم قيماً غريبةً بعد ألف نداء**.

وهذا يفسّر ما تراه في الأخطاء الحقيقية: انهيارٌ في موضعٍ لا علاقة له بالخطأ، أو
نتيجةٌ خاطئةٌ بلا انهيار.

**والأدواتُ لا الحدس:**

<!-- shell -->

```
PYTHONMALLOC=malloc valgrind --leak-check=full .venv/bin/python prog.py
```

وعلى macOS `leaks` و`MallocStackLogging`. والفكرة واحدة: التسريب يُقاس ولا
يُستنتَج.

## الحالات

### `from_buffer` تمسك الكائن، و`cast` لا

`ffi.from_buffer(a)` تعيد كائناً يحفظ إشارةً إلى `a`، فيبقى حياً ما دام حياً.
و`ffi.cast(...)` عليه تعطي مؤشّراً **خامّاً** لا يحفظ شيئاً.

ولهذا الاصطلاح أن يُحفَظ ناتج `from_buffer` في اسمٍ إن طال عمر المؤشّر:

<!-- task -->

```python
keep = ffi.from_buffer(a)          # يمسك a
ptr = ffi.cast("long long *", keep)
```

وفي الفصل `23` نجا السطر لأن النداء وقع في نفس العبارة، فبقي المؤقّت حياً حتى
انتهائها.

## تمرين

أضف إلى `kernel.c` دالّةً تخصّص وتعيد مصفوفةً بطولٍ **تحسبه هي** (تصفية مثلاً)،
وأعِد الطول في معامِلٍ خارج.

<!-- task -->

```c
long long *px_filter(const long long *in, size_t n, long long min, size_t *out_n);
```

ثم لُفَّها بدالّة Python تعيد `ndarray` **تملك ذاكرتها**، بلا تسريبٍ في أي مسار
خطأ. واختبر التسريب بألف نداءٍ وقياس الذاكرة.
