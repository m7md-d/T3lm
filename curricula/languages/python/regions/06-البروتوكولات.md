# الإقليم ٠٦ — البروتوكولات

> `len` و`in` و`for` و`+` و`[]` ليست ميزاتٍ مبنيّةً في أنواعٍ بعينها. كلُّها
> **طلباتٌ لفتحاتٍ مسمّاة** في نوع الكائن.
>
> وهذا الإقليم يفتح القائمة ويقرأها، ثم يقيس ما يكلّفه اختيارُ الفتحة الخطأ.

## خريطة الفتحات

بدل أن تُشرَح القائمة، اجعل الكائن يبلّغ عن نفسه:

<!-- part: 06-protocol-map -->

```python
class Probe:
    def __getitem__(self, k):
        print("  __getitem__", repr(k))
        raise IndexError

    def __len__(self):
        print("  __len__")
        return 0

    def __contains__(self, v):
        print("  __contains__", v)
        return False

    def __add__(self, other):
        print("  __add__")
        return NotImplemented
```

<!-- out -->

```
len(p):
  __len__
p[3]:
  __getitem__ 3
2 in p:
  __contains__ 2
for _ in p:
  __getitem__ 0
p + 1:
  __add__
  TypeError: unsupported operand type(s) for +: 'Probe' and 'int'
```

أربعة تراكيب نحوية، وكلٌّ منها نداءٌ لفتحة. **ولا يوجد شيء آخر يجري.** ولأن
النوع صفةُ الكائن (البديهية الأولى)، فالفتحة تُطلَب وقت التشغيل من نوعٍ لم يكن
معروفاً قبله.

ولاحظ سطرين:

`for _ in p` نادت `__getitem__(0)` — ولا `__iter__` هنا. هذا **البروتوكول القديم
للتكرار**: إن غابت `__iter__` جرّب Python الفهرسة من الصفر حتى `IndexError`. وهو
باقٍ من قبل أن تُوجَد المكرِّرات، ولم يُحذَف لأن كوداً كثيراً يعتمد عليه.

و`p + 1` أعادت `NotImplemented` — وهي **قيمةٌ لا استثناء**. فذهبت Python تسأل
الطرف الآخر `int.__radd__`، فلم تجد، فرفعت `TypeError` بنفسها. وهذه هي الآلية
التي تجعل `2 * v` تعمل على نوعك بلا أن تلمس `int`.

## ثمنُ الفتحة الخطأ

**تنبّأ:** صنفان متطابقان، في أحدهما `__iter__` وفي الآخر `__getitem__` وحدها.
كلاهما يعمل مع `sum`. كم الفرق في الزمن؟

<!-- part: 06-iter-cost -->

```python
class WithIter:
    def __getitem__(self, i):
        return self.values[i]

    def __iter__(self):
        return iter(self.values)


class OnlyGetItem:
    def __getitem__(self, i):
        return self.values[i]
```

المخرَج:

<!-- runs: 06-iter-cost -->

```
__iter__ موجودة         0.93 ms
__getitem__ وحدها       8.89 ms
```

**عشرة أضعافٍ تقريباً.** لأن `__iter__` تسلّم مكرِّر القائمة نفسه، فتدور الحلقة
داخل C من أوّلها إلى آخرها. أمّا المسار القديم فيرجع إلى المفسّر **في كل عنصر**:
ينشئ كائن عدد للفهرس، وينادي طريقةً مكتوبةً بـPython، ويفحص هل رُفع `IndexError`.

وهذا هو الفرق نفسه الذي رأيتَه بين `sum` المدمَجة وحلقتك في الإقليم `01`، ظاهراً
هذه المرّة داخل صنفٍ واحد: **كلُّ رجوعٍ إلى المفسّر يُدفَع.**

**وهذه ليست حالةً نادرة.** كل صنفٍ فيه `__getitem__` بلا `__iter__` يعمل — ولذلك
لا يشتكي أحد، ويبقى الثمن مدفوعاً بلا أن يُرى.

## القدرة لا النوع

تمرين الإقليم `03` طلب منك أن ترفض ما لا يُهشَّم **بلا فحص نوع**. الجواب هنا:
اسأل عن **القدرة**.

`hash(v)` تنجح أو ترفع `TypeError`. و`iter(v)` كذلك. والسؤال عن القدرة أدقُّ من
السؤال عن النوع، لأن النوع قد يرث القدرة أو يفقدها أو يزوّرها — والفتحة وحدها هي
الحقيقة.

**وهذا هو الـduck typing بلا مجاز:** لا «إن مشى كالبطّة»، بل **«إن كانت الفتحة
مملوءة»**. وهي جملةٌ تُفحَص لا تُتخيَّل.

## التمرين

**اجعل `Table` يستجيب لـ`in` و`len` و`for`** بحيث:

<!-- task -->

```python
"v" in t          # هل يوجد عمودٌ بهذا الاسم
len(t)            # عدد الصفوف
for row in t      # الصفوف، لا الأعمدة
```

**والقيد:** لاحظ أن `in` و`for` هنا يتكلّمان عن شيئين مختلفين — الأول عن الأعمدة
والثاني عن الصفوف. **قرّر أيَّهما أصدق لجدول، واكتب سطرين يبرّران قرارك في
الملفّ.** لا يوجد جوابٌ واحد صحيح؛ يوجد جوابٌ متّسق وجوابٌ يفاجئ من يقرأ كودك.

**ثم:** بعد أن تكتب `__iter__` على الجدول، قِس `sum(len(r) for r in t)` قبلها
وبعدها.

## الخلاصة

النحو كلُّه سكرٌ فوق فتحاتٍ مسمّاة، وقائمتُها هي الواجهة الحقيقية للغة. ونوعك يصير
مواطناً كامل الحقوق بمقدار ما تملأ منها.

واختيار الفتحة يُدفَع ثمنُه: المسار الذي يبقى داخل C أسرع عشرة أضعافٍ من المسار
الذي يرجع إلى المفسّر في كل عنصر.

وبقي سؤال: حين تكون الفتحة موجودةً في أكثر من موضع — في الكائن وصنفه وقواعده —
**من يفوز؟**
