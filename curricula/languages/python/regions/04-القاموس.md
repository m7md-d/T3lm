# ٠٤ — القاموس

القاموس هو بنية Python المركزية. الجدول في المنهج يخزّن أعمدته فيه، وكل كائنٍ
تكتبه يحمل قاموساً لسماته، وكل وحدةٍ تستوردها قاموسٌ لأسمائها.

---

## كيف يجد المفتاح

القاموس يحسب `hash(key)` فيحصل على عددٍ صحيح، ويستعمله ليختار خانةً في مصفوفة
داخلية. وحين يجد في الخانة مفتاحاً، يقارنه بـ`==` ليتأكّد.

فالبحث خطوتان: **تجزئةٌ تحدّد الموضع**، ثم **مقارنةٌ تؤكّد الهوية**.

**مثال**

<!-- part: 04-lookup -->

```python
class Key:
    def __init__(self, name):
        self.name = name

    def __hash__(self):
        print(f"  __hash__ {self.name}")
        return hash(self.name)

    def __eq__(self, other):
        print(f"  __eq__ {self.name} == {other.name}")
        return self.name == other.name
```

**المخرَج**

<!-- out -->

```
الإدخال:
  __hash__ a
البحث:
  __hash__ a
  __eq__ a == a
1
```

الإدخال نادى `__hash__` وحدها: الخانة كانت فارغة فلا شيء يُقارَن. والبحث نادى
الاثنتين.

**المكسب:** إن عرّفتَ `__eq__` على صنفك ولم تعرّف `__hash__`، يجعل Python صنفك
غير قابلٍ للتجزئة. القاعدة أن المتساويين يجب أن يعطيا التجزئة نفسها، ولو كسرتها
لضاعت المفاتيح في قاموس.

---

## المفتاح يجب أن يمنع التعديل

**مثال**

<!-- part: 04-hash -->

```python
print(hash("sales") == hash("sales"))
print(hash((1, 2)))

d = {}
d[[1, 2]] = "x"
```

**المخرَج**

<!-- err: TypeError -->

```
True
-3550055125485641917
TypeError: cannot use 'list' as a dict key (unhashable type: 'list')
```

`list` لا يعرّف `__hash__`. والسبب أن تجزئته ستتغيّر بتغيّر محتواه، فيصير المفتاح
في خانةٍ لا يجده البحث فيها.

**وهذا يشرح ما رأيتَه في الفصل `03`:** `tuple` يصلح مفتاحاً لأنه يمنع الاستبدال،
لكن `tuple` يحمل قائمةً لا يصلح — تجزئتُه تنزل إلى عناصره فتصطدم بالقائمة.

## الترتيب

منذ Python 3.7 يحفظ القاموس ترتيب الإدخال، وهذا جزءٌ من اللغة لا تفصيلُ تنفيذ.

**مثال**

<!-- part: 04-order -->

```python
d = {}
for key in ["zebra", "apple", "mango"]:
    d[key] = len(key)

print(list(d))

del d["apple"]
d["apple"] = 5
print(list(d))
```

**المخرَج**

<!-- out -->

```
['zebra', 'apple', 'mango']
['zebra', 'mango', 'apple']
```

الترتيب ترتيبُ أوّل إدخال. والحذف ثم الإضافة يضعان المفتاح في آخر الصفّ،
بينما `d["zebra"] = 9` على مفتاحٍ موجود يبدّل القيمة ويبقي الموضع.

**المكسب:** الجدول في المنهج يعتمد على هذا. `Table.__len__` تأخذ أول عمودٍ
بـ`next(iter(...))`، و«أوّل» هنا معرَّفٌ لأن الترتيب مضمون.

## الحالات

### كلفة البحث تُقاس، ولا تُوصَف بـ«ثابتة»

البحث لا يمرّ على المفاتيح: يحسب التجزئة ويقفز. فعددُ المقارنات ثابتٌ مهما كبر
القاموس — والزمن ليس كذلك.

**مثال**

<!-- part: 04-cost -->

```python
for size in (1_000, 100_000, 10_000_000):
    d = {i: i for i in range(size)}
    keys = [random.randrange(size) for _ in range(200_000)]

    t0 = time.perf_counter()
    for k in keys:
        d[k]
    per = (time.perf_counter() - t0) / len(keys) * 1e9

    print(f"{size:>10,} مفتاحاً   {per:6.1f} ns للبحث")
```

**المخرَج**

<!-- runs: 04-cost -->

```
     1,000 مفتاحاً     39.6 ns للبحث
   100,000 مفتاحاً     63.8 ns للبحث
10,000,000 مفتاحاً    789.7 ns للبحث
```

الأرقام من جهازٍ واحد، والثابت هو النسبة. وعشرةُ ملايين مفتاح أبطأ **عشرين
ضعفاً** من الألف، وعددُ المقارنات في الحالتين واحد.

السبب أن الجدول عند هذا الحجم لا يسكن الذاكرة المخبَّأة، فكل بحثٍ يقفز إلى موضعٍ
عشوائيٍّ في الذاكرة الرئيسية. **والقفزة هي ما يُقاس هنا**، وحسابُ التجزئة ثابتٌ
في الأحجام الثلاثة.

**المكسب:** «ثابتة الكلفة» جملةٌ عن عدد المقارنات وحده. وهذه الجملة نفسها تعود في
الفصل `17` حين تقارن `list` بمصفوفةٍ متجاورة، وفي `21` حين تقيس ما تكسبه NumPy.
