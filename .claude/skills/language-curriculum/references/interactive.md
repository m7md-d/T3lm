# الكود التفاعلي في موقع المنهج

> يُقرأ مع `curriculum-site-design`. ذلك المهارة تحكم الشكل والثيم؛ هذا الملف يحكم
> **الكود الحيّ**: كيف يُلوَّن، كيف يُحرَّر، كيف يُنفَّذ فعلاً، وأين يستحيل تنفيذه.

**المبدأ الحاكم:** البلوك التفاعلي ليس زينة تقنية — هو **آلة تنفيذ قاعدة "تنبّأ ثم
شغّل"** (`craft.md` §٤). إن لم يخدم البلوك التفاعلي دفن اعتقاد أو كشف آلية، فهو
بلوك عرض عادي ولا يحتاج جافاسكربت.

---

## الطبقات الأربع (لا تخلطها)

### الطبقة ١ — العرض: Shiki

**الافتراضي لكل بلوك كود.** [Shiki](https://shiki.style) يستعمل **نفس محرّك VS
Code**: قواعد TextMate وثيمات VS Code نفسها. تلوين مطابق حرفياً، لا تقريب بـregex.

- يُشغَّل **وقت البناء** (build-time) ويُخرج HTML جاهزاً: صفر جافاسكربت وقت التصفّح،
  صفر وميض، يعمل بلا شبكة.
- الثيمات المدمجة (`dark-plus`, `github-dark`, `vitesse-dark`, …) متاحة مباشرة.
- **التكامل مع ثيم الموقع (مهم):** `curriculum-site-design` تفرض اشتقاق الثيم من
  الموضوع. لا تفرض ألوان `dark-plus` الزرقاء على ثيم كهرماني أو أخضر حمضي. الحل:
  استعمل وضع **متغيّرات CSS** في Shiki، واربط ألوان التلوين بـtokens الموقع نفسها.
  البديل: ولّد ثيم TextMate بصيغة JSON مشتقّاً من لوحة الموقع ومرّره لـShiki.
  «ألوان VS Code» تعني **دقّة التوكنة**، لا اختطاف لوحة الموقع.
- استعمل خصائص Shiki العملية: إبراز أسطر بعينها، تمييز أسطر مضافة/محذوفة، وتعليقات
  داخل الكود — مفيدة جداً لـ"التشريح سطراً سطراً".

### الطبقة ٢ — التحرير: CodeMirror 6 (أو Monaco)

للبلوكات التي يعدّلها المتعلّم فقط.

- **CodeMirror 6** هو الافتراضي: خفيف، معياري، يعمل جيداً على الجوال. لثيم VS Code:
  `@uiw/codemirror-theme-vscode` (`vscodeDark`) أو ثيمات `@fsegurai/codemirror-themes`.
- **Monaco** هو محرّر VS Code نفسه حرفياً — يعطي مطابقة كاملة (نفس التلوين، نفس
  الاختصارات، إكمال) لكنه ثقيل جداً ومزعج على الجوال. لا تستعمله إلا إن كان "شعور
  المحرّر الحقيقي" جزءاً من هدف الدرس.
- **قاعدة bidi:** الصفحة RTL. أي محرّر داخلها يحتاج `direction: ltr;
  unicode-bidi: isolate;` صراحةً على حاويته، وإلا انهار عرض الكود.
- **لا تجعل كل بلوك محرّراً.** المحرّر يوحي «عدّلني»؛ استعماله على كود للقراءة فقط
  تشويش. Shiki للقراءة، CodeMirror للتعديل.

### الطبقة ٣ — التنفيذ: يعتمد على اللغة (لا يوجد حل واحد)

| اللغة | المحرّك | يعمل في المتصفّح؟ | ملاحظات |
|---|---|---|---|
| Python | Pyodide (CPython كامل) أو Runno | نعم | Pyodide أثقل لكنه أوفى وفيه حزم |
| C / C++ | Runno (`clang`/`clangpp`) | نعم | WASI، بلا شبكة، stdin/stdout فقط |
| Ruby / PHP / SQLite / JS | Runno (`ruby`/`php-cgi`/`sqlite`/`quickjs`) | نعم | — |
| **Go** | **لا يدعمه Runno** — انظر أدناه | جزئياً | أهم حالة، وأخطرها |
| Rust | واجهة `play.rust-lang.org` (خادم) | لا | تحتاج وسيطاً لـCORS |

**Runno** (`@runno/runtime`): مكوّنات ويب جاهزة
(`<runno-run runtime="python" editor controls>`) فوق WASI preview1 مع نظام ملفات
وهمي وبلا شبكة. **قيد نشر حرج:** يحتاج عزلاً عبر الأصول
(`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy:
require-corp`). الاستضافات الساكنة التي لا تسمح بضبط الترويسات (مثل GitHub Pages)
تحتاج حيلة `coi-serviceworker`. **قرّر هذا قبل اختيار الاستضافة، لا بعدها.**

**Go تحديداً — ثلاثة مسارات، ولكلٍّ ثمن:**

1. **واجهة Go Playground الرسمية** (`go.dev/_/compile`): مترجم `gc` الحقيقي، يشمل
   `go vet`. أدقّ خيار دلالياً. لكنه **خادم**: يحتاج وسيط CORS (Cloudflare Worker
   صغير يكفي)، ومحدود بمعدّل الطلبات، وساعته وهمية، وبلا شبكة، وبلا ملفات.
2. **Yaegi مُصرَّفاً لـWASM**: مفسّر Go يعمل كلياً في المتصفّح، ويدعم الـgoroutines
   والقنوات فعلياً (فوق runtime الحقيقي). لكن: **لا ملفات تجميع (.s)، لا cgo، لا
   توجيهات مترجم، و`unsafe` معطّل افتراضياً** — أي أنه يعجز بالضبط عن المحاور
   منخفضة المستوى في المنهج.
3. **GopherJS** (ما يستعمله LiveCodes): يترجم Go إلى JavaScript، ويعمل بلا خادم.
   لكن إصداره متأخّر عن Go الحديث — وهذا **قاتل** لمنهج مبنيّ على الحواف.

### الطبقة ٤ — محليّ فقط (لا تكذب على المتعلّم)

هذه لا تعمل في المتصفّح **إطلاقاً**، ولا تحاول محاكاتها:

- إخراج التجميع (assembly) وتفكيك الملف التنفيذي.
- تحليل الهروب للكومة (escape analysis) وقرارات المترجم.
- كاشف السباقات، التشريح الزمني (profiling)، القياس (benchmarking).
- حجم الملف التنفيذي، الرموز، الاعتماديات، نداءات النظام.

**بلوكات هذه الفئة تُوسَم بصرياً بوسم واضح** («يُشغَّل محلياً») مع الأمر كاملاً
والمخرج الحقيقي مطبوعاً. عدم الوسم يجعل المتعلّم يجرّب ويفشل ويظن أن العيب فيه.

## عقد وسم البلوكات

كل بلوك كود في المنهج يحمل ثلاث سمات، تُقرّر وقت الكتابة لا وقت البناء:

```
lang    : اللغة (للتلوين)
run     : none | edit | run:<engine> | local
version : الإصدار الذي شُغّل عليه فعلاً وأنتج المخرج المكتوب
```

- `none` → Shiki فقط. **الافتراضي**، والأغلبية.
- `edit` → CodeMirror بلا تنفيذ (تمارين قراءة وتعديل ذهني).
- `run:<engine>` → قابل للتنفيذ، مع تسمية المحرّك صراحةً.
- `local` → وسم "محلياً" + المخرج الحقيقي مطبوع.

## قاعدة الأمانة الدلالية (الأهم في هذا الملف)

**حالات الحواف تُشغَّل على المحرّك الحقيقي، أو لا تُشغَّل.**

المنهج مبنيّ على حالات شاذّة وفروق بين الإصدارات (`craft.md` §٨). المفسّرات
والمترجمات البديلة في المتصفّح **تختلف عن التنفيذ المرجعي بالضبط في هذه النقاط**:
مفسّر متأخّر بإصدارات سيُظهر السلوك القديم، فيعلّم المتعلّم عكس ما يقوله النص، وهو
يظن أنه "تحقّق بنفسه". هذا أسوأ من عدم وجود زر تشغيل أصلاً.

لذلك:
- بلوكات الحواف والسلوك الدقيق ← المحرّك المرجعي (واجهة الخادم الرسمية) أو `local`.
- بلوكات التوضيح العامّة ← أي محرّك متصفّح، **مع لافتة تذكر المحرّك وإصداره**.
- عند أي شكّ: `local`.

## أنماط الاختبار التفاعلي

1. **بوّابة التنبّؤ** (الأساس): الكود ظاهر، **المخرج محجوب**، وحقل إدخال للتوقّع.
   لا يظهر زر التشغيل قبل إدخال توقّع. بعد التشغيل: عرض المتوقّع والحقيقي جنباً
   إلى جنب مع الفرق. هذه هي الآلية التي تدفن الاعتقاد فعلياً.
2. **الكود المكسور**: كود لا يُترجم، والمطلوب إصلاحه. **رسالة المترجم الحقيقية هي
   المعلّم** — لا تعيد صياغتها ولا تلخّصها.
3. **اختبار حقيقي**: يشغّل الكود مقابل حالات، ويعرض نجاح/فشل **من التنفيذ الفعلي**.
4. **املأ الفراغ**: منطقة قابلة للتحرير داخل هيكل ثابت، مع تحقّق بالتنفيذ.
5. **قِس بنفسك**: `local` دائماً.

**ممنوع منعاً باتاً: التقييم بمطابقة نصية مع جواب مخزَّن.** التقييم يكون بتنفيذ
حقيقي ومقارنة مخرجات. مطابقة النصّ تكذب على المتعلّم وتُصحّح الخطأ الصحيح وتقبل
الحلّ الخاطئ.

**ولا تُسرّب الحلّ في مصدر الصفحة.** المتعلّم يستطيع فتح مصدر HTML. إن احتاج
التحقّق مخرجاً متوقّعاً، خزّن **بصمته (hash)** بعد التطبيع، لا نصّه. هذا امتداد
مباشر لقاعدة "لا حلّ قبل الكفاح".

## قواعد هندسية

- **تحسين تدريجي (progressive enhancement):** الكود المُلوَّن من Shiki موجود في
  HTML دائماً. التفاعلية تُركَّب فوقه. بلا جافاسكربت أو مع CDN محجوب، الصفحة تبقى
  مقروءة كاملة.
- **تحميل كسول:** أنوية التنفيذ تُقاس بعشرات الميغابايت. لا تُحمَّل إلا عند أول
  ضغطة "تشغيل"، مع مؤشّر تقدّم صريح. لا تعلّق تحميل الصفحة على شيء منها.
- **تثبيت الإصدارات** لكل مكتبة، وتفضيل الاستضافة الذاتية للأصول على CDN خارجي.
- **حالات الفشل مرئية:** انقطاع الشبكة، تجاوز حد الطلبات، حلقة لا نهائية. مهلة
  زمنية صريحة ورسالة واضحة، لا دوران أبدي.
- **المنهج يبقى قابلاً للدراسة كنصّ.** الموقع يضيف طبقة تحقّق، ولا يصير شرطاً
  لفهم المادة (`curriculum-architect`: مكتفٍ ذاتياً).
